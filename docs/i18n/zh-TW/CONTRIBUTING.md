# 貢獻指南

> 🌐 [English](../../CONTRIBUTING.md) · [Português (Brasil)](../pt-BR/CONTRIBUTING.md) · [中文（简体）](../zh-CN/CONTRIBUTING.md) · **中文（繁體）**

> **非官方社群專案,與 DeepSeek 無關聯、未經其認可,也未獲其贊助。**
> DeepSeek 的名稱與標識歸其各自所有者所有。

感謝你為改善本目錄所做的貢獻。貢獻遵循創作者優先的原則:使用原始儲存庫證據、保留掛名,並確保每個外掛都能獨立審查。目錄在設計上從空目錄開始;任何條目都必須經過獨立審查的提取請求(PR)才會被接受。

## 從創作者開始

由外掛創作者本人或所屬組織直接開啟的提取請求,永遠是優先選項。如果創作者已準備好貢獻,應使用他們自己的分支與提取請求,而不是在策展人或自動化分支中重新建立他們的成果。

當社群策展能幫助尚未開啟提取請求的創作者時,這樣的貢獻是受歡迎的。但這並不會為日後創作者直接提交的貢獻建立所有權或優先權。

## 一個外掛對應一個分支與提取請求

為單一外掛建立一個專屬分支,並從該分支開啟一個提取請求。該分支與提取請求必須恰好只建立或變更 `catalog/plugins/` 底下的一個 YAML 檔案。不要在該分支或提取請求中混入其他外掛、文件清理、產生的索引或無關的維護工作。

條目 ID 與檔案名稱必須是同一個小寫連字號命名(kebab-case)值。維護者會逐一審查並合併每個外掛的提取請求;包含多個外掛的批次不會被拆分或部分合併。

## 溯源到原始來源

每一個公開欄位都必須依據原始創作者儲存庫、套件、清單檔、README、授權條款或發行版本在固定提交(pinned commit)當下的內容重新建構。不要照抄其他目錄或聚合網站的敘述、分類、截圖、排名、徽章或產生的中繼資料。在總覽專案、市集、列表或聚合網站中找到的連結只是一條線索,不是證據,也不是外掛的來源。

切勿將總覽專案、聚合網站、市集、安裝器目錄或列表本身作為目錄條目提交,即使它可以被獨立安裝。應只將其當作線索,並將每個可獨立安裝的子外掛溯源到其真正的創作者與原始儲存庫。位於創作者真實單體儲存庫(monorepo)中的外掛,可以從其確切子路徑提交,但必須遵循下文的單體儲存庫星標政策。

## 必要的證據

請在提取請求中提供以下所有內容:

- 原始儲存庫的規範公開網址,以及其不可變的儲存庫節點 ID。維護者會在另外的溯源審查環節解析該節點 ID,並拒絕網址不一致的情況。
- 創作者的公開 GitHub 帳號,以及與之相符的公開個人檔案網址。YAML 只儲存一次帳號;個人檔案網址是依 `https://github.com/<handle>` 推導出來的。
- 完整的 40 字元原始提交 OID,以及確切的外掛子路徑;若外掛位於儲存庫根目錄,則為 `null`。
- 一段有長度限制的英文描述,以及其在該固定提交當下的證據路徑。
- 從 [docs/CATEGORIES.md](../../docs/CATEGORIES.md) 中選取的 artifact `kind`(種類)、主要分類與標籤。
- 在固定提交當下有證據支持的完整上游 SPDX 授權表達式。
- 一個固定到確切 npm 版本,或固定到來源儲存庫、完整提交與子路徑的規範安裝描述子。該描述子是資料,絕不是 shell 指令。
- 原生 DSH 整合的證據,以及其在固定提交當下的路徑。
- 針對該確切 artifact 版本、既有且非敏感的煙霧測試(smoke test)證據,或明確填入 `not run`。不要只為了準備目錄貢獻,就安裝該外掛或執行 `preinstall`、`install`、`postinstall`、`prepare` 等套件/外掛生命週期程式碼。
- 對於專屬儲存庫,提供該確切儲存庫可驗證的星標數,以及其公開來源與查核時間。對於單體儲存庫中的外掛,請採用下文要求的必要空值(null)政策。
- 若存在公開的 Discussion 或留言溯源資訊,請一併提供;否則使用 `null`。
- 機器可讀的 `unofficial: true` 值。

若目前不存在符合條件的煙霧測試,請使用 `verification.status: eligible` 與 `verification.smokeTest: null`。只有當該確切版本存在可供審查的煙霧測試證據時,才使用 `verified`。這兩種狀態都不代表官方背書或安全認證。

切勿提交憑證、Cookie、私人電子郵件地址、未公開的原始碼或其他機密資訊。

## YAML 與結構描述(schema)規則

建立 `catalog/plugins/<plugin-id>.yaml` 檔案,並對照 [`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml) 進行驗證。該結構描述檔案是欄位名稱與允許值的唯一真實來源;[docs/CATEGORIES.md](../../docs/CATEGORIES.md) 定義了如何選擇唯一的 artifact 種類、主要分類、標籤與儲存庫範圍。

npm 描述子必須包含有效的套件名稱與確切版本。公開結構描述會拒絕形似選項參數的值與無邊界的值,但不會重新實作 SemVer 或 SRI 的驗證邏輯:目錄驗證必須解析版本、要求確切的 SemVer,並將任何完整性(integrity)值解析為有效的 SHA-512 SRI。來源描述子綁定於 `source.repository`、`source.commit` 與 `source.subpath`,不會重複儲存可變的來源值。

安裝器必須使用參數陣列、停用 shell 執行,並在被呼叫指令支援的情況下,於目錄提供的位置引數前加上選項終止符。提交驗證絕不能呼叫安裝器或外掛生命週期。

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` 是一項本機的、唯讀的結構與語意檢查。它會解析安全 YAML、驗證公開結構描述、解析 SPDX 表達式、要求確切的 SemVer 與有效的 SHA-512 SRI,並拒絕重複的 ID 以及重複的「儲存庫節點 ID + 子路徑」規範鍵值。它不會連上 GitHub、解析儲存庫身分,也不會檢查固定提交當下的證據路徑。

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

在條目達到 `eligible` 狀態之前,維護者會另外解析規範儲存庫與節點 ID,將創作者與原始來源綁定,並檢查在 `source.commit` 當下宣告的描述、授權、DSH 整合與煙霧測試證據。本機驗證通過並不能證明溯源或來源的真實性。

## 儲存庫星標

只能記錄經過驗證、確實屬於該專屬外掛儲存庫的星標數。絕不能將母專案的星標歸給存放在更大單體儲存庫(monorepo)中的外掛。單體儲存庫中的條目仍可進入目錄的功能性區塊,但必須宣告:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

專屬條目使用 `repositoryScope: dedicated`、`starsPolicy: exact-repository`,以及在同一儲存庫上觀察到的非負星標數。提交熱度資料前,請先閱讀 [docs/RANKING.md](../../docs/RANKING.md)。

## 創作者優先與禮貌聯繫

對於同一個規範外掛,優先順序如下:

1. 由創作者或所屬組織開啟的提取請求。
2. 經創作者明確核准的社群提取請求。
3. 現有有效的社群策展提取請求。
4. 目錄自動化提取請求。

創作者直接提交的提取請求,會取代任何開啟中的策展或自動化提取請求,無論哪一個先開啟或進度更靠前。創作者的提取請求會成為審查載體;維護者不會強制推送創作者的分支,也不會把他們的成果移植到策展提取請求中。如果策展條目已經合併,公開歷史不會被改寫。創作者可以先使用認領或更正請求,之後再直接貢獻一個後續的提取請求。

策展提取請求應在其描述中使用一次禮貌的公開 `@creator` 提及,並附上原始儲存庫的連結,邀請創作者審查或以直接提取請求取代它。不要重複提及、開啟宣傳性議題、跨平台轉發、傳送未經請求的私訊,或以其他方式打擾創作者。

<!-- creator-first:source-bound-git-identity -->

創作者本人撰寫的提取請求與提交會自然保留創作者掛名。策展提交只有在存在與來源綁定、可公開驗證的身分時,才能使用創作者的 Git 作者身分或 `Co-authored-by` 附註。絕不能捏造或猜測電子郵件地址。當沒有可驗證的 Git 身分時,由策展人擔任提交作者,並在 YAML 與提取請求中明確給出 `Created by @handle` 的掛名,以及原始儲存庫連結。維護者或自動化帳號可以擔任提交者或已驗證的共同作者,但絕不能取代創作者的作者身分。完整政策請參閱 [docs/CREDIT.md](../../docs/CREDIT.md)。

## 驗證指令與可用性

該 npm CLI 以 `@diegosouza.pw/dsh-plugins@0.1.0` 發布,因此下列指令目前可透過 `npx` 使用。請照原樣使用這些指令;貢獻者不應自行捏造替代指令。

請在儲存庫根目錄執行下列指令:

```bash
npx @diegosouza.pw/dsh-plugins catalog validate --catalog .
npx @diegosouza.pw/dsh-plugins catalog docs-check .
npx @diegosouza.pw/dsh-plugins catalog github-forms-check .
```

`catalog validate` 只執行上文所述的本機 YAML、結構描述、SPDX、確切 SemVer、SHA-512 SRI 與重複項檢查,並接受刻意為之的零條目目錄。它無法證明遠端儲存庫身分或固定來源證據。其他指令會檢查所需的公開文件與結構化的 GitHub Issue 表單。這些指令在本機通過,並不會放寬證據要求;維護者在合併前仍會套用每一項對應的發布關卡。

## 審查關卡、衝突與合併

維護者會在合併前,對當前提取請求的提交套用每一項關卡:

1. **範圍:** 一個專屬分支、一個外掛 YAML 檔案,且沒有無關的變更。
2. **原始身分:** 創作者、規範儲存庫、節點 ID、完整提交與子路徑彼此一致。
3. **結構描述與證據:** YAML、分類、SPDX、安裝固定版本、DSH 證據與煙霧測試狀態,在不執行外掛生命週期程式碼的情況下保持內部一致。
4. **熱度:** 專屬儲存庫的星標可在該確切儲存庫上驗證,或單體儲存庫的星標為 `null` 並附帶 `undefined-parent-repository`。
5. **文件與表單:** 公開文件、Markdown 圍欄與結構化表單保持有效。
6. **衝突與去重:** 沒有任何已合併條目或未關閉的提取請求代表同一個規範外掛。

不同的名稱或 ID 不會使重複的外掛變得不同。相同的儲存庫節點 ID 與子路徑、相同的規範套件,或其他可證明相同的安裝目標,都應視為衝突。合併前必須先解決別名與互相競爭的提取請求。當創作者直接提交的提取請求與策展或自動化提取請求發生衝突時,創作者的提取請求獲勝;否則維護者會選定一個作為審查載體,並關閉或重新導向其餘重複項,而不是兩者都合併。

只有在所有關卡都通過後,才會由維護者合併外掛。每個被接受的外掛都是個別合併的;通過驗證、策展或自動化並不代表會自動或批次合併。

## 提取請求檢查清單

- [ ] 我使用了一個專屬分支,且此 PR 只變更了一個外掛條目。
- [ ] 來源是原始創作者儲存庫,而不是總覽專案或聚合網站。
- [ ] 創作者帳號/個人檔案、儲存庫、節點 ID、子路徑與完整提交都已提供證據。
- [ ] 種類(kind)、分類與標籤遵循 `docs/CATEGORIES.md`。
- [ ] SPDX 授權與固定的安裝描述子都已提供證據。
- [ ] 原生 DSH 整合,以及煙霧測試結果或 `not run` 狀態,都已提供證據。
- [ ] 我沒有為了準備此貢獻而執行外掛或套件生命週期程式碼。
- [ ] 專屬儲存庫的星標可驗證,或單體儲存庫的星標使用了所要求的空值政策。
- [ ] 我已確認是否存在同一規範外掛的既有條目或未關閉的提取請求。
- [ ] 該條目已明確標示為非官方,且不含任何機密資訊或私人個人資料。
