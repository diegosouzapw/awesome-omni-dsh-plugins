# 目錄治理

> 🌐 [English](../../docs/GOVERNANCE.md) · **中文（繁體）**

> **非官方社群專案,與 DeepSeek 無關聯、未經其認可,也未獲其贊助。**
> DeepSeek 的名稱與標識歸其各自所有者所有。

本頁說明公開目錄的治理方式:由誰決定收錄什麼內容、彼此競爭的貢獻依什麼順序被尊重、哪些檢查
是自動執行的、哪些判斷仍然保留給人來做。這裡引用的政策分別記載於
[CONTRIBUTING.md](../../CONTRIBUTING.md)、[docs/CREDIT.md](../../docs/CREDIT.md) 與
[docs/RANKING.md](../../docs/RANKING.md);本頁說明的是它們如何整合在一起運作。

## 基本原則

1. **創作者優先。** 本目錄的存在是為了讓創作者的作品被更多人發現,而不是奪走其所有權。對於
   同一個標準外掛(canonical plugin),創作者本人直接開出的提取請求(PR),優先於任何既有、
   開啟中的社群策展(curation)或自動化提取請求——完整的優先順序與 Git 身分規則記載於
   [docs/CREDIT.md](../../docs/CREDIT.md)。
2. **一個外掛,一個經審查的提取請求。** 不進行批次合併,也不會有產生式的批量匯入直接進入公
   開目錄。每一個條目都必須贏得屬於它自己的審查。
3. **證據勝於信任。** 每一個公開欄位都必須可以追溯到原始創作者儲存庫中某個固定的提交
   (commit)。自動化檢查顯示綠燈,絕不會被當作來源證明來接受。
4. **永遠是非官方的。** 目錄中的任何狀態,都不會被呈現為 DeepSeek 的審查、認證或背書。

## 變更如何進入 `main`

所有變更都透過經審查的提取請求進入 `main`——不存在直接推送(push)。預設分支的運作政策如
下:

- **僅接受提取請求。** 目錄條目、文件與結構描述(schema)的變更,一律透過 PR 進入;目錄相
  關的 PR 必須遵守 [CONTRIBUTING.md](../../CONTRIBUTING.md) 中「每個分支一個外掛」的規則。
- **線性歷史紀錄。** PR 會以維持 `main` 線性、可稽核歷史紀錄的方式整合;已合併的公開歷史紀
  錄不會被改寫。若某個經策展的條目在創作者出面之前就已合併,創作者會透過後續的貢獻來認領或
  修正該條目,而不是改寫歷史紀錄。
- **審查討論串需先解決。** 審查對話必須在合併前解決完畢;未解決的意見回饋會擋下整合。
- **由維護者合併。** 只有維護者能合併外掛條目,且必須在目前 PR 的提交(commit)通過
  [CONTRIBUTING.md](../../CONTRIBUTING.md) →「審查關卡、衝突與合併」中的每一道關卡之後才能
  進行。

## `catalog-validation` 檢查

每一個觸及 `catalog/plugins/`、`schemas/` 或工作流程本身的提取請求,都會執行
`catalog-validation` 這項工作(job)(`.github/workflows/validate-catalog.yml`),並固定使用
已發布的 CLI:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**它驗證的內容**——僅限本機的結構與語意層面:

- 對 `catalog/plugins/` 底下每一個條目進行安全的 YAML 剖析。
- 符合公開結構描述(見 [docs/SCHEMA.md](../../docs/SCHEMA.md))。
- SPDX 表達式剖析、確切的 SemVer 版本、有效的 SHA-512 SRI 完整性(integrity)值。
- 拒絕重複:不允許重複的條目 ID,也不允許重複的標準儲存庫節點加子路徑組合鍵。
- 刻意設計的零條目目錄狀態也能通過驗證(`0 entries valid; catalog is empty`)。

**它「不會」驗證的內容**——因此綠燈檢查絕不代表以下事項已獲證明:

- 遠端儲存庫身分:它不會連線 GitHub,也不會將儲存庫節點 ID 與網址進行核對。
- 固定提交當下的證據:描述、授權條款、DSH 整合與煙霧測試(smoke test)證據都不會被擷取或檢
  視。
- 創作者所有權、星標數,或與既有開啟中提取請求之間的衝突。

這些判斷屬於維護者另外的溯源關卡,會在合併前套用,詳見
[CONTRIBUTING.md](../../CONTRIBUTING.md)。本機檢查只是最低門檻,不是通過標準本身。

## 驗證狀態

驗證會針對每一個條目、依其確切的固定提交進行記錄,使用公開結構描述中定義的狀態(`eligible`、
`verified`、`stale`、`unavailable`、`archived`、`quarantined`)。其中兩種正向狀態被刻意定義
得很狹窄:

- `eligible`(合格)——公開結構與原生 DSH 整合已通過驗證。
- `verified`(已驗證)——在此之外,還針對其固定來源或套件通過了一次安裝的煙霧測試;結構描
  述要求該煙霧測試紀錄必須存在。

無論是這兩種狀態,或是其他任何狀態,都不代表任何背書、保證或安全認證。完整語意(包含這些狀
態如何與排名互動)記載於 [docs/RANKING.md](../../docs/RANKING.md);紀錄格式則記載於
[docs/SCHEMA.md](../../docs/SCHEMA.md)。

## 認領、更正與移除

結構化的 GitHub Issue 表單(`.github/ISSUE_TEMPLATE/`)是變更「非你本人所提交」條目的正式管
道:

| 表單           | 使用對象                                  | 結果                                                     |
| -------------- | ------------------------------------------- | ------------------------------------------------------- |
| **認領(Claim)**      | 外掛被他人策展收錄的創作者本人 | 所有權會綁定回原始來源;之後創作者即可直接貢獻 |
| **更正(Correction)** | 任何發現公開中繼資料有誤的人 | 針對受影響條目進行經審查的修正             |
| **移除(Removal)**    | 希望下架自己作品的創作者,或違規行為的檢舉人 | 針對該條目進行經審查的移除或隔離處理 |

適用於以上三種流程的共通規則:

- 所有權主張必須有可驗證的公開證據佐證(儲存庫擁有者身分、套件著作權、清單中繼資料或固定的
  來源歷史紀錄)——在 Discussion 上留言並不構成創作者身分的認定
  ([docs/CREDIT.md](../../docs/CREDIT.md))。
- 已收錄外掛中的安全問題,應先回報給該外掛本身的維護者;目錄這一側之後才處理更正或隔離,且
  不會公開漏洞利用細節([SECURITY.md](../../SECURITY.md))。
- 絕不在表單中包含憑證、私人聯絡方式或其他機密資訊。

## 角色

- **創作者**擁有自己外掛及其掛名條目的優先權。他們可以直接貢獻、核准社群策展,或認領/更正/
  移除既有條目。
- **社群貢獻者**可以在遵守 [docs/CREDIT.md](../../docs/CREDIT.md) 中尊重聯繫與掛名規則的前
  提下,為尚未親自貢獻的創作者策展條目。策展永遠不會凌駕於創作者本人後續直接貢獻之上。
- **維護者**負責審查、套用溯源關卡、解決衝突並執行合併。他們同時維運官方網站
  ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online))與從私有原始碼發布
  的 CLI;本儲存庫的公開資料、結構描述與政策,正是這些對外介面所依賴使用的內容。
