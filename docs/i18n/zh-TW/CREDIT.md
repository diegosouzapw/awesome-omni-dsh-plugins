# 創作者掛名與提取請求優先順序

> 🌐 [English](../../CREDIT.md) · [Português (Brasil)](../pt-BR/CREDIT.md) · [中文（简体）](../zh-CN/CREDIT.md) · **中文（繁體）**

本目錄的存在,是為了讓獨立完成的 DSH 作品能被更多人發現,而不是把作品的所有權從創作者手中
奪走。公開條目會引用原始儲存庫及一個不可變更的來源提交(commit)。

## 同一個外掛的優先順序

<!-- creator-first:direct-pr-supersedes-curation-and-automation -->

1. 由外掛創作者本人或其所屬組織開出的提取請求(PR)。
2. 經創作者明確核准或與其共同具名(co-authored)的社群提取請求。
3. 既有且有效的社群提取請求。
4. 目錄自動化流程開出的提取請求。
5. 尚無公開提取請求的私人候選條目。

同一個標準外掛(canonical plugin)若出現創作者本人直接開出的提取請求,無論其開出時間先後或
進度如何,一律優先於任何既有、開啟中的社群策展(curation)或自動化提取請求。創作者的提取請
求會成為審查媒介;其分支(branch)絕不會被覆寫、強制推送(force-pushed)或移植進策展用的
提取請求中。若某個經過策展的條目已經合併,其歷史紀錄會維持完整,創作者可以透過新的貢獻來認
領或修正該條目。

## 公開掛名

每一個目錄條目都會標示創作者的公開 GitHub 帳號、原始儲存庫、儲存庫節點 ID(node ID)、外掛
子路徑與完整的固定提交。公開的創作者檔案是由單一帳號推導而來,而不是另外儲存成第二個身分。
另外還有一道維護者溯源關卡,會單獨解析節點 ID,並拒絕儲存庫網址不相符的情況。提取請求描述
應寫明 `Created by @handle`,並附上來源儲存庫與來源提交的中繼資料。

在 Discussion 上發文或留言的人,不會因此自動被視為創作者。所有權主張必須有儲存庫擁有者或
組織、套件著作權、清單(manifest)中繼資料,或確切的固定來源歷史紀錄作為佐證。

## Git 身分

<!-- creator-first:source-bound-git-identity -->

提交(commit)的作者身分與提取請求的作者身分是分開的兩件事。由創作者本人發起的提取請求,其
提取請求作者維持為創作者本人,其提交也會自然保留該作者身分。維護者或自動化帳號可能會以提交
者(committer)身分出現,或作為經驗證的共同作者(co-author),但不得取代創作者的作者身分。

對於經策展的提交,只有在確切身分具備來源可佐證且可公開驗證(例如該身分已存在於原始儲存庫中
創作者本人提交的紀錄裡)的情況下,才可以將創作者設為 Git 作者,或加上 `Co-authored-by`
標記。絕不可臆測電子郵件、自行捏造 noreply 位址,或使用在未經授權的公開來源之外找到的私人
地址。

當無法取得已驗證的 Git 身分時,由策展者或自動化帳號擔任提交作者,並改以明確可見的方式給予
掛名:在條目與提取請求中寫明 `Created by @handle`、對應的公開檔案連結,以及原始儲存庫連結。
無論 Git 身分是否對應成功,可見的 YAML 掛名資訊都是必要項目。日後若創作者本人直接開出提取
請求,會取代既有的策展提取請求,而不會繼承其人工合成的歷史紀錄。

## 尊重創作者的提及方式

策展用的提取請求,只會在其描述中、緊鄰原始儲存庫連結處,以一次禮貌且公開的 `@creator` 方式
提及創作者。可以邀請對方參與審查或提出替代的直接提取請求,但不得重複提及、開立宣傳性質的
Issue、跨平台轉發,或私訊未經對方同意的訊息。

## 目錄授權與上游授權的差異

目錄中的事實資料與編輯用的 YAML 中繼資料,是以 CC0-1.0 方式公開釋出。這項釋出聲明不會改變
上游外掛本身的授權條款。上游程式碼、文件、螢幕截圖、標識與其他創作素材,仍持續受其原始授權
條款與所有者約束。
