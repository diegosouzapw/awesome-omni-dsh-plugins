# حوكمة الكتالوج

> 🌐 [English](../../docs/GOVERNANCE.md) · **العربية**

> **مشروع مجتمعي غير رسمي. لا علاقة له بشركة DeepSeek ولا يحظى بتأييدها أو رعايتها.**
> أسماء وعلامات DeepSeek ملك لأصحابها.

كيف يُحكَم الكتالوج العام: من يقرر ما يدخل، وبأي ترتيب تُحتَرم المساهمات المتنافسة، وأي الفحوصات
تعمل آليًا، وأي الأحكام تبقى بشرية. تعيش السياسات المُشار إليها هنا في
[CONTRIBUTING.md](../../CONTRIBUTING.md)، و[docs/CREDIT.md](../../docs/CREDIT.md)،
و[docs/RANKING.md](../../docs/RANKING.md)؛ وتصف هذه الصفحة كيف تتلاءم معًا.

## المبادئ

1. **صاحب الإضافة أولًا (Creator-first).** يوجد الكتالوج لجعل عمل المُنشئين قابلًا للاكتشاف،
   وليس لانتزاع ملكيته منهم أبدًا. بالنسبة لنفس الإضافة القانونية، يحلّ طلب سحب مباشر من المنشئ
   محل أي طلب سحب تنسيق مجتمعي أو أتمتة مفتوح — ترتيب الأولوية الكامل وقواعد هوية Git في
   [docs/CREDIT.md](../../docs/CREDIT.md).
2. **إضافة واحدة، طلب سحب واحد يُراجَع.** لا دمج دفعي، ولا استيراد جماعي مُولَّد إلى الكتالوج
   العام. يكسب كل إدخال مراجعته الخاصة.
3. **الدليل قبل الثقة.** يتتبع كل حقل عام مستودع المُنشئ الأصلي عند التزام (commit) مثبَّت. لا
   يُقبَل فحص آلي أخضر أبدًا كدليل على المصدر.
4. **غير رسمي، دائمًا.** لا تُعرَض أي حالة كتالوج على أنها مراجعة، أو شهادة، أو تأييد من DeepSeek.

## كيف تصل التغييرات إلى `main`

تصل كل التغييرات إلى `main` عبر طلبات سحب مُراجَعة — لا يوجد دفع مباشر (direct push). سياسة العمل
الخاصة بالفرع الافتراضي:

- **طلبات سحب فقط.** تدخل إدخالات الكتالوج، والتوثيق، وتغييرات المخطط كلها عبر طلب سحب؛ يجب أن
  تتبع طلبات سحب الكتالوج قاعدة إضافة واحدة لكل فرع في
  [CONTRIBUTING.md](../../CONTRIBUTING.md).
- **سجل خطي.** تُدمَج طلبات السحب بحيث يحافظ `main` على سجل خطي قابل للتدقيق؛ لا يُعاد كتابة
  السجل العام المُدمَج. إذا دُمج إدخال مُنسَّق قبل أن يتقدم المنشئ، يُطالِب المنشئ به أو يُصحِّحه
  في مساهمة متابعة بدلًا من إعادة كتابة السجل.
- **حلّ خيوط المراجعة.** تُحَلّ محادثات المراجعة قبل الدمج؛ وأي ملاحظات غير محلولة تحجب الدمج.
- **دمج المشرف.** يقوم مشرف واحد فقط بدمج إدخال إضافة، وفقط بعد اجتياز كل بوابة في
  [CONTRIBUTING.md](../../CONTRIBUTING.md) ← "بوابات المراجعة، والتعارضات، والدمج" على التزام
  طلب السحب الحالي.

## فحص `catalog-validation`

يُشغِّل كل طلب سحب يمسّ `catalog/plugins/`، أو `schemas/`، أو سير العمل نفسه مهمة
`catalog-validation` (`.github/workflows/validate-catalog.yml`)، المُثبَّتة عند الـ CLI المنشور:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**ما الذي يتحقق منه** — البنية والدلالات المحلية فقط:

- تحليل YAML آمن لكل إدخال تحت `catalog/plugins/`.
- المطابقة مع المخطط العام (راجع [docs/SCHEMA.md](../../docs/SCHEMA.md)).
- تحليل تعبير SPDX، وإصدارات SemVer دقيقة، وقيم سلامة (integrity) SRI صالحة من نوع SHA-512.
- رفض التكرار: لا معرّفات إدخال مكررة ولا مفاتيح "عقدة المستودع + المسار الفرعي" القانونية
  مكررة.
- ينجح الكتالوج الفارغ عمدًا (`0 entries valid; catalog is empty`).

**ما لا يتحقق منه** — وبالتالي ما لا يُثبته أبدًا الفحص الأخضر:

- هوية المستودع البعيدة: لا يتواصل مع GitHub ولا يحلّ معرّف عقدة المستودع مقابل عنوان URL.
- الدليل عند الالتزام المثبَّت: لا تُجلَب أو تُفحَص الأوصاف، والتراخيص، وتكامل DSH، ودليل اختبار
  التشغيل السريع.
- ملكية المُنشئ، وعدد النجوم، أو التعارض مع طلبات سحب مفتوحة.

تنتمي تلك الأحكام إلى بوابات إثبات المصدر (provenance) المنفصلة الخاصة بالمشرفين، والمُطبَّقة قبل
الدمج، والموصوفة في [CONTRIBUTING.md](../../CONTRIBUTING.md). الفحص المحلي هو الحد الأدنى، وليس
المعيار الكامل.

## حالات التحقق

يُسجَّل التحقق لكل إدخال مقابل التزامه (commit) المثبَّت الدقيق، باستخدام الحالات المُعرَّفة في
المخطط العام (`eligible`، و`verified`، و`stale`، و`unavailable`، و`archived`، و`quarantined`).
الحالتان الإيجابيتان ضيقتان عمدًا:

- `eligible` — تم التحقق من البنية العامة وتكامل DSH الأصلي.
- `verified` — إضافةً إلى ذلك، اجتاز اختبار تشغيل سريع للتثبيت للمصدر أو الحزمة المثبَّتة؛ يشترط
  المخطط وجود سجل اختبار التشغيل السريع.

لا تُشكِّل أي من الحالتين — ولا أي حالة أخرى — تزكية أو ضمانًا أو شهادة أمان. توجد الدلالات
الكاملة، بما في ذلك كيفية تفاعل الحالات مع الترتيب، في [docs/RANKING.md](../../docs/RANKING.md)؛
وشكل السجل في [docs/SCHEMA.md](../../docs/SCHEMA.md).

## المطالبات، والتصحيحات، وعمليات الإزالة

نماذج مشكلات (issue) GitHub المُهيكَلة (`.github/ISSUE_TEMPLATE/`) هي المسار المحكوم لتغيير
إدخال لم تُقدِّمه أنت:

| النموذج        | من يستخدمه                                   | النتيجة                                                    |
| -------------- | --------------------------------------------- | ------------------------------------------------------------ |
| **مطالبة (Claim)**      | منشئ تم تنسيق إضافته من قِبل شخص آخر | تُربَط الملكية بالمصدر الأصلي؛ ويمكن للمنشئ حينها المساهمة مباشرة |
| **تصحيح (Correction)** | أي شخص يلاحظ بيانات وصفية عامة غير دقيقة | إصلاح مُراجَع للإدخال المتأثر             |
| **إزالة (Removal)**    | منشئ يريد إزالة إدراجه، أو مُبلِّغ عن مخالفة سياسة | إزالة أو حجر صحي (quarantine) مُراجَعان للإدخال |

قواعد تنطبق على المسارات الثلاثة كلها:

- يجب أن تكون مطالبات الملكية مدعومة بدليل عام قابل للتحقق (ملكية المستودع، أو تأليف الحزمة، أو
  بيانات وصفية للبيان (manifest)، أو سجل مصدر مثبَّت) — التعليق على نقاش (Discussion) لا يُثبِت
  صفة المنشئ ([docs/CREDIT.md](../../docs/CREDIT.md)).
- تذهب مشكلات الأمان في إضافة مُدرَجة إلى القائم على صيانة تلك الإضافة أولًا؛ ثم يتعامل جانب
  الكتالوج مع التصحيح أو الحجر الصحي دون نشر تفاصيل الاستغلال
  ([SECURITY.md](../../SECURITY.md)).
- لا تُضمِّن أبدًا بيانات اعتماد، أو تفاصيل اتصال خاصة، أو أي أسرار أخرى في نموذج.

## الأدوار

- **المُنشئون** يملكون إضافاتهم وأولوية إدراجاتهم. يمكنهم المساهمة مباشرة، أو الموافقة على تنسيق
  مجتمعي، أو المطالبة بإدخال قائم/تصحيحه/إزالته.
- **المساهمون المجتمعيون** يمكنهم تنسيق إدخالات لمنشئين لم يساهموا بعد، وفق قواعد التواصل
  المحترم ونسب الفضل في [docs/CREDIT.md](../../docs/CREDIT.md). لا يتفوق التنسيق المجتمعي أبدًا
  على مساهمة مباشرة لاحقة من المنشئ.
- **المشرفون** يراجعون، ويُطبِّقون بوابات إثبات المصدر، ويحلّون التعارضات، ويدمجون. كما يصونون
  الموقع ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online)) والـ CLI
  المنشور من مصدر خاص؛ وبيانات هذا المستودع العامة، والمخطط، والسياسات هي ما تستهلكه تلك
  الأسطح.
