# 貢献する

> 🌐 [English](../../CONTRIBUTING.md) · **日本語**

> **これは非公式のコミュニティプロジェクトです。DeepSeek とは提携・承認・スポンサー関係はありません。**
> DeepSeek の名称および商標は、それぞれの権利者に帰属します。

カタログの改善にご協力いただきありがとうございます。貢献はクリエイター最優先です: 元のリポジトリの証拠を
使用し、帰属表示を保持し、各プラグインを個別にレビュー可能な状態に保ってください。カタログは設計上、空の
状態から始まります。個別にレビューされたプルリクエストなしに受け入れられるエントリはありません。

## クリエイターから始める

プラグインのクリエイター、またはそれを所有する組織が直接開いたプルリクエストが常に優先されます。クリエイ
ターが貢献する準備ができている場合は、その作業をキュレーターや自動化のブランチで再作成するのではなく、
クリエイター自身のブランチとプルリクエストを使用してください。

コミュニティによるキュレーションは、まだプルリクエストを開いていないクリエイターの助けになる場合に歓迎さ
れます。それは、その後に行われるクリエイター自身による直接の貢献に対して、所有権や優先権を確立するもの
ではありません。

## 1つのブランチとプルリクエストにつき1つのプラグイン

1つのプラグインのために専用のブランチを作成し、そのブランチから1件のプルリクエストを開いてください。ブラ
ンチとプルリクエストは、`catalog/plugins/` 配下の正確に1つのYAMLファイルを作成または変更しなければなりま
せん。そのブランチやプルリクエストに、複数のプラグイン、ドキュメントの整理、生成されたインデックス、無関
係なメンテナンスを混在させないでください。

エントリのIDとファイル名は、同じ小文字のkebab-case値でなければなりません。メンテナーは各プラグインのプル
リクエストを個別にレビューし、マージします。複数のプラグインを含むバッチは、分割されたり部分的にマージさ
れたりすることはありません。

## 元のソースを特定する

すべての公開フィールドは、固定されたコミットにおける、クリエイター元のリポジトリ、パッケージ、マニフェス
ト、README、ライセンス、またはリリースから再構築されなければなりません。他のカタログやアグリゲーターの文
章、カテゴリの割り当て、スクリーンショット、ランキング、バッジ、生成されたメタデータをコピーしないでくだ
さい。アンブレラプロジェクト、マーケットプレイス、リスト、またはアグリゲーターで見つかったリンクは、単な
る手がかりに過ぎず、証拠でもプラグインのソースでもありません。

アンブレラプロジェクト、アグリゲーター、マーケットプレイス、インストーラーカタログ、またはリストを、それ
が独立してインストール可能であっても、カタログエントリとして提出しないでください。それは手がかりとしての
み使用し、独立してインストール可能な各子プラグインを、その実際のクリエイターと元のリポジトリまで特定して
ください。クリエイターの実際のモノレポ内にあるプラグインは、その正確なサブパスから提出できますが、以下の
モノレポのスターポリシーに従わなければなりません。

## 必要な証拠

プルリクエストには、以下のすべてを提供してください:

- 元のリポジトリの正規の公開URLと、その不変のリポジトリノードID。メンテナーはノードIDを解決し、別個の来
  歴ゲートでURLの不一致を拒否します。
- クリエイターの公開GitHubハンドルと、それに対応する公開プロフィールURL。YAMLはハンドルを一度だけ保存
  し、プロフィールURLは `https://github.com/<handle>` として導出されます。
- 完全な40文字のソースコミットOIDと、プラグインの正確なサブパス。リポジトリのルートにあるプラグインの場
  合は `null`。
- 文字数が制限された英語の説明と、その固定されたコミットにおける証拠パス。
- アーティファクトの `kind`、主要カテゴリ、そして [docs/CATEGORIES.md](../../docs/CATEGORIES.md) から選
  択されたタグ。
- 固定されたコミットで証拠づけられた、upstreamの完全なSPDXライセンス表記。
- 正確なnpmバージョンに固定された正規のインストール記述子、またはソースリポジトリ・完全なコミット・サブ
  パスに固定された記述子。この記述子はデータであり、シェルコマンドでは決してありません。
- ネイティブDSH統合の証拠と、固定されたコミットにおけるそのパス。
- その正確なアーティファクトのpinに対する、既存の非機密なスモークテストの証拠、または明示的な値
  `not run`。カタログへの貢献を準備するためだけに、プラグインをインストールしたり、`preinstall`、
  `install`、`postinstall`、`prepare`、その他のパッケージ/プラグインのライフサイクルコードを実行したり
  しないでください。
- 専用リポジトリの場合、その正確なリポジトリの検証可能なスター数を、公開ソースとチェック日時とともに記載
  してください。モノレポのプラグインの場合は、以下の必須のnullポリシーを使用してください。
- 存在する場合は、公開Discussionまたはコメントの来歴。存在しない場合は `null` を使用してください。
- 機械可読な `unofficial: true` の値。

適格なスモークテストがまだ存在しない場合は、`verification.status: eligible` と
`verification.smokeTest: null` を使用してください。`verified` は、その正確なpinに対するレビュー可能なス
モークテストの証拠が存在する場合にのみ使用してください。どちらの状態も、推奨やセキュリティ認証を意味する
ものではありません。

認証情報、cookie、個人のメールアドレス、未公開のソース、その他の秘密情報を決して提出しないでください。

## YAMLとスキーマのルール

`catalog/plugins/<plugin-id>.yaml` を作成し、[`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml)
に対して検証してください。スキーマはフィールド名と許可される値についての信頼できる情報源です。
[docs/CATEGORIES.md](../../docs/CATEGORIES.md) は、単一のアーティファクトの種類、主要カテゴリ、タグ、リ
ポジトリスコープの選び方を定義しています。

npm記述子は、有効なパッケージ名と正確なバージョンを含まなければなりません。公開スキーマはオプションのよ
うな値や無制限の値を拒否しますが、SemVerやSRIを再実装するわけではありません: カタログの検証は、バージョ
ンをパースし、正確なSemVerを要求し、あらゆるintegrityの値を有効なSHA-512 SRIとしてパースしなければなり
ません。ソース記述子は `source.repository`、`source.commit`、`source.subpath` に紐づけられ、可変のソー
ス値を重複して持つことはありません。

インストーラーは引数の配列を使用し、シェル実行を無効化し、呼び出されるコマンドがサポートしている場合はカ
タログが提供する位置引数の前にオプション終端子を配置しなければなりません。提出時の検証は、インストーラー
やプラグインのライフサイクルを呼び出してはいけません。

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` は、ローカルで実行される、読み取り専用の構造的・意味的チェックです。安全なYAMLをパー
スし、公開スキーマを検証し、SPDX表記をパースし、正確なSemVerと有効なSHA-512 SRIを要求し、重複するIDや正
規のリポジトリノード+サブパスのキーを拒否します。GitHubに接続したり、リポジトリの識別情報を解決したり、
固定されたコミットにおける証拠パスを検査したりすることはありません。

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

エントリが `eligible` に到達する前に、メンテナーは正規のリポジトリとノードIDを個別に解決し、クリエイター
を元のソースに紐付け、`source.commit` における宣言された説明、ライセンス、DSH統合、スモークテストの証拠
を検査します。ローカルでの検証結果が緑であることは、来歴や出所の証明にはなりません。

## リポジトリのスター

検証可能に、そのプラグイン専用の正確なリポジトリに属するスターのみを記録できます。親プロジェクトのスター
が、より広いモノレポ内に格納されたプラグインに帰属することは決してあってはなりません。モノレポのエントリ
は、カタログの機能的なセクションには引き続き適格ですが、以下を宣言しなければなりません:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

専用エントリは `repositoryScope: dedicated`、`starsPolicy: exact-repository`、そしてその同じリポジトリ
で観測された非負のスター数を使用します。人気度データを提出する前に
[docs/RANKING.md](../../docs/RANKING.md) を読んでください。

## クリエイターの優先順位と敬意ある連絡

同一の正規プラグインについて、優先順位は以下のとおりです:

1. クリエイター、またはそれを所有する組織が開いたプルリクエスト。
2. クリエイターによって明示的に承認された、コミュニティによるプルリクエスト。
3. 既存の有効な、コミュニティによるキュレーションのプルリクエスト。
4. カタログ自動化のプルリクエスト。

クリエイター自身による直接のプルリクエストは、どちらが先に開かれたか、どちらがより進んでいるかにかかわら
ず、開いているキュレーションや自動化のプルリクエストに優先します。クリエイターのプルリクエストがレビュー
の対象となり、メンテナーはクリエイターのブランチにforce-pushしたり、その作業をキュレートされたプルリクエ
ストへ移植したりすることはありません。キュレートされたエントリがすでにマージされている場合、公開履歴が書
き換えられることはありません。クリエイターはクレームまたは修正のリクエストを利用したうえで、その後直接フ
ォローアップのプルリクエストを貢献することができます。

キュレートされたプルリクエストは、その説明文の中で、元のリポジトリへのリンクの隣に、敬意を込めた公開の
`@creator` メンションを1回だけ使用し、クリエイターにレビューまたは直接のプルリクエストへの置き換えを促す
べきです。メンションを繰り返したり、宣伝目的のissueを開いたり、クロスポストしたり、勧誘のないダイレクト
メッセージを送ったり、その他の方法でクリエイターにスパム行為をしたりしないでください。

<!-- creator-first:source-bound-git-identity -->

クリエイター自身が作成したプルリクエストとコミットは、自然にクリエイターへのクレジットを保持します。キュ
レートされたコミットは、ソースに紐づいた、公に検証可能なアイデンティティがある場合に限り、クリエイターの
Git authorshipまたは `Co-authored-by` トレーラーを使用できます。メールアドレスを決して創作したり推測した
りしないでください。検証済みのGitアイデンティティが利用できない場合、キュレーターがコミットのauthorとな
り、YAMLとプルリクエストの中で、元のリポジトリへのリンクとともに明示的な `Created by @handle` のクレジッ
トを与えます。メンテナーや自動化アカウントはcommitterまたは検証済みのco-authorになることができますが、ク
リエイターのauthorshipを置き換えてはいけません。完全なポリシーについては
[docs/CREDIT.md](../../docs/CREDIT.md) を参照してください。

## 検証コマンドと利用可能性

npmのCLIは `omni-dsh-plugins@1.0.0` として公開されているため、以下のコマンドは現在 `npx` を通
じて利用できます。記載されているとおりに正確に使用してください。貢献者は代替コマンドを創作すべきではあり
ません。

これらのコマンドはリポジトリのルートから実行してください:

```bash
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

`catalog validate` は、上記で説明したローカルのYAML、スキーマ、SPDX、正確なSemVer、SHA-512 SRI、重複の
チェックのみを行い、意図的にエントリ数がゼロのカタログを受け入れます。リモートのリポジトリの識別情報や、
固定されたソースの証拠を証明するものではありません。他のコマンドは、必要な公開ドキュメントと構造化された
GitHub issueフォームをチェックします。これらのコマンドをローカルで通過しても、証拠の要件が緩和されるわけ
ではありません。メンテナーは、マージ前に対応するすべてのリリースゲートを引き続き適用します。

## レビューゲート、衝突、マージ

メンテナーは、マージする前に、現在のプルリクエストのコミットに対してすべてのゲートを適用します:

1. **スコープ:** 1つの専用ブランチ、1つのプラグインYAMLファイル、そして無関係な変更がないこと。
2. **元の識別情報:** クリエイター、正規のリポジトリ、ノードID、完全なコミット、サブパスが一致しているこ
   と。
3. **スキーマと証拠:** YAML、カテゴリ、SPDX、インストールのpin、DSHの証拠、スモークテストの状態が、プラ
   グインのライフサイクルコードを実行することなく、内部的に整合していること。
4. **人気度:** 専用のスターが正確なリポジトリで検証可能であること、またはモノレポのスターが
   `undefined-parent-repository` とともに `null` であること。
5. **ドキュメントとフォーム:** 公開ドキュメント、Markdownのフェンス、構造化フォームが有効なままであるこ
   と。
6. **衝突と重複排除:** マージ済みのエントリや開いているプルリクエストが、同じ正規のプラグインを表してい
   ないこと。

名前やIDが異なっていても、重複したプラグインが別物になるわけではありません。同じリポジトリノードIDとサ
ブパス、同じ正規パッケージ、または実証的に同一と分かる別のインストールターゲットは、衝突として扱ってくだ
さい。マージする前に、エイリアスや競合するプルリクエストを解決してください。クリエイター自身による直接の
プルリクエストは、キュレーションや自動化との衝突に勝ちます。それ以外の場合、メンテナーは1つのレビュー対
象を選び、両方をマージするのではなく、重複を閉じるかリダイレクトします。

すべてのゲートを通過した後、メンテナーのみがプラグインをマージします。受け入れられた各プラグインは個別に
マージされます。検証、キュレーション、または自動化は、自動マージやバッチマージを意味しません。

## プルリクエストのチェックリスト

- [ ] 1つの専用ブランチを使用し、このPRは正確に1つのプラグインエントリを変更しています。
- [ ] ソースは、アンブレラやアグリゲーターではなく、元のクリエイターのリポジトリです。
- [ ] クリエイターのハンドル/プロフィール、リポジトリ、ノードID、サブパス、完全なコミットが証拠づけられ
      ています。
- [ ] kind、カテゴリ、タグが `docs/CATEGORIES.md` に従っています。
- [ ] SPDXライセンスと固定されたインストール記述子が証拠づけられています。
- [ ] ネイティブDSH統合と、スモークテストの結果または `not run` のステータスが証拠づけられています。
- [ ] この貢献を準備するために、プラグインやパッケージのライフサイクルコードを実行していません。
- [ ] 専用のスターが検証可能であるか、モノレポのスターが必須のnullポリシーを使用しています。
- [ ] 同じ正規のプラグインについて、既存のエントリと開いているプルリクエストを確認しました。
- [ ] このエントリは明示的に非公式であり、秘密情報や個人の非公開データを含んでいません。

## 言語ポリシー

ローンチ時のドキュメントとカタログの説明は英語のみです。43ロケールの展開は引き続きMVP後のバックログ項目
であり、空のロケールドキュメントや自動一括翻訳を追加しないでください。
