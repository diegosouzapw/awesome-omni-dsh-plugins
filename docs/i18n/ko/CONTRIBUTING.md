# Contributing

> 🌐 [English](../../CONTRIBUTING.md) · **한국어**

> **비공식 커뮤니티 프로젝트입니다. DeepSeek와 제휴, 승인, 후원 관계가 없습니다.**
> DeepSeek의 이름과 상표는 각 소유자에게 귀속됩니다.

카탈로그를 개선해 주셔서 감사합니다. 기여는 크리에이터를 최우선으로 합니다: 원 저장소의 증거를 사용하고,
저작자 표시를 보존하며, 각 플러그인을 독립적으로 검토 가능한 상태로 유지하세요. 카탈로그는 설계상
빈 상태에서 시작합니다; 어떤 항목도 그 자체의 검토된 풀 리퀘스트 없이는 받아들여지지 않습니다.

## 크리에이터부터 시작하기

플러그인 크리에이터나 소유 조직이 직접 연 풀 리퀘스트가 항상 우선입니다. 크리에이터가 기여할
준비가 되어 있다면, 큐레이터나 자동화 브랜치에서 그들의 작업을 재구성하는 대신 그들의 브랜치와
풀 리퀘스트를 사용하세요.

커뮤니티 큐레이션은 아직 풀 리퀘스트를 열지 않은 크리에이터를 돕는 경우 환영받습니다. 다만
이후 크리에이터가 직접 하는 기여에 대해 소유권이나 우선권을 확립하지는 않습니다.

## 브랜치 및 풀 리퀘스트당 하나의 플러그인

하나의 플러그인을 위한 전용 브랜치를 만들고, 그 브랜치로부터 하나의 풀 리퀘스트를 여세요.
브랜치와 풀 리퀘스트는 `catalog/plugins/` 아래의 정확히 하나의 YAML 파일만 생성하거나 변경해야
합니다. 그 브랜치나 풀 리퀘스트에 여러 플러그인, 문서 정리, 생성된 인덱스 또는 관련 없는 유지보수
작업을 섞지 마세요.

항목 ID와 파일명은 동일한 소문자 kebab-case 값이어야 합니다. 메인테이너는 각 플러그인 풀 리퀘스트를
개별적으로 검토하고 병합합니다; 여러 플러그인을 포함하는 배치는 분할되거나 부분적으로 병합되지
않습니다.

## 원본 소스 확인하기

모든 공개 필드는 고정된 커밋 시점의 원 크리에이터 저장소, 패키지, 매니페스트, README, 라이선스
또는 릴리스로부터 재구성되어야 합니다. 다른 카탈로그나 애그리게이터의 텍스트, 카테고리 지정,
스크린샷, 순위, 배지 또는 생성된 메타데이터를 복사하지 마세요. 엄브렐라 프로젝트, 마켓플레이스,
목록 또는 애그리게이터에서 발견된 링크는 단지 단서일 뿐이며, 증거도 아니고 플러그인 소스도
아닙니다.

엄브렐라, 애그리게이터, 마켓플레이스, 인스톨러 카탈로그 또는 목록을 카탈로그 항목으로 제출하지
마세요. 독립적으로 설치 가능하더라도 마찬가지입니다. 이를 단서로만 사용하고, 독립적으로 설치
가능한 각 자식 플러그인을 실제 크리에이터와 원본 저장소로 해결하세요. 플러그인이 크리에이터의
실제 모노레포 안에 있다면 정확한 서브패스로부터 제출할 수 있지만, 아래의 모노레포 스타 정책을
따라야 합니다.

## 필수 증거

풀 리퀘스트에 다음 모든 것을 제공하세요:

- 원본 저장소의 정규 공개 URL과 그 불변의 저장소 노드 ID. 메인테이너는 별도의 프로버넌스 게이트에서
  노드 ID를 확인하고 URL 불일치를 거부합니다.
- 크리에이터의 공개 GitHub 핸들과 이에 대응하는 공개 프로필 URL. YAML은 핸들을 한 번만 저장합니다;
  프로필 URL은 `https://github.com/<handle>`로 도출됩니다.
- 40자리 전체 소스 커밋 OID와 정확한 플러그인 서브패스, 또는 저장소 루트 플러그인의 경우 `null`.
- 제한된 영어 설명과 그 고정된 커밋 시점의 증거 경로.
- [docs/CATEGORIES.md](../../docs/CATEGORIES.md)에서 선택된 아티팩트 `kind`, 주요 카테고리, 태그.
- 고정된 커밋 시점에 증거로 확인된 완전한 업스트림 SPDX 라이선스 표현식.
- npm의 정확한 버전에 고정된, 또는 소스 저장소, 전체 커밋 및 서브패스에 고정된 정규 설치
  디스크립터. 디스크립터는 데이터이며, 결코 셸 명령어가 아닙니다.
- 네이티브 DSH 통합 증거와 고정된 커밋 시점의 그 경로.
- 그 정확한 아티팩트 pin에 대해 존재하는, 민감하지 않은 스모크 테스트 증거, 또는 명시적인 값
  `not run`. 카탈로그 기여를 준비하기 위한 목적만으로 플러그인을 설치하거나 `preinstall`,
  `install`, `postinstall`, `prepare` 또는 그 밖의 패키지/플러그인 라이프사이클 코드를 실행하지
  마세요.
- 전용 저장소의 경우, 그 정확한 저장소에 대해 확인 가능한 스타 수와 함께 공개 소스 및 확인 시각.
  모노레포 플러그인의 경우, 아래의 필수 null 정책을 사용하세요.
- 존재하는 경우 공개 Discussion 또는 댓글 프로버넌스; 존재하지 않으면 `null`을 사용하세요.
- 기계 판독 가능한 값 `unofficial: true`.

자격을 갖춘 스모크 테스트가 아직 존재하지 않는 경우, `verification.status: eligible`과
`verification.smokeTest: null`을 사용하세요. `verified`는 정확한 pin에 대한 검토 가능한 스모크
테스트 증거가 존재할 때만 사용하세요. 두 상태 모두 보증이나 보안 인증이 아닙니다.

절대 자격 증명, 쿠키, 개인 이메일 주소, 미공개 소스 또는 그 밖의 비밀 정보를 제출하지 마세요.

## YAML과 스키마 규칙

`catalog/plugins/<plugin-id>.yaml`을 생성하고 [`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml)에
대해 검증하세요. 스키마는 필드명과 허용되는 값에 대한 신뢰할 수 있는 원천 데이터입니다;
[docs/CATEGORIES.md](../../docs/CATEGORIES.md)는 단일 아티팩트 kind, 주요 카테고리, 태그, 저장소
범위를 선택하는 방법을 정의합니다.

npm 디스크립터는 유효한 패키지 이름과 정확한 버전을 포함해야 합니다. 공개 스키마는 옵션처럼
보이거나 제한되지 않은 값을 거부하지만 SemVer나 SRI를 재구현하지는 않습니다: 카탈로그 검증은
버전을 파싱하고, 정확한 SemVer를 요구하며, 어떤 무결성 값이든 유효한 SHA-512 SRI로 파싱해야
합니다. 소스 디스크립터는 가변적인 소스 값을 중복하지 않고 `source.repository`,
`source.commit`, `source.subpath`에 바인딩됩니다.

인스톨러는 인수 배열을 사용해야 하고, 셸 실행을 비활성화해야 하며, 호출된 명령어가 지원하는 경우
카탈로그가 제공하는 위치 인자 값 앞에 옵션 종결자를 배치해야 합니다. 제출 검증은 인스톨러나
플러그인 라이프사이클을 호출해서는 안 됩니다.

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate`는 로컬의, 읽기 전용인, 구조적 및 시맨틱 검사입니다. 안전한 YAML을 파싱하고,
공개 스키마를 검증하고, SPDX 표현식을 파싱하고, 정확한 SemVer와 유효한 SHA-512 SRI를 요구하며,
중복된 ID와 저장소-노드-플러스-서브패스 정규 키를 거부합니다. GitHub에 연결하거나, 저장소 신원을
확인하거나, 고정된 커밋 시점의 증거 경로를 검사하지 않습니다.

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

항목이 `eligible`에 도달하기 전에, 메인테이너는 정규 저장소와 노드 ID를 별도로 확인하고,
크리에이터를 원본 소스에 연결하며, `source.commit` 시점의 선언된 설명, 라이선스, DSH 통합,
스모크 테스트 증거를 검사합니다. 초록불의 로컬 검증 결과는 프로버넌스나 출처의 증명이 아닙니다.

## 저장소 스타

플러그인의 정확한 전용 저장소에 검증 가능하게 속한 스타만 기록될 수 있습니다. 부모 프로젝트의
스타가 더 넓은 모노레포 안에 저장된 플러그인에 귀속되어서는 절대 안 됩니다. 모노레포 항목은
카탈로그의 기능적 섹션에 계속 적격하지만 다음을 선언해야 합니다:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

전용 항목은 `repositoryScope: dedicated`, `starsPolicy: exact-repository`, 그리고 동일한
저장소에서 관측된 음수가 아닌 스타 수를 사용합니다. 인기도 데이터를 제출하기 전에
[docs/RANKING.md](../../docs/RANKING.md)를 읽으세요.

## 크리에이터 우선순위와 정중한 연락

동일한 정규 플러그인에 대해, 우선순위는 다음과 같습니다:

1. 크리에이터 또는 소유 조직이 연 풀 리퀘스트.
2. 크리에이터가 명시적으로 승인한 커뮤니티 풀 리퀘스트.
3. 이미 존재하는 유효한 커뮤니티 큐레이션 풀 리퀘스트.
4. 카탈로그 자동화 풀 리퀘스트.

크리에이터의 직접적인 풀 리퀘스트는, 어느 것이 먼저 열렸거나 더 진행되었는지와 무관하게, 열려
있는 어떤 큐레이션이나 자동화 풀 리퀘스트보다 우선합니다. 크리에이터의 풀 리퀘스트가 검토
수단이 되며; 메인테이너는 크리에이터의 브랜치에 force-push하거나 그들의 작업을 큐레이션된
풀 리퀘스트로 이식하지 않습니다. 큐레이션된 항목이 이미 병합된 경우, 공개 히스토리는 다시
쓰이지 않습니다. 크리에이터는 클레임이나 정정 요청을 사용한 다음 직접 후속 풀 리퀘스트로
기여할 수 있습니다.

큐레이션된 풀 리퀘스트는 원본 저장소 링크 옆에 설명란에서 정중한 공개 `@creator` 멘션을
한 번 사용하여, 크리에이터가 직접 풀 리퀘스트로 검토하거나 대체하도록 초대해야 합니다. 멘션을
반복하거나, 홍보성 이슈를 열거나, 크로스 포스팅하거나, 원치 않는 다이렉트 메시지를 보내거나,
그 밖의 방식으로 크리에이터에게 스팸을 보내지 마세요.

<!-- creator-first:source-bound-git-identity -->

크리에이터가 작성한 풀 리퀘스트와 커밋은 자연스럽게 크리에이터의 크레딧을 보존합니다. 큐레이션된
커밋은 소스에 결속되어 공개적으로 검증 가능한 신원이 있을 때만 크리에이터의 Git 저작자 정보나
`Co-authored-by` 트레일러를 사용할 수 있습니다. 절대 이메일을 지어내거나 추측하지 마세요.
검증된 Git 신원을 사용할 수 없을 때, 큐레이터가 커밋을 저작하고 YAML과 풀 리퀘스트에 원본
저장소 링크와 함께 명시적인 "Created by @handle" 크레딧을 부여합니다. 메인테이너나 자동화
계정은 커미터이거나 검증된 공동 저자일 수 있지만, 크리에이터의 저작권을 대체해서는 안 됩니다.
전체 정책은 [docs/CREDIT.md](../../docs/CREDIT.md)를 참고하세요.

## 검증 명령어와 가용성

npm CLI는 `@diegosouza.pw/dsh-plugins@0.1.0`으로 배포되어 있으므로, 아래 명령어는 오늘
`npx`를 통해 사용할 수 있습니다. 정확히 작성된 대로 사용하세요; 기여자는 대체 명령어를 지어내지
말아야 합니다.

이 명령어들을 저장소 루트에서 실행하세요:

```bash
npx @diegosouza.pw/dsh-plugins catalog validate --catalog .
npx @diegosouza.pw/dsh-plugins catalog docs-check .
npx @diegosouza.pw/dsh-plugins catalog github-forms-check .
```

`catalog validate`는 위에서 설명한 로컬 YAML, 스키마, SPDX, 정확한 SemVer, SHA-512 SRI 및
중복 검사만 수행하며, 의도적으로 비어 있는 카탈로그를 허용합니다. 원격 저장소 신원이나 고정된
소스 증거를 증명하지는 않습니다. 다른 명령어들은 필수 공개 문서와 구조화된 GitHub 이슈 양식을
검사합니다. 이 명령어들을 로컬에서 통과하더라도 증거 요구사항이 완화되지는 않습니다; 메인테이너는
병합 전에 여전히 해당하는 모든 릴리스 게이트를 적용합니다.

## 검토 게이트, 충돌 및 병합

메인테이너는 병합 전에 현재 풀 리퀘스트 커밋에 모든 게이트를 적용합니다:

1. **범위:** 하나의 전용 브랜치, 하나의 플러그인 YAML 파일, 관련 없는 변경 없음.
2. **원본 신원:** 크리에이터, 정규 저장소, 노드 ID, 전체 커밋, 서브패스가 일치함.
3. **스키마와 증거:** YAML, 카테고리, SPDX, 설치 pin, DSH 증거, 스모크 상태가 플러그인 라이프사이클
   코드를 실행하지 않고도 내부적으로 일관됨.
4. **인기도:** 전용 스타가 정확한 저장소에서 검증 가능하거나, 모노레포 스타가
   `undefined-parent-repository`와 함께 `null`임.
5. **문서와 양식:** 공개 문서, Markdown 펜스, 구조화된 양식이 계속 유효함.
6. **충돌과 중복 제거:** 병합된 항목이나 열려 있는 풀 리퀘스트 중 어느 것도 동일한 정규 플러그인을
   나타내지 않음.

다른 이름이나 ID가 중복된 플러그인을 구별되게 만들지는 않습니다. 동일한 저장소 노드 ID와 서브패스,
동일한 정규 패키지, 또는 그 밖의 입증 가능하게 동일한 설치 대상을 충돌로 취급하세요. 병합 전에
별칭과 경쟁하는 풀 리퀘스트를 해결하세요. 크리에이터의 직접적인 풀 리퀘스트는 큐레이션이나
자동화와의 충돌에서 승리합니다; 그렇지 않으면 메인테이너는 하나의 검토 수단을 선택하고 둘 다
병합하는 대신 중복을 닫거나 리디렉션합니다.

메인테이너만이 모든 게이트를 통과한 후 플러그인을 병합합니다. 각 수락된 플러그인은 개별적으로
병합됩니다; 검증, 큐레이션 또는 자동화가 자동 또는 일괄 병합을 의미하지는 않습니다.
