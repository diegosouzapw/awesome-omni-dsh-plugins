# حاکمیت کاتالوگ

> 🌐 [English](../../GOVERNANCE.md) · [Português (Brasil)](../pt-BR/GOVERNANCE.md) · [中文（简体）](../zh-CN/GOVERNANCE.md) · **فارسی**

> **پروژه غیررسمی جامعه. وابسته به، تأییدشده توسط یا اسپانسرشده توسط DeepSeek نیست.**
> نام‌ها و علائم DeepSeek متعلق به مالک مربوطه‌شان است.

کاتالوگ عمومی چگونه اداره می‌شود: چه کسی تصمیم می‌گیرد چه چیزی وارد شود، مشارکت‌های رقیب به چه
ترتیبی محترم شمرده می‌شوند، چه بررسی‌هایی به‌صورت خودکار اجرا می‌شوند و چه قضاوت‌هایی انسانی
باقی می‌مانند. سیاست‌هایی که در اینجا به آن‌ها ارجاع داده شده در
[CONTRIBUTING.md](../../CONTRIBUTING.md)، [docs/CREDIT.md](../../docs/CREDIT.md) و
[docs/RANKING.md](../../docs/RANKING.md) زندگی می‌کنند؛ این صفحه چگونگی هم‌راستایی آن‌ها را
توصیف می‌کند.

## اصول

1. **اولویت با سازنده.** کاتالوگ برای قابل‌کشف کردن کار سازندگان وجود دارد، هرگز برای گرفتن
   مالکیت از آن‌ها. برای یک افزونهٔ قانونیِ یکسان، یک pull request مستقیم از سازنده جایگزین هر
   pull request باز ویرایش جامعه یا خودکارسازی می‌شود — ترتیب کامل اولویت و قواعد هویت Git در
   [docs/CREDIT.md](../../docs/CREDIT.md) است.
2. **یک افزونه، یک pull request بازبینی‌شده.** بدون ادغام‌های دسته‌ای، بدون وارد کردن انبوهِ
   تولیدشده به کاتالوگ عمومی. هر ورودی بازبینی خودش را کسب می‌کند.
3. **شاهد بر اعتماد.** هر فیلد عمومی به ریپازیتوری سازندهٔ اصلی در یک کامیت پین‌شده رد می‌شود.
   یک بررسی خودکار سبز هرگز به‌عنوان اثبات منشأ پذیرفته نمی‌شود.
4. **همیشه غیررسمی.** هیچ وضعیتی از کاتالوگ به‌عنوان بازبینی، گواهی یا تأیید DeepSeek ارائه
   نمی‌شود.

## چگونه تغییرات روی `main` می‌نشینند

همهٔ تغییرات از طریق pull requestهای بازبینی‌شده به `main` می‌رسند — هیچ pushی مستقیم وجود ندارد.
سیاست کاری برای شاخهٔ پیش‌فرض:

- **فقط pull request.** ورودی‌های کاتالوگ، مستندات و تغییرات اسکیما همه از طریق یک PR وارد
  می‌شوند؛ PRهای کاتالوگ باید از قاعدهٔ یک‌افزونه‌برای‌هر‌شاخه در
  [CONTRIBUTING.md](../../CONTRIBUTING.md) پیروی کنند.
- **تاریخچهٔ خطی.** PRها به شکلی ادغام می‌شوند که `main` تاریخچه‌ای خطی و قابل‌ممیزی حفظ کند؛
  تاریخچهٔ عمومیِ ادغام‌شده بازنویسی نمی‌شود. اگر یک ورودی ویرایش‌شده پیش از آنکه سازنده جلو
  بیاید ادغام شده باشد، سازنده به‌جای بازنویسی تاریخچه، در یک مشارکت پیگیری آن را ادعا یا اصلاح
  می‌کند.
- **حل رشتهٔ بازبینی.** مکالمات بازبینی پیش از ادغام حل می‌شوند؛ بازخورد حل‌نشده مانع ادغام
  می‌شود.
- **ادغام توسط نگهدارنده.** فقط یک نگهدارنده یک ورودی افزونه را ادغام می‌کند، و فقط پس از آنکه
  هر دروازه در [CONTRIBUTING.md](../../CONTRIBUTING.md) ← «دروازه‌های بازبینی، تصادم‌ها و
  ادغام» روی کامیت فعلیِ PR عبور کند.

## بررسی `catalog-validation`

هر pull requestی که `catalog/plugins/`، `schemas/` یا خودِ workflow را لمس کند job
`catalog-validation` (`.github/workflows/validate-catalog.yml`) را اجرا می‌کند، پین‌شده به
CLI منتشرشده:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**آنچه اعتبارسنجی می‌کند** — فقط ساختار و معناشناسی محلی:

- تجزیهٔ YAML امن برای هر ورودی زیر `catalog/plugins/`.
- انطباق با اسکیمای عمومی (ببینید [docs/SCHEMA.md](../../docs/SCHEMA.md)).
- تجزیهٔ عبارت SPDX، نسخه‌های SemVer دقیق، مقادیر integrity معتبرِ SRI از نوع SHA-512.
- رد تکراری‌ها: بدون شناسهٔ ورودی تکراری و بدون کلیدهای ترکیبیِ گرهٔ ریپازیتوری‌به‌علاوهٔ
  زیرمسیرِ تکراری.
- کاتالوگ عمداً بدون ورودی عبور می‌کند (`0 entries valid; catalog is empty`).

**آنچه اعتبارسنجی نمی‌کند** — و بنابراین آنچه یک بررسی سبز هرگز اثبات نمی‌کند:

- هویت ریپازیتوری از راه دور: با GitHub تماس نمی‌گیرد یا شناسهٔ گرهٔ ریپازیتوری را در برابر URL
  حل نمی‌کند.
- شاهد در کامیت پین‌شده: توضیحات، مجوزها، یکپارچگی DSH و شاهد smoke test واکشی یا بازرسی
  نمی‌شوند.
- مالکیت سازنده، تعداد ستاره یا تصادم با pull requestهای باز.

آن قضاوت‌ها به دروازه‌های منشأ جداگانهٔ نگهدارندگان تعلق دارند که پیش از ادغام اعمال می‌شوند و در
[CONTRIBUTING.md](../../CONTRIBUTING.md) توصیف شده‌اند. بررسی محلی کف است، نه سقف.

## وضعیت‌های اعتبارسنجی

اعتبارسنجی برای هر ورودی در برابر کامیت پین‌شدهٔ دقیقش، با استفاده از وضعیت‌های تعریف‌شده در
اسکیمای عمومی (`eligible`، `verified`، `stale`، `unavailable`، `archived`، `quarantined`)
ثبت می‌شود. دو وضعیت مثبت عمداً محدود هستند:

- `eligible` — ساختار عمومی و یکپارچگی بومی DSH اعتبارسنجی شده‌اند.
- `verified` — به‌علاوه، یک smoke test نصب برای منبع یا بستهٔ پین‌شده موفق شده؛ اسکیما نیاز به
  حضور رکورد smoke test را الزامی می‌کند.

هیچ‌کدام از این وضعیت‌ها — و هیچ وضعیت دیگری — تأیید، تضمین یا گواهی امنیتی نیست. معناشناسی
کامل، شامل اینکه وضعیت‌ها چگونه با رتبه‌بندی تعامل دارند، در
[docs/RANKING.md](../../docs/RANKING.md) است؛ شکل رکورد در
[docs/SCHEMA.md](../../docs/SCHEMA.md) است.

## ادعاها، اصلاحات و حذف‌ها

فرم‌های ساختاریافتهٔ issue گیت‌هاب (`.github/ISSUE_TEMPLATE/`) مسیر اداره‌شده برای تغییر ورودی‌ای
هستند که شما ارسال نکرده‌اید:

| فرم           | چه کسی از آن استفاده می‌کند                              | نتیجه                                             |
| -------------- | ---------------------------------------- | --------------------------------------------------- |
| **ادعا**      | سازنده‌ای که افزونه‌اش توسط شخص دیگری ویرایش شده | مالکیت به منبع اصلی مقید می‌شود؛ سپس سازنده می‌تواند مستقیماً مشارکت کند |
| **اصلاح** | هرکسی که ابردادهٔ عمومیِ نادرست را می‌بیند | یک اصلاح بازبینی‌شده روی ورودی متأثر             |
| **حذف**    | سازنده‌ای که می‌خواهد فهرست خود را حذف‌شده ببیند، یا گزارش‌دهندهٔ یک تخلف از سیاست | حذف یا قرنطینهٔ بازبینی‌شدهٔ ورودی |

قواعدی که روی هر سه جریان اعمال می‌شود:

- ادعاهای مالکیت باید با شاهد عمومیِ قابل‌تأیید پشتیبانی شوند (مالکیت ریپازیتوری، تألیف بسته،
  ابردادهٔ مانیفست یا تاریخچهٔ منبع پین‌شده) — کامنت‌گذاری روی یک Discussion سازندگی را ایجاد
  نمی‌کند ([docs/CREDIT.md](../../docs/CREDIT.md)).
- مشکلات امنیتی در یک افزونهٔ فهرست‌شده ابتدا به نگهدارندهٔ خود آن افزونه می‌رود؛ سمت کاتالوگ
  سپس اصلاح یا قرنطینه را بدون انتشار جزئیات بهره‌برداری مدیریت می‌کند
  ([SECURITY.md](../../SECURITY.md)).
- هرگز اعتبارنامه، اطلاعات تماس خصوصی یا سایر اطلاعات محرمانه را در یک فرم قرار ندهید.

## نقش‌ها

- **سازندگان** مالک افزونه‌های خود و اولویت فهرست‌های خود هستند. آن‌ها می‌توانند مستقیماً
  مشارکت کنند، ویرایش جامعه را تأیید کنند، یا یک ورودی موجود را ادعا/اصلاح/حذف کنند.
- **مشارکت‌کنندگان جامعه** می‌توانند برای سازندگانی که هنوز مشارکت نکرده‌اند، تحت قواعد تماس
  محترمانه و اعتباردهیِ [docs/CREDIT.md](../../docs/CREDIT.md)، ورودی‌ها را ویرایش کنند. ویرایش
  هرگز بر یک مشارکت مستقیم بعدیِ سازنده اولویت پیدا نمی‌کند.
- **نگهدارندگان** بازبینی می‌کنند، دروازه‌های منشأ را اعمال می‌کنند، تصادم‌ها را حل می‌کنند و
  ادغام می‌کنند. آن‌ها همچنین وب‌سایت
  ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online)) و CLI منتشرشده را از
  منبع خصوصی نگهداری می‌کنند؛ دادهٔ عمومی، اسکیما و سیاست‌های این ریپازیتوری همان چیزی هستند که
  آن سطوح مصرف می‌کنند.
