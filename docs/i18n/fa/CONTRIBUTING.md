# مشارکت

> 🌐 [English](../../../CONTRIBUTING.md) · [Português (Brasil)](../pt-BR/CONTRIBUTING.md) · [中文（简体）](../zh-CN/CONTRIBUTING.md) · **فارسی**

> **پروژه غیررسمی جامعه. وابسته به، تأییدشده توسط یا اسپانسرشده توسط DeepSeek نیست.**
> نام‌ها و علائم DeepSeek متعلق به مالک مربوطه‌شان است.

از اینکه در بهبود کاتالوگ مشارکت می‌کنید سپاسگزاریم. مشارکت‌ها اولویت‌شان با سازنده است: از شواهد
ریپازیتوری اصلی استفاده کنید، اعتباردهی را حفظ کنید و هر افزونه را مستقلاً قابل‌بازبینی نگه دارید.
کاتالوگ عمداً خالی شروع می‌شود؛ هیچ ورودی بدون pull request بازبینی‌شدهٔ خودش پذیرفته نمی‌شود.

## با سازنده شروع کنید

یک pull request که مستقیماً توسط سازندهٔ افزونه یا سازمان مالک آن باز شده باشد همیشه ترجیح داده
می‌شود. اگر سازنده آمادهٔ مشارکت است، از شاخه و pull request خودش استفاده کنید به‌جای بازآفرینی کار
او در یک شاخهٔ ویرایش جامعه (curator) یا خودکارسازی.

ویرایش جامعه زمانی خوش‌آمد است که به سازنده‌ای کمک کند که هنوز pull request باز نکرده. این کار
مالکیت یا اولویتی بر یک مشارکت مستقیم بعدی از سوی سازنده ایجاد نمی‌کند.

## یک افزونه برای هر شاخه و pull request

یک شاخهٔ اختصاصی برای یک افزونه ایجاد کنید و از آن شاخه یک pull request باز کنید. شاخه و pull
request باید دقیقاً یک فایل YAML زیر `catalog/plugins/` را ایجاد یا تغییر دهند. افزونه‌ها، نظافت
مستندات، ایندکس‌های تولیدشده یا نگهداری نامرتبط را در آن شاخه یا pull request مخلوط نکنید.

شناسهٔ ورودی (ID) و نام فایل باید همان مقدار kebab-case با حروف کوچک باشند. نگهدارندگان هر
pull request افزونه را جداگانه بازبینی و ادغام می‌کنند؛ یک دسته که چند افزونه دارد تقسیم یا
به‌صورت جزئی ادغام نمی‌شود.

## منبع اصلی را مشخص کنید

هر فیلد عمومی باید از ریپازیتوری سازندهٔ اصلی، بسته، مانیفست، README، مجوز یا انتشار در کامیت
پین‌شده بازسازی شود. متن، تخصیص دسته، اسکرین‌شات‌ها، رتبه‌بندی، نشان‌ها یا ابرداده‌های تولیدشدهٔ
یک کاتالوگ یا جمع‌کنندهٔ دیگر را کپی نکنید. لینکی که در یک پروژهٔ چتری، بازار، فهرست یا
جمع‌کننده پیدا شود فقط یک سرنخ است، نه شاهد و نه منبع افزونه.

هرگز یک پروژهٔ چتری، جمع‌کننده، بازار، کاتالوگ نصب‌کننده یا فهرست را به‌عنوان ورودی کاتالوگ ارسال
نکنید، حتی وقتی به‌طور مستقل قابل‌نصب باشد. از آن فقط به‌عنوان سرنخ استفاده کنید و هر افزونهٔ
فرزندِ به‌طور مستقل قابل‌نصب را به سازنده و ریپازیتوری اصلی واقعی‌اش برگردانید. یک افزونه در
مونوریپوی واقعی سازنده‌اش می‌تواند از زیرمسیر دقیقش ارسال شود، اما باید سیاست ستاره‌های مونوریپو
در زیر را رعایت کند.

## شواهد لازم

همهٔ موارد زیر را در pull request ارائه دهید:

- URL عمومی قانونیِ ریپازیتوری اصلی و شناسهٔ گرهٔ (node ID) ثابت آن. نگهدارندگان شناسهٔ گره را در
  دروازهٔ منشأ (provenance) جداگانه حل می‌کنند و ناهماهنگی URL را رد می‌کنند.
- هندل عمومی GitHub سازنده و URL پروفایل عمومی متناظر. YAML هندل را یک‌بار ذخیره می‌کند؛ URL
  پروفایل به‌صورت `https://github.com/<handle>` استخراج می‌شود.
- یک OID کامیت منبع کامل و ۴۰ کاراکتری و زیرمسیر دقیق افزونه، یا `null` برای افزونه‌ای در ریشهٔ
  ریپازیتوری.
- توضیحی انگلیسی و محدود به‌همراه مسیر شاهدش در همان کامیت پین‌شده.
- `kind` مصنوع، دستهٔ اصلی و برچسب‌های انتخاب‌شده از
  [docs/CATEGORIES.md](../../docs/CATEGORIES.md).
- عبارت کامل مجوز SPDX بالادستی که در کامیت پین‌شده شاهدش موجود است.
- یک توصیف‌گر نصبِ قانونی که به یک نسخهٔ دقیق npm، یا به ریپازیتوری منبع، کامیت کامل و زیرمسیر
  پین شده است. توصیف‌گر داده است، هرگز دستور شل نیست.
- شاهد یکپارچگی بومی DSH و مسیر آن در کامیت پین‌شده.
- شاهد smoke test موجود و غیرحساس برای همان پین دقیق مصنوع، یا مقدار صریح `not run`. برای
  آماده‌سازی یک مشارکت کاتالوگ، افزونه را نصب نکنید و `preinstall`، `install`، `postinstall`،
  `prepare` یا سایر کدهای چرخهٔ حیات بسته/افزونه را اجرا نکنید.
- برای یک ریپازیتوری اختصاصی، تعداد ستارهٔ قابل‌تأیید برای همان ریپازیتوری دقیق، به‌همراه منبع
  عمومی و زمان بررسی. برای افزونهٔ مونوریپو، از سیاست null الزامی در زیر استفاده کنید.
- منشأ عمومی Discussion یا کامنت در صورت وجود؛ در غیر این صورت از `null` استفاده کنید.
- مقدار قابل‌خواندن توسط ماشین `unofficial: true`.

اگر هیچ smoke test واجدشرایطی از قبل وجود ندارد، از `verification.status: eligible` و
`verification.smokeTest: null` استفاده کنید. `verified` را فقط زمانی استفاده کنید که شاهد
smoke test قابل‌بازبینی برای همان پین دقیق موجود باشد. هیچ‌کدام از این وضعیت‌ها تأیید یا گواهی
امنیتی نیستند.

هرگز اعتبارنامه، کوکی، آدرس ایمیل خصوصی، سورس‌کد منتشرنشده یا سایر اطلاعات محرمانه ارسال نکنید.

## قواعد YAML و اسکیما

`catalog/plugins/<plugin-id>.yaml` را ایجاد کنید و آن را در برابر
[`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml) اعتبارسنجی کنید. `id` باید برابر
با نام پایهٔ فایل باشد و باید با فضای نام شما شروع شود: هندل `creator.github` شما با حروف کوچک
(هر دنبالهٔ کاراکتری خارج از `[a-z0-9]` به یک `-` تبدیل می‌شود) به‌همراه `-`، برای مثال
`some-creator-my-plugin` برای هندل `Some-Creator`. اعتبارسنجی کاتالوگ هر دو را اعمال می‌کند.
اسکیما منبع حقیقت برای نام فیلدها و مقادیر مجاز است؛
[docs/CATEGORIES.md](../../docs/CATEGORIES.md) نحوهٔ انتخاب تک `kind` مصنوع، دستهٔ اصلی، برچسب‌ها
و دامنهٔ ریپازیتوری را تعریف می‌کند.

یک توصیف‌گر npm باید شامل یک نام بستهٔ معتبر و نسخهٔ دقیق باشد. اسکیمای عمومی مقادیر شبیه‌گزینه و
نامحدود را رد می‌کند اما SemVer یا SRI را دوباره پیاده‌سازی نمی‌کند: اعتبارسنجی کاتالوگ باید نسخه
را تجزیه کند، SemVer دقیق را الزامی کند و هر مقدار integrity را به‌عنوان SRI معتبرِ SHA-512 تجزیه
کند. یک توصیف‌گر منبع بدون تکرار مقادیر منبع متغیر به `source.repository`، `source.commit` و
`source.subpath` مقید است.

نصب‌کننده‌ها باید از آرایه‌های آرگومان استفاده کنند، اجرای شل را غیرفعال کنند و هرجا دستور
فراخوانی‌شده پشتیبانی می‌کند، پیش از مقادیر موضعیِ ارائه‌شده توسط کاتالوگ یک ترمینیتور گزینه قرار
دهند. اعتبارسنجی ارسال نباید یک نصب‌کننده یا چرخهٔ حیات افزونه را فراخوانی کند.

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` یک بررسی محلی، فقط‌خواندنی، ساختاری و معنایی است. YAML امن را تجزیه می‌کند،
اسکیمای عمومی را اعتبارسنجی می‌کند، عبارات SPDX را تجزیه می‌کند، SemVer دقیق و SRI معتبرِ
SHA-512 را الزامی می‌کند و شناسه‌های تکراری و کلیدهای ترکیبیِ گرهٔ ریپازیتوری‌به‌علاوهٔ زیرمسیر را
رد می‌کند. با GitHub تماس نمی‌گیرد، هویت ریپازیتوری را حل نمی‌کند و مسیرهای شاهد را در کامیت
پین‌شده بازرسی نمی‌کند.

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

پیش از آنکه یک ورودی به `eligible` برسد، نگهدارندگان جداگانه ریپازیتوری قانونی و شناسهٔ گره را
حل می‌کنند، سازنده را به منبع اصلی پیوند می‌دهند و توضیحات، مجوز، یکپارچگی DSH و شاهد smoke test
اعلام‌شده را در `source.commit` بازرسی می‌کنند. یک نتیجهٔ اعتبارسنجی محلیِ سبز شاهد منشأ یا
اصالت نیست.

## ستاره‌های ریپازیتوری

فقط ستاره‌هایی که به‌صورت قابل‌تأیید متعلق به ریپازیتوری اختصاصی دقیق افزونه هستند می‌توانند ثبت
شوند. ستاره‌های یک پروژهٔ والد هرگز نباید به افزونه‌ای که درون یک مونوریپوی گسترده‌تر ذخیره شده
نسبت داده شوند. یک ورودی مونوریپو برای بخش‌های عملکردی کاتالوگ واجدشرایط باقی می‌ماند اما باید
اعلام کند:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

یک ورودی اختصاصی از `repositoryScope: dedicated`، `starsPolicy: exact-repository` و تعداد
ستارهٔ غیرمنفیِ مشاهده‌شده در همان ریپازیتوری استفاده می‌کند. پیش از ارسال داده‌های محبوبیت
[docs/RANKING.md](../../docs/RANKING.md) را بخوانید.

## اولویت سازنده و تماس محترمانه

برای یک افزونهٔ قانونیِ یکسان، اولویت به این ترتیب است:

1. یک pull request باز‌شده توسط سازنده یا سازمان مالک.
2. یک pull request جامعه که صراحتاً توسط سازنده تأیید شده.
3. یک pull request ویرایش جامعهٔ معتبر و موجود.
4. یک pull request خودکارسازی کاتالوگ.

یک pull request مستقیم از سازنده جایگزین هر pull request باز ویرایش یا خودکارسازی می‌شود، صرف
نظر از اینکه کدام‌یک اول باز شده یا پیشرفته‌تر است. pull request سازنده به وسیلهٔ بازبینی تبدیل
می‌شود؛ نگهدارندگان force-push روی شاخهٔ سازنده انجام نمی‌دهند و کار او را به pull request
ویرایش‌شده منتقل نمی‌کنند. اگر یک ورودی ویرایش‌شده از قبل ادغام شده، تاریخچهٔ عمومی بازنویسی
نمی‌شود. سازنده می‌تواند از یک درخواست ادعا (claim) یا اصلاح استفاده کند و سپس مستقیماً با یک
pull request پیگیری مشارکت کند.

یک pull request ویرایش‌شده باید یک اشارهٔ عمومی محترمانهٔ `@creator` در توضیحاتش، کنار لینکی به
ریپازیتوری اصلی، استفاده کند که سازنده را به بازبینی یا جایگزینی آن با یک pull request مستقیم
دعوت می‌کند. اشاره را تکرار نکنید، issue تبلیغاتی باز نکنید، cross-post نکنید، پیام مستقیم
ناخواسته نفرستید یا به‌شکل دیگری سازنده را اسپم نکنید.

<!-- creator-first:source-bound-git-identity -->

pull requestها و کامیت‌هایی که سازنده نوشته اعتبار سازنده را به‌طور طبیعی حفظ می‌کنند. کامیت‌های
ویرایش‌شده فقط با یک هویت مقیدشده به منبع و به‌صورت عمومی قابل‌تأیید می‌توانند از تألیف Git
سازنده یا تریلر `Co-authored-by` استفاده کنند. هرگز ایمیلی را اختراع یا حدس نزنید. وقتی هیچ
هویت Git تأییدشده‌ای در دسترس نیست، ویرایشگر کامیت را تألیف می‌کند و اعتبار صریح
«Created by @handle» را به‌همراه لینک ریپازیتوری اصلی در YAML و pull request می‌دهد. یک
نگهدارنده یا حساب خودکارسازی می‌تواند committer یا هم‌مؤلف تأییدشده باشد، اما نباید جایگزین
تألیف سازنده شود. برای سیاست کامل [docs/CREDIT.md](../../docs/CREDIT.md) را ببینید.

## دستورات اعتبارسنجی و در دسترس بودن

CLI ای npm به‌صورت `omni-dsh-plugins@1.0.1` منتشر می‌شود، بنابراین دستورات زیر امروز از طریق
`npx` در دسترس‌اند. آن‌ها را دقیقاً همان‌طور که نوشته شده استفاده کنید؛ مشارکت‌کنندگان نباید
دستورات جایگزین اختراع کنند.

این دستورات را از ریشهٔ ریپازیتوری اجرا کنید:

```bash
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

`catalog validate` فقط بررسی‌های محلیِ YAML، اسکیما، SPDX، SemVer دقیق، SRI از نوع SHA-512 و
تکراری‌های توصیف‌شده در بالا را انجام می‌دهد و کاتالوگ عمداً بدون ورودی را می‌پذیرد. این دستور
هویت ریپازیتوری از راه دور یا شاهد منبع پین‌شده را اثبات نمی‌کند. دستورات دیگر مستندات عمومی
لازم و فرم‌های ساختاریافتهٔ issue گیت‌هاب را بررسی می‌کنند. عبور موفق این دستورات به‌صورت محلی
الزامات شواهد را کاهش نمی‌دهد؛ نگهدارندگان همچنان پیش از ادغام هر دروازهٔ انتشار متناظر را اعمال
می‌کنند.

## دروازه‌های بازبینی، تصادم‌ها و ادغام

نگهدارندگان پیش از ادغام هر دروازه را روی کامیت فعلیِ pull request اعمال می‌کنند:

1. **دامنه:** یک شاخهٔ اختصاصی، یک فایل YAML افزونه و بدون تغییرات نامرتبط.
2. **هویت اصلی:** سازنده، ریپازیتوری قانونی، شناسهٔ گره، کامیت کامل و زیرمسیر با هم مطابقت
   دارند.
3. **اسکیما و شواهد:** YAML، دسته‌ها، SPDX، پین نصب، شاهد DSH و وضعیت smoke test بدون اجرای
   کد چرخهٔ حیات افزونه به‌صورت درونی سازگارند.
4. **محبوبیت:** ستاره‌های اختصاصی روی ریپازیتوری دقیق قابل‌تأیید هستند، یا ستاره‌های مونوریپو
   `null` با `undefined-parent-repository` هستند.
5. **مستندات و فرم‌ها:** مستندات عمومی، fenceهای Markdown و فرم‌های ساختاریافته معتبر باقی
   می‌مانند.
6. **تصادم و حذف تکرار:** هیچ ورودی ادغام‌شده یا pull request بازی نمایندهٔ همان افزونهٔ
   قانونی نیست.

نام‌ها یا شناسه‌های متفاوت افزونه‌های تکراری را متمایز نمی‌کنند. همان شناسهٔ گرهٔ ریپازیتوری و
زیرمسیر، همان بستهٔ قانونی یا هدف نصب دیگری که به‌طور اثبات‌شده یکسان است را به‌عنوان تصادم در
نظر بگیرید. اسم‌های مستعار و pull requestهای رقیب را پیش از ادغام حل کنید. یک pull request
مستقیم از سازنده در تصادم با ویرایش یا خودکارسازی برنده می‌شود؛ در غیر این صورت نگهدارندگان یک
وسیلهٔ بازبینی را انتخاب می‌کنند و تکراری‌ها را می‌بندند یا هدایت مجدد می‌کنند به‌جای ادغام
هر دو.

فقط یک نگهدارنده پس از عبور همهٔ دروازه‌ها یک افزونه را ادغام می‌کند. هر افزونهٔ پذیرفته‌شده
جداگانه ادغام می‌شود؛ اعتبارسنجی، ویرایش یا خودکارسازی به معنای ادغام خودکار یا دسته‌ای نیست.

## چک‌لیست pull request

- [ ] از یک شاخهٔ اختصاصی استفاده کردم و این PR دقیقاً یک ورودی افزونه را تغییر می‌دهد.
- [ ] منبع ریپازیتوری سازندهٔ اصلی است، نه یک پروژهٔ چتری یا جمع‌کننده.
- [ ] هندل/پروفایل سازنده، ریپازیتوری، شناسهٔ گره، زیرمسیر و کامیت کامل شاهددار هستند.
