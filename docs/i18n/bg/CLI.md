# Справочник на CLI — `omni-dsh-plugins@1.0.0`

> 🌐 [English](../../docs/CLI.md) · [Português (Brasil)](../pt-BR/CLI.md) · [中文（简体）](../zh-CN/CLI.md) · **Български**

> **Неофициален общностен проект. Не е свързан с, одобрен от или спонсориран от DeepSeek.**
> Имената и марките на DeepSeek принадлежат на съответните им собственици.

Тази страница документира публикувания CLI точно както се държи във версия `1.0.0`. Всеки
синопсис и флаг по-долу идва от собствения `--help` изход на публикуваната команда; нищо тук не
описва непубликувано поведение. CLI-ят се поддържа от частен изходен код и се публикува в npm
като scoped пакета
[`omni-dsh-plugins`](https://www.npmjs.com/package/omni-dsh-plugins).

```bash
npx omni-dsh-plugins --help
```

## Принципи на дизайна в v1.0.0

- **По подразбиране само за четене.** `catalog`, `search`, `info`, `list` и `doctor` никога не
  променят профили, не записват файлове и не стартират код на плъгини.
- **Gate за съгласие за изпълнение на код.** `add`, `update` и `remove` отказват да изпълнят код
  от жизнения цикъл на DSH/pnpm, освен ако не подадете `--allow-code-execution`. Без него
  използвайте `--dry-run`, за да видите проверения план.
- **Политика за нативен Windows.** Нативните `add`/`update`/`remove` в Windows с изпълнение на код
  са забранени в v1.0.0; използвайте WSL. Dry-run и командите само за четене остават налични, а
  маркерите за възстановяване в нативен Windows изискват документирано ръчно възстановяване.
- **Закрепени входове.** Входът за каталога може да бъде локална директория, файл със снимка на
  състоянието (snapshot) или закрепен публичен snapshot URL, по избор заключен към точна
  40-символна ревизия.

## Общи опции

Тези опции се появяват в командите, консумиращи каталога (`catalog validate`, `search`, `info`,
`add`, `update`, `remove`, `doctor`):

| Опция                     | Значение                                                            |
| ------------------------- | -------------------------------------------------------------------- |
| `--catalog <path-or-url>` | Локална директория на каталога, snapshot файл или закрепен публичен snapshot URL |
| `--revision <sha>`        | Точна 40-символна ревизия на snapshot-а                              |
| `--json`                  | Извежда стабилен JSON изход                                          |

Глобални опции: `-V, --version` извежда версията на CLI-я; `-h, --help` извежда помощ за всяка
команда (`dsh-plugins help [command]` също работи).

## Изходни кодове

CLI-ят използва конвенционални изходни кодове на процеса:

| Изходен код | Значение                                                                    |
| ----------: | ---------------------------------------------------------------------------- |
| `0`         | Успех (включително резултати „празни, но валидни“, като например празен каталог) |
| `1`         | Неуспех: грешка при валидация, запис не е намерен, липсваща задължителна опция, или диагностична проверка, докладваща грешка |

Наблюдавани примери с v1.0.0: `catalog validate` върху валиден празен каталог излиза с `0` и
`0 entries valid; catalog is empty`; `info <unknown-id>` излиза с `1` и `Plugin not found`;
`doctor` излиза с `1`, когато която и да е проверка (например липсващ изпълним файл `dsh`)
докладва грешка.

## Команди

### `catalog` — валидира публичните повърхности на каталога

```text
dsh-plugins catalog validate [--catalog <path-or-url>] [--revision <sha>] [--json]
dsh-plugins catalog docs-check [root]
dsh-plugins catalog github-forms-check [root]
```

- **`catalog validate`** — валидира YAML-а и семантиката на каталога: безопасен YAML parsing,
  публичната схема, parsing на SPDX изрази, точен SemVer, SHA-512 SRI и отхвърляне на дублирани
  ID-та / ключове от ID на възел на хранилището плюс подпът. Тя е локална и само за четене: не се
  свързва с GitHub, не установява самоличността на хранилището и не проверява доказателства при
  закрепения commit. Това е точно командата, която CI job-ът `catalog-validation` изпълнява при
  всеки pull request за каталога.
- **`catalog docs-check [root]`** — проверява дали задължителната публична документация на
  каталога съществува и дали Markdown оградите за код са балансирани.
- **`catalog github-forms-check [root]`** — проверява структурираните публични GitHub issue форми
  (претенция, корекция, премахване).

```bash
# From the repository root:
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

### `search` — търси локално в публичните полета на каталога

```text
dsh-plugins search [options] <query...>
```

Търси локално в публичните полета на каталога спрямо избрания вход за каталога. Извежда
съвпадащите записи, или `No plugins found.` (изход `0`), когато нищо не съвпада.

```bash
npx omni-dsh-plugins search memory --catalog .
npx omni-dsh-plugins search notes markdown --catalog . --json
```

### `discover` — намира плъгини извън каталога

```text
dsh-plugins discover [options] <query...>
```

> **Не е налична в публикуваната `1.0.0`.** `discover` се появява в `1.0.0`; всяка друга команда
> на тази страница работи с версията, налична в момента в npm. Изпълняването ѝ спрямо `@1.0.0`
> се проваля с непозната команда.

Търси първо в курирания каталог, след което — освен ако не е зададено `--offline` — в темата
`dsh-plugin` на живо в GitHub, така че плъгин, който все още не е подаден, пак да може да бъде
намерен. Резултатите от каталога носят доказателствата, които каталогът съхранява (закрепен
commit, създател, лиценз); резултатите от общността не носят нищо от това и са обозначени
съответно, защото нищо в тях не е рецензирано.

`--limit <n>` ограничава резултатите на ниво (по подразбиране `8`). `--json` извежда стабилната
машинна форма, която никога не се локализира.

```bash
npx omni-dsh-plugins@1.0.0 discover memory --catalog .
npx omni-dsh-plugins@1.0.0 discover vision --offline --catalog . --json
```

### `info` — показва един публичен запис от каталога

```text
dsh-plugins info [options] <id>
```

Показва един публичен запис от каталога по каноничен ID на плъгина. Излиза с `1` и
`Plugin not found: <id>`, когато ID-то не е в каталога.

```bash
npx omni-dsh-plugins info example-notes-search --catalog .
```

### `add` — добавя плъгин от каталога чрез официално делегиране към DSH

```text
dsh-plugins add [options] <id>
```

| Опция                                 | Значение                                                            |
| -------------------------------------- | ---------------------------------------------------------------------- |
| `--profile <name>`                    | DSH профил, който да бъде променен (на практика задължителен; командата дава грешка без него) |
| `--dry-run`                           | Показва проверения план без файлове или подпроцеси                     |
| `--allow-code-execution`              | Съгласие за код от жизнения цикъл на DSH/pnpm (нативен Windows забранен; използвайте WSL) |
| `--catalog` / `--revision` / `--json` | Общите опции по-горе                                                  |

Семантика на dry-run в тази версия: командата разрешава и проверява плана за закрепения запис и
го извежда, без да създава файлове или да стартира подпроцеси. Реалната инсталация делегира на
официалните DSH инструменти и продължава само с `--allow-code-execution`.

```bash
# Preview only — nothing is written, nothing executes:
npx omni-dsh-plugins add example-notes-search --profile default --dry-run

# Real install — explicit consent to lifecycle code:
npx omni-dsh-plugins add example-notes-search --profile default --allow-code-execution
```

### `update` — обновява плъгин от каталога чрез официално делегиране към DSH

```text
dsh-plugins update [options] <id>
```

Същите опции и семантика на съгласие като `add`: `--profile <name>`, `--dry-run`,
`--allow-code-execution`, плюс общите опции за каталога.

### `remove` — премахва управляван от каталога плъгин чрез официално делегиране към DSH

```text
dsh-plugins remove [options] <id>
```

Същите опции и семантика на съгласие като `add`. Премахват се само инсталации, управлявани от
каталога.

### `recover` — възстановява задържана POSIX мутация

```text
dsh-plugins recover
```

Възстановява задържана POSIX мутация след прекъснат `add`/`update`/`remove`. Когато няма нищо
чакащо, извежда `No mutation recovery is pending.` и излиза с `0`. Възстановяването в нативен
Windows остава ръчно, съгласно документираната политика.

### `list` — изброява управляваните от каталога инсталации

```text
dsh-plugins list [--profile <name>] [--json]
```

Изброява управляваните от каталога инсталации, без да променя профили. `--profile <name>`
филтрира по DSH профил. Когато няма инсталации, извежда `No catalog-managed plugins installed.`
и излиза с `0`.

### `doctor` — диагностика само за четене

```text
dsh-plugins doctor [--catalog <path-or-url>] [--revision <sha>] [--json]
```

Изпълнява диагностика само за четене на Node, DSH, политиката за нативен Windows и каталога.
Всяка проверка докладва `ok` или `error`; всяко `error` прави общия изходен код `1`. Пример за
изход на машина без изпълнимия файл `dsh`:

```text
node [ok]: Node 24.16.0 is supported
dsh [error]: dsh executable was not found
catalog [ok]: catalog is valid and empty
```

## Какво не доказва локалната валидация

Зелено изпълнение на `catalog validate` потвърждава само структура и локална семантика. То не
доказва отдалечена самоличност на хранилището, собственост на създателя, или доказателство при
закрепения commit — поддръжниците прилагат тези отделни gate-ове за произход преди всяко
обединяване, както е описано в [CONTRIBUTING.md](../../CONTRIBUTING.md) и
[docs/GOVERNANCE.md](../../docs/GOVERNANCE.md).
