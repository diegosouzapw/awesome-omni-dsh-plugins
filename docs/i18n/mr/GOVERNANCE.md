# कॅटलॉग शासन

> 🌐 [English](../../GOVERNANCE.md) · [Português (Brasil)](../pt-BR/GOVERNANCE.md) · [中文（简体）](../zh-CN/GOVERNANCE.md) · **मराठी**

> **अनधिकृत समुदाय प्रकल्प. DeepSeek शी संलग्न नाही, त्यांच्याकडून मान्यताप्राप्त किंवा प्रायोजित नाही.**
> DeepSeek ची नावे आणि चिन्हे त्यांच्या संबंधित मालकांची आहेत.

सार्वजनिक कॅटलॉगचे शासन कसे होते: काय दाखल होते हे कोण ठरवते, स्पर्धात्मक योगदानांना
कोणत्या क्रमाने सन्मानित केले जाते, कोणत्या तपासण्या आपोआप चालतात आणि कोणते निर्णय मानवी राहतात.
इथे संदर्भित केलेली धोरणे [CONTRIBUTING.md](../../CONTRIBUTING.md),
[docs/CREDIT.md](../../docs/CREDIT.md) आणि [docs/RANKING.md](../../docs/RANKING.md) मध्ये आहेत; हे पृष्ठ वर्णन करते की ती कशी
एकत्र जुळतात.

## तत्त्वे

1. **निर्मात्याला प्राधान्य.** कॅटलॉग निर्मात्यांचे काम शोधण्यायोग्य बनवण्यासाठी अस्तित्वात आहे,
   त्याची मालकी घेण्यासाठी कधीही नाही. त्याच प्रामाणिक प्लगइनसाठी, निर्मात्याची थेट पुल रिक्वेस्ट
   कोणत्याही उघड्या समुदाय क्युरेशन किंवा ऑटोमेशन पुल रिक्वेस्टपेक्षा वरचढ ठरते — पूर्ण प्राधान्यक्रम आणि Git ओळख
   नियम [docs/CREDIT.md](../../docs/CREDIT.md) मध्ये.
2. **एक प्लगइन, एक पुनरावलोकित पुल रिक्वेस्ट.** बॅच विलीनीकरण नाही, सार्वजनिक कॅटलॉगमध्ये
   जनरेट केलेले मोठ्या प्रमाणातील आयात नाहीत. प्रत्येक एंट्री स्वतःचे पुनरावलोकन कमवते.
3. **विश्वासापेक्षा पुरावा.** प्रत्येक सार्वजनिक फील्ड निश्चित केलेल्या कमिटवरील मूळ निर्माता
   रिपॉझिटरीपर्यंत शोधता येते. हिरवी स्वयंचलित तपासणी कधीही उगमाचा पुरावा म्हणून स्वीकारली जात नाही.
4. **अनधिकृत, नेहमीच.** कोणतीही कॅटलॉग स्थिती DeepSeek पुनरावलोकन, प्रमाणपत्र किंवा
   मान्यता म्हणून सादर केली जात नाही.

## बदल `main` वर कसे पोहोचतात

सर्व बदल `main` वर पुनरावलोकित पुल रिक्वेस्ट्सद्वारे पोहोचतात — थेट पुश नाहीत. डीफॉल्ट
ब्रँचसाठीचे कार्यरत धोरण:

- **फक्त पुल रिक्वेस्ट्स.** कॅटलॉग एंट्रीज, दस्तऐवजीकरण आणि स्कीमा बदल सर्व PR द्वारे
  दाखल होतात; कॅटलॉग PR ने [CONTRIBUTING.md](../../CONTRIBUTING.md) मधील
  एक-ब्रँच-एक-प्लगइन नियमाचे पालन केले पाहिजे.
- **रेषीय इतिहास.** PR अशा प्रकारे एकत्रित केले जातात की `main` चा रेषीय, ऑडिट करता येण्याजोगा
  इतिहास कायम राहतो; विलीन केलेला सार्वजनिक इतिहास पुन्हा लिहिला जात नाही. क्युरेट केलेली एंट्री निर्माता
  पुढे येण्यापूर्वी विलीन झाली असल्यास, निर्माता इतिहास पुन्हा लिहिण्याऐवजी फॉलो-अप योगदानात ती दावा किंवा दुरुस्त करतो.
- **रिव्ह्यू-थ्रेड निराकरण.** विलीनीकरणापूर्वी पुनरावलोकन संभाषणे सोडवली जातात; न सोडवलेला
  अभिप्राय एकत्रीकरण अडवतो.
- **मेंटेनर विलीनीकरण.** प्लगइन एंट्री फक्त मेंटेनरच विलीन करतो, आणि फक्त
  [CONTRIBUTING.md](../../CONTRIBUTING.md) → "पुनरावलोकन गेट्स, टक्कर आणि विलीनीकरण" मधील प्रत्येक गेट सध्याच्या
  PR कमिटवर पास झाल्यानंतरच.

## `catalog-validation` तपासणी

`catalog/plugins/`, `schemas/` किंवा वर्कफ्लो स्वतःला स्पर्श करणारी प्रत्येक पुल रिक्वेस्ट
`catalog-validation` जॉब चालवते (`.github/workflows/validate-catalog.yml`), प्रकाशित
CLI वर निश्चित केलेली:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**ती काय पडताळते** — फक्त स्थानिक रचना आणि सिमॅंटिक्स:

- `catalog/plugins/` अंतर्गत प्रत्येक एंट्रीचे सुरक्षित YAML पार्सिंग.
- सार्वजनिक स्कीमेशी अनुपालन ([docs/SCHEMA.md](../../docs/SCHEMA.md) पहा).
- SPDX अभिव्यक्ती पार्सिंग, अचूक SemVer आवृत्त्या, वैध SHA-512 SRI इंटेग्रिटी मूल्ये.
- डुप्लिकेट नाकार: पुनरावृत्ती होणारे एंट्री ID नाहीत आणि पुनरावृत्ती होणाऱ्या प्रामाणिक
  रिपॉझिटरी-नोड-प्लस-सबपाथ की नाहीत.
- जाणीवपूर्वक रिकामा कॅटलॉग पास होतो (`0 entries valid; catalog is empty`).

**ती काय पडताळत नाही** — आणि त्यामुळे हिरवी तपासणी काय कधीही सिद्ध करत नाही:

- रिमोट रिपॉझिटरी ओळख: ती GitHub शी कनेक्ट होत नाही किंवा रिपॉझिटरी नोड ID
  URL विरुद्ध निश्चित करत नाही.
- निश्चित केलेल्या कमिटवरील पुरावा: वर्णने, परवाने, DSH एकत्रीकरण आणि स्मोक पुरावा
  आणला किंवा तपासला जात नाही.
- निर्मात्याचे मालकत्व, स्टार संख्या, किंवा उघड्या पुल रिक्वेस्ट्सशी टक्कर.

ते निर्णय मेंटेनरच्या स्वतंत्र प्रोव्हिनन्स गेट्सच्या अधिकारक्षेत्रातील आहेत, जे विलीनीकरणापूर्वी लागू केले जातात आणि
[CONTRIBUTING.md](../../CONTRIBUTING.md) मध्ये वर्णन केले आहेत. स्थानिक तपासणी ही तळमर्यादा आहे, मानदंड नाही.

## पडताळणी स्थिती

पडताळणी प्रत्येक एंट्रीसाठी तिच्या नेमक्या निश्चित केलेल्या कमिटविरुद्ध नोंदवली जाते, सार्वजनिक स्कीमामध्ये
व्याख्यित स्थिती वापरून (`eligible`, `verified`, `stale`, `unavailable`, `archived`, `quarantined`).
दोन सकारात्मक स्थिती जाणूनबुजून अरुंद आहेत:

- `eligible` — सार्वजनिक रचना आणि नेटिव्ह DSH एकत्रीकरण पडताळले गेले.
- `verified` — याव्यतिरिक्त, निश्चित केलेल्या सोर्स किंवा पॅकेजसाठी इंस्टॉलेशन स्मोक टेस्ट पास झाली;
  स्कीमेला स्मोक-टेस्ट रेकॉर्ड अस्तित्वात असणे आवश्यक असते.

कोणतीही स्थिती — किंवा इतर कोणतीही — मान्यता, हमी किंवा सुरक्षा प्रमाणपत्र नाही.
स्थिती क्रमवारीशी कशा संवाद साधतात यासह पूर्ण सिमॅंटिक्स
[docs/RANKING.md](../../docs/RANKING.md) मध्ये आहे; रेकॉर्ड आकार [docs/SCHEMA.md](../../docs/SCHEMA.md) मध्ये आहे.

## क्लेम, करेक्शन आणि रिमूव्हल

संरचित GitHub इश्यू फॉर्म्स (`.github/ISSUE_TEMPLATE/`) हे तुम्ही सादर न केलेल्या एंट्रीमध्ये
बदल करण्यासाठी शासित मार्ग आहे:

| फॉर्म          | कोण वापरते                               | निकाल                                                |
| -------------- | ---------------------------------------- | --------------------------------------------------- |
| **क्लेम**      | निर्माता ज्याचे प्लगइन दुसऱ्याने क्युरेट केले आहे | मालकी मूळ स्रोताशी जोडली जाते; निर्माता मग थेट योगदान देऊ शकतो |
| **करेक्शन**    | कोणीही ज्याला अचूक नसलेला सार्वजनिक मेटाडेटा दिसतो | प्रभावित एंट्रीचे पुनरावलोकित दुरुस्ती              |
| **रिमूव्हल**    | निर्माता ज्यांना त्यांची नोंद काढायची आहे, किंवा धोरण उल्लंघनाची तक्रार करणारा | एंट्रीचे पुनरावलोकित काढणे किंवा क्वारंटाइन |

तिन्ही प्रवाहांना लागू होणारे नियम:

- मालकीचे दावे पडताळणीयोग्य सार्वजनिक पुराव्याने समर्थित असले पाहिजेत (रिपॉझिटरी मालकी,
  पॅकेज लेखकत्व, मॅनिफेस्ट मेटाडेटा किंवा निश्चित केलेला सोर्स इतिहास) — Discussion वर टिप्पणी करणे
  निर्मातृत्व सिद्ध करत नाही ([docs/CREDIT.md](../../docs/CREDIT.md)).
- नोंदवलेल्या प्लगइनमधील सुरक्षा समस्या आधी त्या प्लगइनच्या स्वतःच्या मेंटेनरकडे जातात; कॅटलॉग
  बाजू नंतर एक्सप्लॉइट तपशील प्रकाशित न करता दुरुस्ती किंवा क्वारंटाइन हाताळते
  ([SECURITY.md](../../SECURITY.md)).
- फॉर्ममध्ये कधीही क्रेडेन्शियल्स, खाजगी संपर्क तपशील किंवा इतर गुपिते समाविष्ट करू नका.

## भूमिका

- **निर्माते** त्यांच्या प्लगइन्स आणि त्यांच्या नोंदींच्या प्राधान्याचे मालक आहेत. ते थेट योगदान देऊ शकतात,
  समुदाय क्युरेशन मंजूर करू शकतात किंवा विद्यमान एंट्रीचा क्लेम/करेक्शन/रिमूव्हल करू शकतात.
- **समुदाय योगदानकर्ते** ज्या निर्मात्यांनी अजून योगदान दिले नाही त्यांच्यासाठी एंट्रीज क्युरेट करू शकतात,
  [docs/CREDIT.md](../../docs/CREDIT.md) मधील आदरपूर्ण-संपर्क आणि श्रेय नियमांच्या अंतर्गत. क्युरेशन कधीही
  नंतरच्या थेट निर्माता योगदानापेक्षा वरचढ नसते.
- **मेंटेनर्स** पुनरावलोकन करतात, प्रोव्हिनन्स गेट्स लागू करतात, टक्कर सोडवतात आणि विलीन करतात. ते
  वेबसाइट ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online))
  आणि प्रकाशित CLI खाजगी स्रोतातून देखील सांभाळतात; या रिपॉझिटरीचा सार्वजनिक डेटा, स्कीमा आणि धोरणे
  हेच ते पृष्ठभाग वापरतात.
