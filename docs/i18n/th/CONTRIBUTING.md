# การมีส่วนร่วม

> 🌐 [English](../../../CONTRIBUTING.md) · [Português (Brasil)](../pt-BR/CONTRIBUTING.md) · [中文（简体）](../zh-CN/CONTRIBUTING.md) · **ไทย**

> **โปรเจกต์ชุมชนที่ไม่เป็นทางการ ไม่มีส่วนเกี่ยวข้อง ไม่ได้รับการรับรอง และไม่ได้รับการสนับสนุนจาก DeepSeek**
> ชื่อและเครื่องหมายการค้าของ DeepSeek เป็นของเจ้าของแต่ละราย

ขอบคุณที่ช่วยปรับปรุงแคตตาล็อกนี้ การมีส่วนร่วมยึดหลักผู้สร้างมาก่อนเสมอ: ใช้หลักฐานจากรีโพซิทอรีดั้งเดิม
รักษาการให้เครดิต และทำให้ปลั๊กอินแต่ละตัวสามารถรีวิวได้อย่างเป็นอิสระ แคตตาล็อกนี้ถูกออกแบบให้เริ่มต้นจากศูนย์
ไม่มีรายการใดถูกยอมรับโดยไม่มีพูลรีเควสต์ (pull request) ของตัวเองที่ผ่านการรีวิวแล้ว

## เริ่มต้นจากผู้สร้าง

พูลรีเควสต์ที่เปิดโดยผู้สร้างปลั๊กอินเองหรือองค์กรเจ้าของโดยตรงจะได้รับความสำคัญเป็นอันดับแรกเสมอ
หากผู้สร้างพร้อมที่จะมีส่วนร่วมแล้ว ให้ใช้แบรนช์และพูลรีเควสต์ของผู้สร้างแทนการสร้างผลงานของพวกเขาขึ้นใหม่ใน
แบรนช์ของผู้จัดทำ (curator) หรือระบบอัตโนมัติ

การจัดทำโดยชุมชนเป็นที่ยินดีต้อนรับเมื่อช่วยเหลือผู้สร้างที่ยังไม่ได้เปิดพูลรีเควสต์ แต่การจัดทำนี้ไม่ได้สร้าง
ความเป็นเจ้าของหรือความสำคัญเหนือกว่าการมีส่วนร่วมโดยตรงของผู้สร้างในภายหลัง

## หนึ่งปลั๊กอินต่อหนึ่งแบรนช์และหนึ่งพูลรีเควสต์

สร้างแบรนช์เฉพาะสำหรับปลั๊กอินหนึ่งตัวและเปิดพูลรีเควสต์หนึ่งฉบับจากแบรนช์นั้น แบรนช์และพูลรีเควสต์ต้องสร้าง
หรือแก้ไขไฟล์ YAML เพียงไฟล์เดียวภายใต้ `catalog/plugins/` เท่านั้น อย่านำปลั๊กอินหลายตัว การจัดระเบียบเอกสาร
ดัชนีที่สร้างขึ้นเอง หรืองานบำรุงรักษาที่ไม่เกี่ยวข้องมาผสมกันในแบรนช์หรือพูลรีเควสต์เดียวกัน

ID ของรายการและชื่อไฟล์ต้องเป็นค่าเดียวกันในรูปแบบ lowercase kebab-case ผู้ดูแลจะรีวิวและผสาน (merge)
พูลรีเควสต์ของปลั๊กอินแต่ละฉบับแยกกัน ชุดพูลรีเควสต์ที่รวมปลั๊กอินหลายตัวจะไม่ถูกแยกหรือผสานบางส่วน

## สืบหาแหล่งที่มาดั้งเดิม

ฟิลด์สาธารณะทุกฟิลด์ต้องถูกสร้างขึ้นใหม่จากรีโพซิทอรี แพ็กเกจ ไฟล์ manifest, README หรือรีลีสของผู้สร้างดั้งเดิม
ณ คอมมิตที่ตรึงไว้ ห้ามคัดลอกเนื้อหา การจัดหมวดหมู่ ภาพหน้าจอ การจัดอันดับ แบดจ์ หรือเมทาดาทาที่สร้างขึ้นเองจาก
แคตตาล็อกหรือ aggregator อื่น ลิงก์ที่พบในโปรเจกต์ร่ม (umbrella project) มาร์เก็ตเพลส หรือรายชื่อ/aggregator ถือเป็น
เพียงเบาะแสเท่านั้น ไม่ใช่หลักฐานและไม่ใช่แหล่งที่มาของปลั๊กอิน

ห้ามส่ง umbrella, aggregator, มาร์เก็ตเพลส แคตตาล็อกตัวติดตั้ง หรือรายชื่อใด ๆ เป็นรายการในแคตตาล็อกเด็ดขาด
แม้ว่าตัวมันเองจะติดตั้งได้อย่างอิสระก็ตาม ใช้มันเป็นเพียงเบาะแสและสืบหาปลั๊กอินลูกแต่ละตัวที่ติดตั้งได้อย่างอิสระ
ไปยังผู้สร้างและรีโพซิทอรีดั้งเดิมที่แท้จริง ปลั๊กอินที่อยู่ใน monorepo จริงของผู้สร้างสามารถส่งได้จาก subpath
ที่แน่นอนของมัน แต่ต้องปฏิบัติตามนโยบายดาวของ monorepo ด้านล่าง

## หลักฐานที่จำเป็น

ระบุสิ่งต่อไปนี้ทั้งหมดในพูลรีเควสต์:

- URL สาธารณะที่เป็นทางการของรีโพซิทอรีดั้งเดิมและ node ID ของรีโพซิทอรีที่ไม่เปลี่ยนแปลง ผู้ดูแลจะตรวจสอบ
  node ID และปฏิเสธความไม่ตรงกันของ URL ในด่านตรวจแหล่งที่มาแยกต่างหาก
- แฮนเดิล GitHub สาธารณะของผู้สร้างและ URL โปรไฟล์สาธารณะที่ตรงกัน ไฟล์ YAML เก็บแฮนเดิลเพียงครั้งเดียว
  URL โปรไฟล์ถูกสร้างขึ้นจาก `https://github.com/<handle>`
- OID คอมมิตต้นทางเต็ม 40 ตัวอักษรและ subpath ของปลั๊กอินที่แน่นอน หรือ `null` สำหรับปลั๊กอินที่รากของรีโพซิทอรี
- คำอธิบายภาษาอังกฤษที่มีขอบเขตจำกัดและเส้นทางหลักฐานของมัน ณ คอมมิตที่ตรึงไว้
- `kind` ของผลงาน หมวดหมู่หลัก และแท็กที่เลือกจาก [docs/CATEGORIES.md](../../docs/CATEGORIES.md)
- ข้อความใบอนุญาต SPDX ต้นทางฉบับสมบูรณ์ที่มีหลักฐาน ณ คอมมิตที่ตรึงไว้
- ตัวระบุการติดตั้งที่เป็นมาตรฐาน ตรึงไว้กับเวอร์ชัน npm ที่แน่นอน หรือกับรีโพซิทอรีต้นทาง คอมมิตเต็ม และ subpath
  ตัวระบุนี้คือข้อมูล ไม่ใช่คำสั่งเชลล์เด็ดขาด
- หลักฐานการเชื่อมต่อ DSH แบบเนทีฟและเส้นทางของมัน ณ คอมมิตที่ตรึงไว้
- หลักฐานการทดสอบเบื้องต้น (smoke test) ที่มีอยู่แล้วและไม่มีข้อมูลอ่อนไหวสำหรับ pin ของผลงานนั้น หรือค่า
  `not run` อย่างชัดแจ้ง ห้ามติดตั้งปลั๊กอินหรือรันโค้ด `preinstall`, `install`, `postinstall`, `prepare` หรือ
  โค้ดวงจรชีวิตของแพ็กเกจ/ปลั๊กอินอื่น ๆ เพียงเพื่อเตรียมการมีส่วนร่วมในแคตตาล็อก
- สำหรับรีโพซิทอรีที่อุทิศให้เฉพาะ ต้องระบุจำนวนดาวที่ตรวจสอบได้ของรีโพซิทอรีนั้นจริง ๆ พร้อมแหล่งข้อมูลสาธารณะ
  และเวลาที่ตรวจสอบ สำหรับปลั๊กอินใน monorepo ให้ใช้นโยบาย null ตามที่กำหนดด้านล่าง
- หลักฐานที่มาจาก Discussion หรือคอมเมนต์สาธารณะเมื่อมีอยู่ มิฉะนั้นให้ใช้ `null`
- ค่า `unofficial: true` ที่เครื่องอ่านได้

หากยังไม่มีการทดสอบเบื้องต้นที่เข้าเงื่อนไข ให้ใช้ `verification.status: eligible` และ
`verification.smokeTest: null` ใช้ `verified` เฉพาะเมื่อมีหลักฐานการทดสอบเบื้องต้นที่รีวิวได้สำหรับ pin นั้น
เท่านั้น ทั้งสองสถานะไม่ใช่การรับรองหรือใบรับรองด้านความปลอดภัย

ห้ามส่งข้อมูลรับรองตัวตน คุกกี้ ที่อยู่อีเมลส่วนตัว ซอร์สที่ยังไม่เผยแพร่ หรือความลับอื่นใดเด็ดขาด

## กฎ YAML และสคีมา

สร้าง `catalog/plugins/<plugin-id>.yaml` และตรวจสอบให้ผ่านตาม
[`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml) ค่า `id` ต้องเท่ากับชื่อไฟล์ฐาน (basename)
และต้องขึ้นต้นด้วยเนมสเปซของคุณ: แฮนเดิล `creator.github` ของคุณที่แปลงเป็นตัวพิมพ์เล็ก (อักขระใด ๆ ที่ต่อเนื่องกัน
นอกช่วง `[a-z0-9]` จะถูกยุบเป็น `-` ตัวเดียว) ตามด้วย `-` เช่น `some-creator-my-plugin` สำหรับแฮนเดิล
`Some-Creator` การตรวจสอบแคตตาล็อกบังคับใช้ทั้งสองอย่างนี้ สคีมาคือแหล่งข้อมูลจริงสำหรับชื่อฟิลด์และค่าที่อนุญาต
[docs/CATEGORIES.md](../../docs/CATEGORIES.md) กำหนดวิธีเลือก artifact kind หมวดหมู่หลัก แท็ก และขอบเขต
รีโพซิทอรีเพียงหนึ่งเดียว

ตัวระบุ npm ต้องมีชื่อแพ็กเกจที่ถูกต้องและเวอร์ชันที่แน่นอน สคีมาสาธารณะปฏิเสธค่าที่คล้ายตัวเลือกหรือไม่มีขอบเขต
แต่ไม่ได้ทำการตรวจ SemVer หรือ SRI ซ้ำ: การตรวจสอบแคตตาล็อกต้อง parse เวอร์ชัน กำหนดให้เป็น SemVer ที่แน่นอน
และ parse ค่า integrity ใด ๆ ให้เป็น SHA-512 SRI ที่ถูกต้อง ตัวระบุแบบซอร์สถูกผูกกับ `source.repository`,
`source.commit` และ `source.subpath` โดยไม่ทำซ้ำค่าต้นทางที่เปลี่ยนแปลงได้

ตัวติดตั้งต้องใช้ argument arrays ปิดการรันเชลล์ และวางตัวคั่นออปชัน (option terminator) ก่อนค่าตำแหน่งที่มาจาก
แคตตาล็อก ในกรณีที่คำสั่งที่เรียกใช้รองรับ การตรวจสอบตอนส่งพูลรีเควสต์ต้องไม่เรียกใช้ตัวติดตั้งหรือวงจรชีวิตของ
ปลั๊กอิน

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` เป็นการตรวจสอบโครงสร้างและความหมายเชิงตรรกะแบบภายในเครื่องและอ่านอย่างเดียว มันจะ parse
YAML แบบปลอดภัย ตรวจสอบสคีมาสาธารณะ parse นิพจน์ SPDX กำหนดให้เป็น SemVer ที่แน่นอนและ SHA-512 SRI ที่ถูกต้อง
และปฏิเสธ ID ซ้ำและคีย์ node-รีโพซิทอรีบวก subpath ที่ซ้ำกัน มันไม่ติดต่อ GitHub ไม่ตรวจสอบตัวตนของรีโพซิทอรี
และไม่ตรวจสอบเส้นทางหลักฐาน ณ คอมมิตที่ตรึงไว้

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

ก่อนที่รายการจะถึงสถานะ `eligible` ผู้ดูแลจะตรวจสอบรีโพซิทอรีที่เป็นทางการและ node ID แยกต่างหาก ผูกผู้สร้างเข้า
กับซอร์สดั้งเดิม และตรวจสอบคำอธิบาย ใบอนุญาต การเชื่อมต่อ DSH และหลักฐานการทดสอบเบื้องต้นที่ระบุไว้ ณ
`source.commit` ผลการตรวจสอบภายในเครื่องที่ผ่านไม่ใช่หลักฐานแหล่งที่มาหรือแหล่งกำเนิด

## ดาวของรีโพซิทอรี

เฉพาะดาวที่ตรวจสอบได้ว่าเป็นของรีโพซิทอรีปลั๊กอินที่อุทิศให้เฉพาะเท่านั้นที่จะถูกบันทึกได้ ดาวของโปรเจกต์แม่ต้อง
ไม่ถูกนำมาระบุให้กับปลั๊กอินที่จัดเก็บอยู่ใน monorepo ที่ใหญ่กว่าเด็ดขาด รายการใน monorepo ยังคงมีสิทธิ์ในส่วน
การใช้งานของแคตตาล็อก แต่ต้องประกาศ:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

รายการที่อุทิศให้เฉพาะใช้ `repositoryScope: dedicated`, `starsPolicy: exact-repository` และจำนวนดาวที่ไม่ติดลบ
ที่สังเกตได้บนรีโพซิทอรีเดียวกันนั้น อ่าน [docs/RANKING.md](../../docs/RANKING.md) ก่อนส่งข้อมูลความนิยม

## ลำดับความสำคัญของผู้สร้างและการติดต่ออย่างสุภาพ

สำหรับปลั๊กอินเดียวกัน ลำดับความสำคัญคือ:

1. พูลรีเควสต์ที่เปิดโดยผู้สร้างหรือองค์กรเจ้าของ
2. พูลรีเควสต์จากชุมชนที่ได้รับการอนุมัติอย่างชัดแจ้งจากผู้สร้าง
3. พูลรีเควสต์การจัดทำโดยชุมชนที่ถูกต้องและมีอยู่แล้ว
4. พูลรีเควสต์จากระบบอัตโนมัติของแคตตาล็อก

พูลรีเควสต์โดยตรงจากผู้สร้างมีความสำคัญเหนือกว่าพูลรีเควสต์การจัดทำหรือระบบอัตโนมัติที่เปิดอยู่เสมอ ไม่ว่าฉบับใด
จะเปิดก่อนหรือคืบหน้าไปมากกว่ากัน พูลรีเควสต์ของผู้สร้างจะกลายเป็นช่องทางการรีวิว ผู้ดูแลจะไม่ force-push แบรนช์
ของผู้สร้างหรือย้ายผลงานของพวกเขาไปยังพูลรีเควสต์ที่จัดทำไว้ หากรายการที่จัดทำแล้วถูกผสานไปแล้ว ประวัติสาธารณะ
จะไม่ถูกเขียนทับ ผู้สร้างสามารถใช้คำขอเรียกร้องความเป็นเจ้าของหรือคำขอแก้ไข แล้วจึงมีส่วนร่วมด้วยพูลรีเควสต์
ติดตามผลโดยตรง

พูลรีเควสต์ที่จัดทำโดยชุมชนควรมีการกล่าวถึง `@creator` แบบสุภาพในคำอธิบายเพียงหนึ่งครั้ง คู่กับลิงก์ไปยัง
รีโพซิทอรีดั้งเดิม เพื่อเชิญชวนให้ผู้สร้างรีวิวหรือแทนที่ด้วยพูลรีเควสต์โดยตรง อย่ากล่าวถึงซ้ำ อย่าเปิด issue
เชิงส่งเสริม อย่าโพสต์ข้ามแพลตฟอร์ม อย่าส่งข้อความส่วนตัวโดยไม่ได้รับการร้องขอ หรือรบกวนผู้สร้างในลักษณะอื่นใด

พูลรีเควสต์และคอมมิตที่เขียนโดยผู้สร้างจะรักษาเครดิตของผู้สร้างไว้ตามธรรมชาติ คอมมิตที่จัดทำโดยชุมชนอาจใช้
Git authorship ของผู้สร้าง หรือ trailer `Co-authored-by` ได้เฉพาะเมื่อมีตัวตนที่ผูกกับแหล่งที่มาและตรวจสอบได้
สาธารณะเท่านั้น ห้ามคาดเดาหรือกุอีเมลขึ้นเองเด็ดขาด เมื่อไม่มีตัวตน Git ที่ตรวจสอบแล้ว ผู้จัดทำจะเป็นผู้เขียนคอมมิต
และให้เครดิตอย่างชัดแจ้งด้วยข้อความ `Created by @handle` พร้อมลิงก์รีโพซิทอรีดั้งเดิมในไฟล์ YAML และพูลรีเควสต์
บัญชีผู้ดูแลหรือระบบอัตโนมัติอาจเป็น committer หรือผู้ร่วมเขียนที่ยืนยันแล้วได้ แต่ต้องไม่แทนที่ authorship ของ
ผู้สร้าง ดู [docs/CREDIT.md](../../docs/CREDIT.md) สำหรับนโยบายฉบับเต็ม

## คำสั่งตรวจสอบและความพร้อมใช้งาน

CLI ของ npm เผยแพร่ในชื่อ `omni-dsh-plugins@1.0.1` ดังนั้นคำสั่งด้านล่างนี้พร้อมใช้งานผ่าน `npx`
แล้วในวันนี้ ใช้คำสั่งเหล่านี้ตามที่เขียนไว้เป๊ะ ๆ ผู้มีส่วนร่วมไม่ควรคิดค้นคำสั่งทดแทนขึ้นเอง

รันคำสั่งเหล่านี้จากรากของรีโพซิทอรี:

```bash
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

`catalog validate` ทำเฉพาะการตรวจสอบ YAML, สคีมา, SPDX, SemVer ที่แน่นอน, SHA-512 SRI และรายการซ้ำแบบ
ภายในเครื่องตามที่อธิบายไว้ข้างต้นเท่านั้น และยอมรับแคตตาล็อกที่ตั้งใจให้ไม่มีรายการเลย มันไม่พิสูจน์ตัวตนของ
รีโพซิทอรีระยะไกลหรือหลักฐานแหล่งที่มาที่ตรึงไว้ คำสั่งอื่น ๆ ตรวจสอบเอกสารสาธารณะที่จำเป็นและแบบฟอร์ม issue ของ
GitHub ที่มีโครงสร้าง การผ่านคำสั่งเหล่านี้ในเครื่องไม่ได้ผ่อนปรนข้อกำหนดด้านหลักฐาน ผู้ดูแลยังคงใช้ด่านตรวจ
รีลีสที่สอดคล้องกันทุกด่านก่อนผสาน

## ด่านตรวจการรีวิว การชนกัน และการผสาน

ผู้ดูแลจะใช้ด่านตรวจทุกด่านกับคอมมิตปัจจุบันของพูลรีเควสต์ก่อนผสาน:

1. **ขอบเขต:** หนึ่งแบรนช์เฉพาะ ไฟล์ YAML ของปลั๊กอินหนึ่งไฟล์ และไม่มีการเปลี่ยนแปลงที่ไม่เกี่ยวข้อง
2. **ตัวตนดั้งเดิม:** ผู้สร้าง รีโพซิทอรีที่เป็นทางการ node ID คอมมิตเต็ม และ subpath ตรงกัน
3. **สคีมาและหลักฐาน:** YAML หมวดหมู่ SPDX pin การติดตั้ง หลักฐาน DSH และสถานะการทดสอบเบื้องต้นสอดคล้องกัน
   ภายในโดยไม่รันโค้ดวงจรชีวิตของปลั๊กอิน
4. **ความนิยม:** ดาวที่อุทิศให้เฉพาะตรวจสอบได้บนรีโพซิทอรีจริง หรือดาวของ monorepo เป็น `null` พร้อม
   `undefined-parent-repository`
5. **เอกสารและแบบฟอร์ม:** เอกสารสาธารณะ Markdown fences และแบบฟอร์มที่มีโครงสร้างยังคงถูกต้อง
6. **การชนกันและการขจัดความซ้ำซ้อน:** ไม่มีรายการที่ผสานแล้วหรือพูลรีเควสต์ที่เปิดอยู่ใดเป็นตัวแทนของปลั๊กอิน
   เดียวกัน

ชื่อหรือ ID ที่ต่างกันไม่ได้ทำให้ปลั๊กอินที่ซ้ำกันแตกต่างกัน ให้ถือว่า node ID ของรีโพซิทอรีและ subpath เดียวกัน
แพ็กเกจมาตรฐานเดียวกัน หรือเป้าหมายการติดตั้งอื่นที่เหมือนกันอย่างชัดเจนเป็นการชนกัน แก้ไขนามแฝงและพูลรีเควสต์
ที่แข่งขันกันก่อนผสาน พูลรีเควสต์โดยตรงจากผู้สร้างชนะการชนกันกับการจัดทำหรือระบบอัตโนมัติ มิฉะนั้นผู้ดูแลจะเลือก
ช่องทางรีวิวหนึ่งช่องทางและปิดหรือเปลี่ยนเส้นทางรายการที่ซ้ำแทนที่จะผสานทั้งสอง

มีเพียงผู้ดูแลเท่านั้นที่ผสานปลั๊กอินหลังจากผ่านด่านตรวจทุกด่านแล้ว ปลั๊กอินที่ได้รับการยอมรับแต่ละตัวจะถูกผสาน
แยกกัน การตรวจสอบ การจัดทำ หรือระบบอัตโนมัติไม่ได้หมายความว่าจะผสานอัตโนมัติหรือเป็นชุด

## เช็กลิสต์พูลรีเควสต์

- [ ] ฉันใช้แบรนช์เฉพาะหนึ่งแบรนช์ และ PR นี้เปลี่ยนแปลงรายการปลั๊กอินเพียงหนึ่งรายการเท่านั้น
- [ ] แหล่งที่มาคือรีโพซิทอรีของผู้สร้างดั้งเดิม ไม่ใช่ umbrella หรือ aggregator
- [ ] แฮนเดิล/โปรไฟล์ของผู้สร้าง รีโพซิทอรี node ID subpath และคอมมิตเต็มมีหลักฐานรองรับ
- [ ] kind หมวดหมู่ และแท็กเป็นไปตาม `docs/CATEGORIES.md`
- [ ] ใบอนุญาต SPDX และตัวระบุการติดตั้งที่ตรึงไว้มีหลักฐานรองรับ
- [ ] การเชื่อมต่อ DSH แบบเนทีฟและผลการทดสอบเบื้องต้นหรือสถานะ `not run` มีหลักฐานรองรับ
- [ ] ฉันไม่ได้รันโค้ดวงจรชีวิตของปลั๊กอินหรือแพ็กเกจเพื่อเตรียมการมีส่วนร่วมนี้
- [ ] ดาวที่อุทิศให้เฉพาะตรวจสอบได้ หรือดาวของ monorepo ใช้นโยบาย null ที่กำหนด
- [ ] ฉันตรวจสอบแล้วว่าไม่มีรายการหรือพูลรีเควสต์ที่เปิดอยู่สำหรับปลั๊กอินเดียวกันนี้
- [ ] รายการนี้ระบุอย่างชัดแจ้งว่าไม่เป็นทางการและไม่มีความลับหรือข้อมูลส่วนตัว
