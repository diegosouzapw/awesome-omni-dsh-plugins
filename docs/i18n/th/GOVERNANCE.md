# การกำกับดูแลแคตตาล็อก

> 🌐 [English](../../docs/GOVERNANCE.md) · **ไทย (th)**

> **โปรเจกต์ชุมชนที่ไม่เป็นทางการ ไม่มีส่วนเกี่ยวข้อง ไม่ได้รับการรับรอง และไม่ได้รับการสนับสนุนจาก DeepSeek**
> ชื่อและเครื่องหมายการค้าของ DeepSeek เป็นของเจ้าของแต่ละราย

แคตตาล็อกสาธารณะนี้ถูกกำกับดูแลอย่างไร: ใครเป็นผู้ตัดสินใจว่าอะไรจะเข้ามาได้ การมีส่วนร่วมที่แข่งขันกันได้รับ
การให้เกียรติตามลำดับใด การตรวจสอบใดที่รันโดยอัตโนมัติ และการตัดสินใจใดที่ยังคงต้องใช้มนุษย์ นโยบายที่อ้างอิงไว้
ที่นี่อยู่ใน [CONTRIBUTING.md](../../CONTRIBUTING.md), [docs/CREDIT.md](../../docs/CREDIT.md) และ
[docs/RANKING.md](../../docs/RANKING.md); หน้านี้อธิบายว่าทุกอย่างเชื่อมโยงกันอย่างไร

## หลักการ

1. **ผู้สร้างมาก่อน** แคตตาล็อกนี้มีอยู่เพื่อทำให้ผลงานของผู้สร้างค้นพบได้ ไม่ใช่เพื่อยึดความเป็นเจ้าของไปจาก
   พวกเขา สำหรับปลั๊กอินเดียวกัน พูลรีเควสต์โดยตรงจากผู้สร้างจะมีความสำคัญเหนือกว่าพูลรีเควสต์การจัดทำโดยชุมชน
   หรือระบบอัตโนมัติที่เปิดอยู่ — ลำดับความสำคัญฉบับเต็มและกฎตัวตน Git อยู่ใน
   [docs/CREDIT.md](../../docs/CREDIT.md)
2. **หนึ่งปลั๊กอิน หนึ่งพูลรีเควสต์ที่ผ่านการรีวิว** ไม่มีการผสานเป็นชุด ไม่มีการนำเข้าจำนวนมากที่สร้างขึ้นเอง
   เข้าสู่แคตตาล็อกสาธารณะ แต่ละรายการได้รับการรีวิวของตัวเอง
3. **หลักฐานสำคัญกว่าความไว้วางใจ** ทุกฟิลด์สาธารณะสืบย้อนไปยังรีโพซิทอรีของผู้สร้างดั้งเดิม ณ คอมมิตที่ตรึงไว้
   การตรวจสอบอัตโนมัติที่ผ่านไม่เคยถูกยอมรับว่าเป็นหลักฐานของแหล่งกำเนิด
4. **ไม่เป็นทางการเสมอ** ไม่มีสถานะใดในแคตตาล็อกที่ถูกนำเสนอว่าเป็นการรีวิว การรับรอง หรือการสนับสนุนจาก
   DeepSeek

## การเปลี่ยนแปลงเข้าสู่ `main` อย่างไร

การเปลี่ยนแปลงทั้งหมดเข้าสู่ `main` ผ่านพูลรีเควสต์ที่ผ่านการรีวิวเท่านั้น — ไม่มีการพุชโดยตรง นโยบายการทำงาน
สำหรับแบรนช์ค่าเริ่มต้น:

- **พูลรีเควสต์เท่านั้น** รายการแคตตาล็อก เอกสารประกอบ และการเปลี่ยนแปลงสคีมาทั้งหมดเข้าผ่าน PR; PR ของ
  แคตตาล็อกต้องปฏิบัติตามกฎหนึ่งปลั๊กอินต่อหนึ่งแบรนช์ใน [CONTRIBUTING.md](../../CONTRIBUTING.md)
- **ประวัติแบบเส้นตรง** PR จะถูกรวมเข้าด้วยกันในลักษณะที่ `main` ยังคงมีประวัติแบบเส้นตรงที่ตรวจสอบได้
  ประวัติสาธารณะที่ผสานแล้วจะไม่ถูกเขียนทับ หากรายการที่จัดทำแล้วถูกผสานก่อนที่ผู้สร้างจะติดต่อมา ผู้สร้างจะขอ
  เรียกร้องความเป็นเจ้าของหรือแก้ไขในผลงานติดตามผลแทนการเขียนประวัติใหม่
- **การแก้ไขเธรดรีวิว** บทสนทนาการรีวิวจะถูกแก้ไขก่อนผสาน; ความเห็นที่ยังไม่ได้รับการแก้ไขจะปิดกั้นการรวม
- **ผู้ดูแลเป็นผู้ผสาน** มีเพียงผู้ดูแลเท่านั้นที่ผสานรายการปลั๊กอิน และเฉพาะหลังจากผ่านด่านตรวจทุกด่านใน
  [CONTRIBUTING.md](../../CONTRIBUTING.md) → "ด่านตรวจการรีวิว การชนกัน และการผสาน" บนคอมมิตปัจจุบันของ PR
  แล้วเท่านั้น

## การตรวจสอบ `catalog-validation`

ทุกพูลรีเควสต์ที่แตะต้อง `catalog/plugins/`, `schemas/` หรือ workflow เองจะรันงาน `catalog-validation`
(`.github/workflows/validate-catalog.yml`) ซึ่งตรึงไว้กับ CLI ที่เผยแพร่แล้ว:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**สิ่งที่มันตรวจสอบ** — โครงสร้างและความหมายเชิงตรรกะภายในเครื่องเท่านั้น:

- การ parse YAML แบบปลอดภัยของทุกรายการภายใต้ `catalog/plugins/`
- ความสอดคล้องกับสคีมาสาธารณะ (ดู [docs/SCHEMA.md](../../docs/SCHEMA.md))
- การ parse นิพจน์ SPDX, เวอร์ชัน SemVer ที่แน่นอน, ค่า integrity SHA-512 SRI ที่ถูกต้อง
- การปฏิเสธรายการซ้ำ: ไม่มี ID รายการที่ซ้ำกันและไม่มีคีย์ node-รีโพซิทอรีบวก subpath มาตรฐานที่ซ้ำกัน
- แคตตาล็อกที่ตั้งใจให้ไม่มีรายการเลยจะผ่าน (`0 entries valid; catalog is empty`)

**สิ่งที่มันไม่ตรวจสอบ** — และดังนั้นสิ่งที่การตรวจสอบที่ผ่านจะไม่มีวันพิสูจน์:

- ตัวตนของรีโพซิทอรีระยะไกล: มันไม่ติดต่อ GitHub หรือแก้ไข node ID ของรีโพซิทอรีเทียบกับ URL
- หลักฐาน ณ คอมมิตที่ตรึงไว้: คำอธิบาย ใบอนุญาต การเชื่อมต่อ DSH และหลักฐานการทดสอบเบื้องต้นไม่ถูกดึงหรือ
  ตรวจสอบ
- ความเป็นเจ้าของของผู้สร้าง จำนวนดาว หรือการชนกันกับพูลรีเควสต์ที่เปิดอยู่

การตัดสินใจเหล่านั้นเป็นหน้าที่ของด่านตรวจแหล่งที่มาแยกต่างหากของผู้ดูแล ซึ่งใช้ก่อนการผสานและอธิบายไว้ใน
[CONTRIBUTING.md](../../CONTRIBUTING.md) การตรวจสอบภายในเครื่องคือพื้นฐานขั้นต่ำ ไม่ใช่มาตรฐานสูงสุด

## สถานะการยืนยัน

การยืนยันถูกบันทึกต่อรายการเทียบกับคอมมิตที่ตรึงไว้แน่นอนของมัน โดยใช้สถานะที่กำหนดไว้ในสคีมาสาธารณะ
(`eligible`, `verified`, `stale`, `unavailable`, `archived`, `quarantined`) สองสถานะเชิงบวกถูกจงใจกำหนดให้
แคบ:

- `eligible` — โครงสร้างสาธารณะและการเชื่อมต่อ DSH แบบเนทีฟถูกตรวจสอบแล้ว
- `verified` — เพิ่มเติมจากข้างต้น การทดสอบเบื้องต้นของการติดตั้งผ่านสำหรับซอร์สหรือแพ็กเกจที่ตรึงไว้; สคีมา
  กำหนดให้ต้องมีบันทึกการทดสอบเบื้องต้นอยู่จริง

ไม่มีสถานะใด — หรือสถานะอื่นใด — เป็นการรับรอง การรับประกัน หรือใบรับรองด้านความปลอดภัย ความหมายฉบับเต็ม
รวมถึงวิธีที่สถานะเหล่านี้มีปฏิสัมพันธ์กับการจัดอันดับ อยู่ใน [docs/RANKING.md](../../docs/RANKING.md); รูปแบบ
บันทึกอยู่ใน [docs/SCHEMA.md](../../docs/SCHEMA.md)

## การขอเป็นเจ้าของ การแก้ไข และการนำออก

แบบฟอร์ม issue ของ GitHub ที่มีโครงสร้าง (`.github/ISSUE_TEMPLATE/`) คือช่องทางที่ถูกกำกับดูแลสำหรับการเปลี่ยน
รายการที่คุณไม่ได้ส่งเอง:

| แบบฟอร์ม           | ใครใช้                              | ผลลัพธ์                                             |
| -------------- | ----------------------------------------- | --------------------------------------------------- |
| **การขอเป็นเจ้าของ (Claim)**      | ผู้สร้างที่ปลั๊กอินของตนถูกจัดทำโดยผู้อื่น | ความเป็นเจ้าของถูกผูกเข้ากับซอร์สดั้งเดิม; ผู้สร้างสามารถมีส่วนร่วมโดยตรงได้จากนั้น |
| **การแก้ไข (Correction)** | ผู้ที่พบเมทาดาทาสาธารณะที่ไม่ถูกต้อง | การแก้ไขที่ผ่านการรีวิวสำหรับรายการที่ได้รับผลกระทบ             |
| **การนำออก (Removal)**    | ผู้สร้างที่ต้องการให้ถอดรายการของตนออก หรือผู้รายงานการละเมิดนโยบาย | การนำออกหรือกักกันรายการที่ผ่านการรีวิว |

กฎที่ใช้กับทั้งสามกระบวนการ:

- คำขอเรียกร้องความเป็นเจ้าของต้องมีหลักฐานสาธารณะที่ตรวจสอบได้รองรับ (ความเป็นเจ้าของรีโพซิทอรี ความเป็น
  ผู้เขียนแพ็กเกจ เมทาดาทาใน manifest หรือประวัติซอร์สที่ตรึงไว้) — การคอมเมนต์ใน Discussion ไม่ได้สร้างสถานะ
  ความเป็นผู้สร้าง ([docs/CREDIT.md](../../docs/CREDIT.md))
- ปัญหาด้านความปลอดภัยในปลั๊กอินที่อยู่ในรายการจะถูกส่งไปยังผู้ดูแลของปลั๊กอินนั้นก่อน จากนั้นฝั่งแคตตาล็อกจะ
  จัดการการแก้ไขหรือกักกันโดยไม่เผยแพร่รายละเอียดการโจมตี ([SECURITY.md](../../SECURITY.md))
- ห้ามใส่ข้อมูลรับรองตัวตน ข้อมูลติดต่อส่วนตัว หรือความลับอื่นใดในแบบฟอร์มเด็ดขาด

## บทบาท

- **ผู้สร้าง** เป็นเจ้าของปลั๊กอินของตนและลำดับความสำคัญของรายการของตน พวกเขาสามารถมีส่วนร่วมโดยตรง อนุมัติ
  การจัดทำโดยชุมชน หรือขอเป็นเจ้าของ/แก้ไข/นำออกรายการที่มีอยู่ได้
- **ผู้มีส่วนร่วมจากชุมชน** สามารถจัดทำรายการสำหรับผู้สร้างที่ยังไม่ได้มีส่วนร่วมได้ ภายใต้กฎการติดต่ออย่างสุภาพ
  และการให้เครดิตใน [docs/CREDIT.md](../../docs/CREDIT.md) การจัดทำโดยชุมชนไม่เคยมีความสำคัญเหนือกว่าการมี
  ส่วนร่วมโดยตรงของผู้สร้างในภายหลัง
- **ผู้ดูแล** รีวิว ใช้ด่านตรวจแหล่งที่มา แก้ไขการชนกัน และผสาน พวกเขายังดูแลเว็บไซต์
  ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online)) และ CLI ที่เผยแพร่จากซอร์สโค้ด
  ส่วนตัวด้วย; ข้อมูลสาธารณะ สคีมา และนโยบายของรีโพซิทอรีนี้คือสิ่งที่พื้นผิวเหล่านั้นใช้บริโภค
