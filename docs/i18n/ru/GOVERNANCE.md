# Управление каталогом

> **Неофициальный проект сообщества. Не аффилирован с DeepSeek, не одобрен и не спонсируется DeepSeek.**
> Названия и товарные знаки DeepSeek принадлежат их правообладателю.

Как управляется публичный каталог: кто решает, что в него попадает, в каком порядке
учитываются конкурирующие вклады, какие проверки выполняются автоматически, а какие решения
остаются за людьми. Политики, на которые здесь ссылаются, находятся в
[CONTRIBUTING.md](../../CONTRIBUTING.md), [docs/CREDIT.md](../../docs/CREDIT.md) и
[docs/RANKING.md](../../docs/RANKING.md); эта страница описывает, как они сочетаются друг с
другом.

## Принципы

1. **Приоритет создателя.** Каталог существует, чтобы сделать работу создателей доступной для
   обнаружения, а не для того, чтобы отобрать у них право собственности на неё. Для одного и
   того же канонического плагина прямой pull request создателя имеет приоритет над любым
   открытым pull request'ом кураторства сообщества или автоматизации — полный порядок
   приоритета и правила Git-идентичности в [docs/CREDIT.md](../../docs/CREDIT.md).
2. **Один плагин, один рецензируемый pull request.** Никаких пакетных слияний, никаких
   сгенерированных массовых импортов в публичный каталог. Каждая запись заслуживает свою
   собственную рецензию.
3. **Доказательства важнее доверия.** Каждое публичное поле восходит к оригинальному
   репозиторию создателя на закреплённом коммите. Зелёная автоматическая проверка никогда не
   принимается как доказательство происхождения.
4. **Всегда неофициально.** Ни одно состояние каталога не представляется как рецензия,
   сертификация или одобрение со стороны DeepSeek.

## Как изменения попадают в `main`

Все изменения попадают в `main` через рецензируемые pull request'ы — прямых пушей не бывает.
Рабочая политика для ветки по умолчанию:

- **Только pull request'ы.** Записи каталога, документация и изменения схемы — всё это
  попадает через PR; PR каталога должны следовать правилу «один плагин на ветку» из
  [CONTRIBUTING.md](../../CONTRIBUTING.md).
- **Линейная история.** PR интегрируются так, чтобы `main` сохраняла линейную, проверяемую
  историю; слитая публичная история не переписывается. Если курированная запись была слита до
  того, как объявился создатель, создатель заявляет права на неё или исправляет её в
  последующем вкладе, а не через переписывание истории.
- **Разрешение веток обсуждения.** Ветки обсуждения рецензии разрешаются перед слиянием;
  неразрешённые замечания блокируют интеграцию.
- **Слияние мейнтейнером.** Только мейнтейнер сливает запись плагина, и только после того, как
  каждый барьер из [CONTRIBUTING.md](../../CONTRIBUTING.md) → «Барьеры рецензии, коллизии и
  слияние» пройден на текущем коммите PR.

## Проверка `catalog-validation`

Каждый pull request, затрагивающий `catalog/plugins/`, `schemas/` или сам workflow, запускает
задачу `catalog-validation` (`.github/workflows/validate-catalog.yml`), закреплённую на
опубликованном CLI:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**Что она проверяет** — только локальную структуру и семантику:

- Безопасный парсинг YAML каждой записи в `catalog/plugins/`.
- Соответствие публичной схеме (см. [docs/SCHEMA.md](../../docs/SCHEMA.md)).
- Парсинг SPDX-выражений, точные версии SemVer, валидные значения целостности SHA-512 SRI.
- Отклонение дубликатов: без повторяющихся ID записей и без повторяющихся канонических ключей
  node-репозитория-плюс-подпуть.
- Намеренно пустой каталог проходит проверку (`0 entries valid; catalog is empty`).

**Что она НЕ проверяет** — и, следовательно, что зелёная проверка никогда не доказывает:

- Идентичность удалённого репозитория: она не обращается к GitHub и не разрешает node ID
  репозитория относительно URL.
- Доказательства на закреплённом коммите: описания, лицензии, интеграция с DSH и доказательства
  smoke-теста не запрашиваются и не проверяются.
- Владение создателя, число звёзд или коллизию с открытыми pull request'ами.

Эти суждения принадлежат отдельным барьерам происхождения мейнтейнеров, применяемым перед
слиянием и описанным в [CONTRIBUTING.md](../../CONTRIBUTING.md). Локальная проверка — это пол,
а не планка.

## Состояния верификации

Верификация записывается для каждой записи относительно её точного закреплённого коммита, с
использованием состояний, определённых публичной схемой (`eligible`, `verified`, `stale`,
`unavailable`, `archived`, `quarantined`). Два позитивных состояния намеренно узкие:

- `eligible` — публичная структура и нативная интеграция с DSH были провалидированы.
- `verified` — дополнительно пройден smoke-тест установки для закреплённого источника или
  пакета; схема требует наличия записи smoke-теста.

Ни одно состояние — как и любое другое — не является одобрением, гарантией или сертификацией
безопасности. Полная семантика, включая то, как состояния взаимодействуют с ранжированием, — в
[docs/RANKING.md](../../docs/RANKING.md); форма записи — в [docs/SCHEMA.md](../../docs/SCHEMA.md).

## Заявления прав, исправления и удаления

Структурированные формы issue GitHub (`.github/ISSUE_TEMPLATE/`) — это управляемый путь для
изменения записи, которую вы не отправляли сами:

| Форма             | Кто использует                                    | Результат                                                        |
| ----------------- | -------------------------------------------------- | ------------------------------------------------------------------ |
| **Заявление прав** | Создатель, чей плагин был курирован кем-то другим  | Владение привязывается к оригинальному источнику; после этого создатель может вносить вклад напрямую |
| **Исправление**    | Любой, кто заметил неточные публичные метаданные   | Рецензированное исправление затронутой записи                   |
| **Удаление**       | Создатель, желающий удалить свою запись, или тот, кто сообщает о нарушении политики | Рецензированное удаление или карантин записи |

Правила, применяемые ко всем трём потокам:

- Заявления о праве собственности должны подтверждаться проверяемыми публичными
  доказательствами (владение репозиторием, авторство пакета, метаданные манифеста или
  закреплённая история источника) — комментарий в Discussion не устанавливает авторство
  ([docs/CREDIT.md](../../docs/CREDIT.md)).
- Проблемы безопасности в перечисленном плагине сначала направляются собственному мейнтейнеру
  этого плагина; сторона каталога затем обрабатывает исправление или карантин без публикации
  деталей эксплойта ([SECURITY.md](../../SECURITY.md)).
- Никогда не включайте учётные данные, приватные контактные данные или другие секреты в форму.

## Роли

- **Создатели** владеют своими плагинами и приоритетом своих записей. Они могут вносить вклад
  напрямую, одобрять кураторство сообщества или заявлять права/исправлять/удалять существующую
  запись.
- **Участники сообщества** могут курировать записи для создателей, которые ещё не внесли
  вклад, соблюдая правила уважительного контакта и указания авторства из
  [docs/CREDIT.md](../../docs/CREDIT.md). Кураторство никогда не превосходит по приоритету
  последующий прямой вклад создателя.
- **Мейнтейнеры** рецензируют, применяют барьеры происхождения, разрешают коллизии и сливают
  изменения. Они также поддерживают сайт
  ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online)) и опубликованный CLI
  из приватного исходного кода; публичные данные, схема и политики этого репозитория — это
  то, что потребляют эти поверхности.
