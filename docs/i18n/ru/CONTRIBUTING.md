# Внесение вклада

> 🌐 [English](../../../CONTRIBUTING.md) · [Português (Brasil)](../pt-BR/CONTRIBUTING.md) · [中文（简体）](../zh-CN/CONTRIBUTING.md) · **Русский**

> **Неофициальный проект сообщества. Не аффилирован с DeepSeek, не одобрен и не спонсируется DeepSeek.**
> Названия и знаки DeepSeek принадлежат их правообладателю.

Спасибо, что улучшаете каталог. Вклад ориентирован в первую очередь на создателя: используйте
доказательства из оригинального репозитория, сохраняйте указание авторства и делайте каждый плагин
независимо проверяемым. Каталог изначально пуст по замыслу; ни одна запись не принимается без
собственного проверенного pull request.

## Начните с создателя

Pull request, открытый непосредственно создателем плагина или владеющей организацией, всегда
предпочтительнее. Если создатель готов внести вклад, используйте его ветку и pull request вместо
того, чтобы воссоздавать его работу в ветке куратора или автоматизации.

Кураторство сообщества приветствуется, когда оно помогает создателю, который ещё не открыл pull
request. Оно не устанавливает право собственности или приоритет над последующим прямым вкладом
создателя.

## Один плагин на ветку и pull request

Создайте отдельную ветку для одного плагина и откройте один pull request из этой ветки. Ветка и
pull request должны создавать или изменять ровно один YAML-файл в `catalog/plugins/`. Не
смешивайте в этой ветке или pull request разные плагины, чистку документации, сгенерированные
индексы или несвязанное обслуживание.

ID записи и имя файла должны быть одним и тем же значением в нижнем регистре в формате
kebab-case. Мейнтейнеры проверяют и сливают каждый pull request с плагином индивидуально; пакет,
содержащий несколько плагинов, не разделяется и не сливается частично.

## Определите оригинальный источник

Каждое публичное поле должно быть восстановлено из оригинального репозитория, пакета, манифеста,
README, лицензии или релиза создателя на закреплённом коммите. Не копируйте текст, назначение
категории, скриншоты, рейтинг, значки или сгенерированные метаданные из другого каталога или
агрегатора. Ссылка, найденная в зонтичном проекте, маркетплейсе, списке или агрегаторе, — это лишь
наводка, а не доказательство и не источник плагина.

Никогда не отправляйте зонтичный проект, агрегатор, маркетплейс, каталог установщика или список
как запись каталога, даже если он независимо устанавливаем. Используйте его только как наводку и
определяйте фактического создателя и оригинальный репозиторий для каждого независимо
устанавливаемого дочернего плагина. Плагин в настоящем монорепозитории своего создателя можно
отправить из его точного подпути, но он должен соответствовать политике звёзд для монорепозитория
ниже.

## Требуемые доказательства

Предоставьте в pull request всё перечисленное ниже:

- Канонический публичный URL оригинального репозитория и его неизменяемый ID узла репозитория.
  Мейнтейнеры разрешают ID узла и отклоняют несовпадения URL на отдельном барьере проверки
  происхождения.
- Публичный хэндл GitHub создателя и соответствующий публичный URL профиля. YAML хранит хэндл
  один раз; URL профиля выводится как `https://github.com/<handle>`.
- Полный 40-символьный OID исходного коммита и точный подпуть плагина, либо `null` для плагина в
  корне репозитория.
- Ограниченное по длине описание на английском языке и путь к доказательству на этом закреплённом
  коммите.
- `kind` артефакта, основная категория и теги, выбранные из
  [docs/CATEGORIES.md](../../docs/CATEGORIES.md).
- Полное вышестоящее SPDX-выражение лицензии, подтверждённое на закреплённом коммите.
- Канонический дескриптор установки, закреплённый на точной версии npm, либо на исходном
  репозитории, полном коммите и подпути. Дескриптор — это данные, а не команда оболочки.
- Доказательство нативной интеграции с DSH и путь к нему на закреплённом коммите.
- Существующие, не чувствительные доказательства дымового теста для этой точной фиксации
  артефакта, либо явное значение `not run`. Не устанавливайте плагин и не выполняйте
  `preinstall`, `install`, `postinstall`, `prepare` или другой код жизненного цикла
  пакета/плагина только ради подготовки вклада в каталог.
- Для выделенного репозитория — проверяемое количество звёзд именно этого репозитория вместе с
  публичным источником и временем проверки. Для плагина из монорепозитория используйте
  обязательную политику null ниже.
- Происхождение в виде публичной Discussion или комментария, если оно существует; в противном
  случае используйте `null`.
- Машиночитаемое значение `unofficial: true`.

Если подходящего дымового теста ещё не существует, используйте `verification.status: eligible` и
`verification.smokeTest: null`. Используйте `verified` только когда существуют проверяемые
доказательства дымового теста для точной фиксации. Ни одно из состояний не является одобрением
или сертификацией безопасности.

Никогда не отправляйте учётные данные, cookies, приватные email-адреса, неопубликованный
исходный код или другие секреты.

## Правила YAML и схемы

Создайте `catalog/plugins/<plugin-id>.yaml` и провалидируйте его по
[`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml). `id` должен совпадать с
базовым именем файла и должен начинаться с вашего пространства имён: ваш хэндл
`creator.github` в нижнем регистре (любая последовательность символов вне `[a-z0-9]`
превращается в один `-`), за которым следует `-`, например `some-creator-my-plugin` для
хэндла `Some-Creator`. Валидация каталога проверяет оба условия. Схема является источником
истины для имён полей и допустимых значений; [docs/CATEGORIES.md](../../docs/CATEGORIES.md)
определяет, как выбрать единственный вид артефакта, основную категорию, теги и область
репозитория.

Дескриптор npm должен содержать допустимое имя пакета и точную версию. Публичная схема отклоняет
значения, похожие на опции, и неограниченные значения, но не реализует заново SemVer или SRI:
валидация каталога должна разбирать версию, требовать точный SemVer и разбирать любое значение
integrity как допустимый SHA-512 SRI. Дескриптор source привязан к `source.repository`,
`source.commit` и `source.subpath` без дублирования изменяемых значений источника.

Установщики должны использовать массивы аргументов, отключать выполнение через shell и размещать
терминатор опций перед позиционными значениями из каталога там, где это поддерживает вызываемая
команда. Валидация отправки не должна вызывать установщик или жизненный цикл плагина.

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` — это локальная проверка структуры и семантики только для чтения. Она
разбирает безопасный YAML, валидирует публичную схему, разбирает SPDX-выражения, требует точный
SemVer и допустимый SHA-512 SRI, а также отклоняет дублирующиеся ID и канонические ключи
узел-репозитория-плюс-подпуть. Она не обращается к GitHub, не разрешает идентичность репозитория
и не проверяет пути доказательств на закреплённом коммите.

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

Прежде чем запись достигнет статуса `eligible`, мейнтейнеры отдельно разрешают канонический
репозиторий и ID узла, привязывают создателя к оригинальному источнику и проверяют заявленное
описание, лицензию, интеграцию с DSH и доказательства дымового теста на `source.commit`. Зелёный
результат локальной валидации не является доказательством происхождения или источника.

## Звёзды репозитория

Могут быть записаны только звёзды, проверяемо принадлежащие именно выделенному репозиторию
плагина. Звёзды родительского проекта никогда не должны приписываться плагину, хранящемуся внутри
более широкого монорепозитория. Запись из монорепозитория остаётся допустимой для функциональных
разделов каталога, но должна декларировать:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

Выделенная запись использует `repositoryScope: dedicated`, `starsPolicy: exact-repository` и
неотрицательное количество звёзд, наблюдаемое в этом же репозитории. Прочитайте
[docs/RANKING.md](../../docs/RANKING.md), прежде чем отправлять данные о популярности.

## Приоритет создателя и уважительный контакт

Для одного и того же канонического плагина приоритет таков:

1. Pull request, открытый создателем или владеющей организацией.
2. Pull request сообщества, явно одобренный создателем.
3. Существующий действительный pull request кураторства сообщества.
4. Pull request автоматизации каталога.

Прямой pull request создателя заменяет собой любой открытый pull request кураторства или
автоматизации, независимо от того, какой из них был открыт раньше или продвинулся дальше. Pull
request создателя становится средством проверки; мейнтейнеры не делают force-push в ветку
создателя и не переносят его работу в курируемый pull request. Если курируемая запись уже слита,
публичная история не переписывается. Создатель может воспользоваться заявкой на права или
запросом на исправление, а затем внести последующий pull request напрямую.

Курируемый pull request должен использовать одно уважительное публичное упоминание `@creator` в
своём описании, рядом со ссылкой на оригинальный репозиторий, приглашая создателя проверить его
или заменить прямым pull request. Не повторяйте упоминание, не открывайте рекламные issue, не
делайте кросс-постинг, не отправляйте незапрошенные личные сообщения и иным образом не спамьте
создателю.

<!-- creator-first:source-bound-git-identity -->

Pull request'ы и коммиты, авторизованные создателем, естественным образом сохраняют указание
авторства создателя. Курируемые коммиты могут использовать авторство создателя в Git или трейлер
`Co-authored-by` только с привязанной к источнику, публично проверяемой идентичностью. Никогда не
придумывайте и не угадывайте email. Когда проверенная Git-идентичность недоступна, куратор
становится автором коммита и даёт явное указание `Created by @handle` со ссылкой на оригинальный
репозиторий в YAML и pull request. Аккаунт мейнтейнера или автоматизации может быть коммиттером
или проверенным соавтором, но не должен заменять авторство создателя. Полную политику см. в
[docs/CREDIT.md](../../docs/CREDIT.md).

## Команды валидации и доступность

CLI на npm опубликован как `omni-dsh-plugins@1.0.1`, поэтому приведённые ниже команды
уже сегодня доступны через `npx`. Используйте их точно как написано; авторам вклада не следует
придумывать замещающие команды.

Запускайте эти команды из корня репозитория:

```bash
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

`catalog validate` выполняет только локальные проверки YAML, схемы, SPDX, точного SemVer,
SHA-512 SRI и дублей, описанные выше, и допускает намеренно пустой каталог. Она не доказывает
идентичность удалённого репозитория или доказательства закреплённого источника. Остальные
команды проверяют требуемую публичную документацию и структурированные формы issue GitHub.
Успешное локальное прохождение этих команд не ослабляет требования к доказательствам; мейнтейнеры
всё равно применяют каждый соответствующий барьер релиза перед слиянием.

## Барьеры проверки, коллизии и слияние

Прежде чем слить pull request, мейнтейнеры применяют каждый барьер к текущему коммиту pull
request:

1. **Область:** одна выделенная ветка, один YAML-файл плагина и никаких несвязанных изменений.
2. **Оригинальная идентичность:** создатель, канонический репозиторий, ID узла, полный коммит и
   подпуть совпадают.
3. **Схема и доказательства:** YAML, категории, SPDX, фиксация установки, доказательства DSH и
   статус дымового теста внутренне согласованы без выполнения кода жизненного цикла плагина.
4. **Популярность:** выделенные звёзды проверяемы в точном репозитории, либо звёзды
   монорепозитория равны `null` с `undefined-parent-repository`.
5. **Документация и формы:** публичная документация, ограждения Markdown и структурированные
   формы остаются действительными.
6. **Коллизия и дедупликация:** ни одна слитая запись или открытый pull request не представляет
   тот же канонический плагин.

Разные имена или ID не делают дублирующиеся плагины различными. Считайте коллизией один и тот же
ID узла репозитория и подпуть, один и тот же канонический пакет, или другую доказуемо идентичную
цель установки. Разрешайте псевдонимы и конкурирующие pull request'ы до слияния. Прямой pull
request создателя побеждает в коллизии с кураторством или автоматизацией; в противном случае
мейнтейнеры выбирают одно средство проверки и закрывают или перенаправляют дубликаты вместо
слияния обоих.

Только мейнтейнер сливает плагин после прохождения всех барьеров. Каждый принятый плагин
сливается индивидуально; валидация, кураторство или автоматизация не подразумевают
автоматического или пакетного слияния.

## Чек-лист pull request

- [ ] Я использовал одну выделенную ветку, и этот PR изменяет ровно одну запись плагина.
- [ ] Источник — оригинальный репозиторий создателя, а не зонтичный проект или агрегатор.
- [ ] Хэндл/профиль создателя, репозиторий, ID узла, подпуть и полный коммит подтверждены
      доказательствами.
- [ ] Вид, категория и теги соответствуют `docs/CATEGORIES.md`.
- [ ] SPDX-лицензия и закреплённый дескриптор установки подтверждены доказательствами.
- [ ] Нативная интеграция с DSH и результат дымового теста или статус `not run` подтверждены
      доказательствами.
- [ ] Я не выполнял код жизненного цикла плагина или пакета для подготовки этого вклада.
- [ ] Выделенные звёзды проверяемы, либо звёзды монорепозитория используют обязательную политику
      null.
- [ ] Я проверил отсутствие существующей записи и открытого pull request для того же
      канонического плагина.
- [ ] Запись явно помечена как неофициальная и не содержит секретов или приватных персональных
      данных.

## Политика языка

Документация запуска и описания каталога — только на английском. Развёртывание на 43 языках
остаётся элементом бэклога после MVP; не добавляйте пустые документы локализации или
автоматические массовые переводы.
