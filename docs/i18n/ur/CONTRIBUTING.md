# حصہ ڈالنا

> 🌐 [English](../../../CONTRIBUTING.md) · [Português (Brasil)](../pt-BR/CONTRIBUTING.md) · [中文（简体）](../zh-CN/CONTRIBUTING.md) · **اردو**

> **غیر سرکاری کمیونٹی پروجیکٹ۔ DeepSeek سے وابستہ، اس کی توثیق یافتہ یا اس کے زیرِ سرپرستی نہیں ہے۔**
> DeepSeek کے نام اور نشانات ان کے متعلقہ مالک کی ملکیت ہیں۔

کیٹلاگ کو بہتر بنانے کے لیے آپ کا شکریہ۔ شراکتیں تخلیق کار کو ترجیح دینے کے اصول پر مبنی ہیں: اصل ریپوزٹری کا ثبوت استعمال کریں، انتساب برقرار رکھیں اور ہر پلگ ان کو آزادانہ طور پر قابلِ جائزہ رکھیں۔ کیٹلاگ ڈیزائن کے مطابق خالی شروع ہوتا ہے؛ کوئی بھی اندراج اپنے جائزہ شدہ pull request کے بغیر قبول نہیں کیا جاتا۔

## تخلیق کار سے آغاز کریں

پلگ ان کے تخلیق کار یا مالک تنظیم کی طرف سے براہِ راست کھولی گئی pull request ہمیشہ ترجیحی ہوتی ہے۔ اگر تخلیق کار حصہ ڈالنے کے لیے تیار ہے تو ان کی برانچ اور pull request استعمال کریں، بجائے اس کے کہ کیوریٹر یا آٹومیشن برانچ میں ان کا کام دوبارہ تخلیق کیا جائے۔

کمیونٹی کیوریشن کا خیرمقدم ہے جب یہ کسی ایسے تخلیق کار کی مدد کرے جس نے ابھی تک pull request نہیں کھولی۔ یہ کسی بعد کی براہِ راست تخلیق کار کی شراکت پر ملکیت یا فوقیت قائم نہیں کرتی۔

## ایک پلگ ان، ایک برانچ اور ایک pull request

ایک پلگ ان کے لیے مخصوص برانچ بنائیں اور اسی برانچ سے ایک pull request کھولیں۔ برانچ اور pull request کو لازمی طور پر `catalog/plugins/` کے تحت بالکل ایک YAML فائل تخلیق یا تبدیل کرنی چاہیے۔ اس برانچ یا pull request میں پلگ انز، دستاویزات کی صفائی، تیار کردہ اشاریے یا غیر متعلقہ دیکھ بھال کو ملانہ نہ کریں۔

اندراج کا ID اور فائل کا نام ایک ہی lowercase kebab-case قدر ہونا چاہیے۔ مینٹینرز ہر پلگ ان pull request کا انفرادی طور پر جائزہ لیتے اور ضم کرتے ہیں؛ متعدد پلگ انز پر مشتمل بیچ کو تقسیم یا جزوی طور پر ضم نہیں کیا جاتا۔

## اصل ماخذ حل کریں

ہر عوامی فیلڈ کو لازمی طور پر اصل تخلیق کار کی ریپوزٹری، پیکج، مینی فیسٹ، README، لائسنس یا پن شدہ کمٹ پر ریلیز سے دوبارہ تعمیر کیا جانا چاہیے۔ کسی دوسرے کیٹلاگ یا اگریگیٹر کی عبارت، زمرہ بندی، اسکرین شاٹس، درجہ بندی، بیجز یا تیار کردہ میٹا ڈیٹا کاپی نہ کریں۔ کسی umbrella پروجیکٹ، مارکیٹ پلیس، فہرست یا اگریگیٹر میں ملنے والا لنک صرف ایک سراغ ہے، ثبوت نہیں اور نہ ہی پلگ ان کا ماخذ ہے۔

کبھی بھی umbrella، اگریگیٹر، مارکیٹ پلیس، انسٹالر کیٹلاگ یا فہرست کو کیٹلاگ اندراج کے طور پر جمع نہ کروائیں، چاہے وہ خود آزادانہ طور پر انسٹال ہونے کے قابل ہی کیوں نہ ہو۔ اسے صرف ایک سراغ کے طور پر استعمال کریں اور ہر آزادانہ طور پر انسٹال ہونے والے چائلڈ پلگ ان کو اس کے اصل تخلیق کار اور اصل ریپوزٹری تک حل کریں۔ تخلیق کار کے اصل مونوریپو میں موجود پلگ ان اس کے عین subpath سے جمع کروایا جا سکتا ہے، لیکن اسے نیچے دی گئی مونوریپو ستاروں کی پالیسی کی پیروی کرنی ہوگی۔

## درکار ثبوت

pull request میں درج ذیل تمام چیزیں فراہم کریں:

- اصل ریپوزٹری کا معیاری عوامی URL اور اس کا ناقابلِ تبدیل repository node ID۔ مینٹینرز node ID حل کرتے ہیں اور علیحدہ provenance گیٹ میں URL کے عدم مطابقت کو مسترد کرتے ہیں۔
- تخلیق کار کا عوامی GitHub ہینڈل اور اس سے مطابقت رکھنے والا عوامی پروفائل URL۔ YAML ہینڈل کو ایک بار محفوظ کرتا ہے؛ پروفائل URL کو `https://github.com/<handle>` کے طور پر اخذ کیا جاتا ہے۔
- ایک مکمل 40-حرفی سورس کمٹ OID اور عین پلگ ان کا subpath، یا ریپوزٹری-روٹ پلگ ان کے لیے `null`۔
- ایک محدود انگریزی تفصیل اور اس پن شدہ کمٹ پر اس کا evidence path۔
- آرٹیفیکٹ `kind`، بنیادی زمرہ اور [docs/CATEGORIES.md](../../docs/CATEGORIES.md) سے منتخب کردہ ٹیگز۔
- پن شدہ کمٹ پر ثبوت شدہ مکمل اپ اسٹریم SPDX لائسنس اظہار۔
- ایک معیاری انسٹال ڈسکرپٹر جو کسی exact npm ورژن، یا سورس ریپوزٹری، مکمل کمٹ اور subpath پر پن کیا گیا ہو۔ ڈسکرپٹر ڈیٹا ہے، کبھی shell کمانڈ نہیں۔
- نیٹو DSH انٹیگریشن کا ثبوت اور پن شدہ کمٹ پر اس کا راستہ۔
- اس عین artifact pin کے لیے موجودہ، غیر حساس smoke ثبوت، یا واضح قدر `not run`۔ کیٹلاگ شراکت تیار کرنے کے لیے صرف پلگ ان انسٹال یا `preinstall`، `install`، `postinstall`، `prepare` یا دیگر package/plugin lifecycle کوڈ ایگزیکیوٹ نہ کریں۔
- مخصوص ریپوزٹری کے لیے، اس عین ریپوزٹری کی قابلِ تصدیق ستاروں کی تعداد، عوامی ماخذ اور چیک کے وقت کے ساتھ۔ مونوریپو پلگ ان کے لیے، نیچے دی گئی درکار null پالیسی استعمال کریں۔
- عوامی Discussion یا comment provenance جب موجود ہو؛ ورنہ `null` استعمال کریں۔
- machine-readable `unofficial: true` قدر۔

اگر کوئی موزوں smoke test پہلے سے موجود نہیں ہے، تو `verification.status: eligible` اور `verification.smokeTest: null` استعمال کریں۔ `verified` صرف تب استعمال کریں جب عین pin کے لیے قابلِ جائزہ smoke ثبوت موجود ہو۔ کوئی بھی حالت توثیق یا سیکیورٹی سرٹیفیکیشن نہیں ہے۔

کبھی بھی اسناد، کوکیز، نجی ای میل پتے، غیر شائع شدہ سورس یا دیگر خفیہ معلومات جمع نہ کروائیں۔

## YAML اور اسکیما قواعد

`catalog/plugins/<plugin-id>.yaml` تخلیق کریں اور اسے [`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml) کے خلاف توثیق کریں۔ `id` لازمی طور پر فائل کے basename کے برابر ہونا چاہیے اور آپ کے namespace سے شروع ہونا چاہیے: آپ کا `creator.github` ہینڈل lowercase میں (`[a-z0-9]` سے باہر کرداروں کا کوئی بھی سلسلہ ایک واحد `-` بن جاتا ہے) جس کے بعد `-` ہو، مثال کے طور پر ہینڈل `Some-Creator` کے لیے `some-creator-my-plugin`۔ کیٹلاگ توثیق دونوں کو نافذ کرتی ہے۔ فیلڈ ناموں اور اجازت شدہ قدروں کے لیے اسکیما سچائی کا ماخذ ہے؛ [docs/CATEGORIES.md](../../docs/CATEGORIES.md) بیان کرتا ہے کہ واحد artifact kind، بنیادی زمرہ، ٹیگز اور repository scope کیسے منتخب کیے جائیں۔

npm ڈسکرپٹر میں ایک درست پیکج نام اور exact ورژن ہونا چاہیے۔ عوامی اسکیما option-like اور غیر محدود قدروں کو مسترد کرتا ہے مگر SemVer یا SRI کو دوبارہ نافذ نہیں کرتا: کیٹلاگ توثیق کو لازمی طور پر ورژن پارس کرنا چاہیے، exact SemVer درکار کرنا چاہیے، اور کسی بھی integrity قدر کو درست SHA-512 SRI کے طور پر پارس کرنا چاہیے۔ سورس ڈسکرپٹر `source.repository`، `source.commit` اور `source.subpath` سے منسلک ہوتا ہے بغیر متغیر سورس قدروں کو دہرائے۔

انسٹالرز کو لازمی طور پر argument arrays استعمال کرنی چاہئیں، shell ایگزیکیوشن کو غیر فعال کرنا چاہیے اور جہاں مدعو کردہ کمانڈ اسے سپورٹ کرتی ہو وہاں کیٹلاگ فراہم کردہ positional قدروں سے پہلے option terminator رکھنا چاہیے۔ جمع کروائی گئی چیز کی توثیق کو لازمی طور پر کوئی انسٹالر یا پلگ ان lifecycle ایگزیکیوٹ نہیں کرنا چاہیے۔

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` ایک مقامی، صرف پڑھنے کے لیے ساختی اور سیمینٹک چیک ہے۔ یہ محفوظ YAML پارس کرتا ہے، عوامی اسکیما کی توثیق کرتا ہے، SPDX اظہارات پارس کرتا ہے، exact SemVer اور درست SHA-512 SRI درکار کرتا ہے، اور نقل شدہ IDs اور معیاری repository-node-plus-subpath keys کو مسترد کرتا ہے۔ یہ GitHub سے رابطہ نہیں کرتا، ریپوزٹری کی شناخت حل نہیں کرتا یا پن شدہ کمٹ پر ثبوت کا معائنہ نہیں کرتا۔

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

کسی اندراج کے `eligible` ہونے سے پہلے، مینٹینرز الگ سے معیاری ریپوزٹری اور node ID حل کرتے ہیں، تخلیق کار کو اصل ماخذ سے منسلک کرتے ہیں، اور `source.commit` پر بیان کردہ تفصیل، لائسنس، DSH انٹیگریشن اور smoke ثبوت کا معائنہ کرتے ہیں۔ ایک مقامی سبز توثیق کا نتیجہ provenance یا origin کا ثبوت نہیں ہے۔

## ریپوزٹری ستارے

صرف وہ ستارے ریکارڈ کیے جا سکتے ہیں جو قابلِ تصدیق طور پر عین مخصوص پلگ ان ریپوزٹری سے تعلق رکھتے ہوں۔ کسی وسیع تر مونوریپو کے اندر محفوظ پلگ ان کو پیرنٹ پروجیکٹ کے ستارے کبھی منسوب نہیں کیے جانے چاہئیں۔ مونوریپو اندراج فعال کیٹلاگ سیکشنز کے لیے اہل رہتا ہے مگر اسے لازمی طور پر یہ اعلان کرنا چاہیے:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

مخصوص اندراج `repositoryScope: dedicated`، `starsPolicy: exact-repository` اور اسی ریپوزٹری پر مشاہدہ کی گئی غیر منفی ستاروں کی تعداد استعمال کرتا ہے۔ مقبولیت کا ڈیٹا جمع کروانے سے پہلے [docs/RANKING.md](../../docs/RANKING.md) پڑھیں۔

## تخلیق کار کی فوقیت اور باعزت رابطہ

ایک ہی معیاری پلگ ان کے لیے، فوقیت یہ ہے:

1. تخلیق کار یا مالک تنظیم کی طرف سے کھولی گئی pull request۔
2. ایک کمیونٹی pull request جسے تخلیق کار نے واضح طور پر منظور کیا ہو۔
3. ایک موجودہ درست کمیونٹی کیوریشن pull request۔
4. ایک کیٹلاگ آٹومیشن pull request۔

ایک براہِ راست تخلیق کار pull request کسی بھی کھلی کیوریشن یا آٹومیشن pull request پر فوقیت رکھتی ہے، چاہے کوئی بھی پہلے کھولی گئی ہو یا زیادہ آگے بڑھی ہو۔ تخلیق کار کی pull request جائزہ کی گاڑی بن جاتی ہے؛ مینٹینرز تخلیق کار کی برانچ کو force-push یا کیوریٹ شدہ pull request میں منتقل نہیں کرتے۔ اگر ایک کیوریٹ شدہ اندراج پہلے ہی ضم ہو چکی ہے، تو عوامی تاریخ دوبارہ نہیں لکھی جاتی۔ تخلیق کار claim یا correction request استعمال کر سکتا ہے اور پھر براہِ راست ایک فالو اَپ pull request کے ساتھ حصہ ڈال سکتا ہے۔

ایک کیوریٹ شدہ pull request کو اپنی تفصیل میں، اصل ریپوزٹری کے لنک کے ساتھ، ایک باعزت عوامی `@creator` ذکر استعمال کرنا چاہیے، جو تخلیق کار کو اسے دیکھنے یا براہِ راست pull request سے بدلنے کی دعوت دے۔ اس ذکر کو دہرائیں نہیں، پرومیشنل issues نہ کھولیں، cross-post نہ کریں، غیر مطلوبہ براہِ راست پیغامات نہ بھیجیں یا تخلیق کار کو کسی اور طریقے سے spam نہ کریں۔

تخلیق کار کی تصنیف کردہ pull requests اور commits قدرتی طور پر تخلیق کار کا کریڈٹ محفوظ رکھتی ہیں۔ کیوریٹ شدہ commits صرف اس وقت تخلیق کار کی Git شناخت یا `Co-authored-by` trailer استعمال کر سکتی ہیں جب شناخت ماخذ سے منسلک اور عوامی طور پر قابلِ تصدیق ہو۔ کبھی بھی ای میل ایجاد یا اندازہ نہ لگائیں۔ جب کوئی تصدیق شدہ Git شناخت دستیاب نہ ہو، تو کیوریٹر commit کا مصنف بنتا ہے اور YAML اور pull request میں اصل ریپوزٹری لنک کے ساتھ واضح `Created by @handle` کریڈٹ دیتا ہے۔ ایک مینٹینر یا آٹومیشن اکاؤنٹ committer یا تصدیق شدہ co-author ہو سکتا ہے، مگر اسے تخلیق کار کی تصنیف کی جگہ نہیں لینی چاہیے۔ مکمل پالیسی کے لیے [docs/CREDIT.md](../../docs/CREDIT.md) دیکھیں۔

## توثیق کمانڈز اور دستیابی

npm CLI `omni-dsh-plugins@1.0.1` کے طور پر شائع کی گئی ہے، اس لیے نیچے دی گئی کمانڈز آج `npx` کے ذریعے دستیاب ہیں۔ انہیں بالکل اسی طرح استعمال کریں جیسے لکھی گئی ہیں؛ حصہ ڈالنے والوں کو متبادل کمانڈز ایجاد نہیں کرنی چاہئیں۔

یہ کمانڈز ریپوزٹری کی جڑ سے چلائیں:

```bash
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

`catalog validate` صرف اوپر بیان کردہ مقامی YAML، اسکیما، SPDX، exact SemVer، SHA-512 SRI اور نقل چیکس انجام دیتا ہے، اور جان بوجھ کر خالی کیٹلاگ کو قبول کرتا ہے۔ یہ ریموٹ ریپوزٹری کی شناخت یا پن شدہ سورس ثبوت ثابت نہیں کرتا۔ دیگر کمانڈز درکار عوامی دستاویزات اور منظم GitHub issue فارمز چیک کرتی ہیں۔ ان کمانڈز کو مقامی طور پر پاس کرنا ثبوت کی ضروریات میں نرمی نہیں کرتا؛ مینٹینرز ضم کرنے سے پہلے اب بھی ہر متعلقہ ریلیز گیٹ لاگو کرتے ہیں۔

## جائزہ گیٹس، تصادم اور ضم کرنا

مینٹینرز ضم کرنے سے پہلے موجودہ pull request commit پر ہر گیٹ لاگو کرتے ہیں:

1. **دائرہ کار:** ایک مخصوص برانچ، ایک پلگ ان YAML فائل اور کوئی غیر متعلقہ تبدیلی نہیں۔
2. **اصل شناخت:** تخلیق کار، معیاری ریپوزٹری، node ID، مکمل کمٹ اور subpath ہم آہنگ ہیں۔
3. **اسکیما اور ثبوت:** YAML، زمرے، SPDX، انسٹال pin، DSH ثبوت اور smoke حیثیت پلگ ان lifecycle کوڈ ایگزیکیوٹ کیے بغیر اندرونی طور پر مستقل ہیں۔
4. **مقبولیت:** مخصوص ستارے عین ریپوزٹری پر قابلِ تصدیق ہیں، یا مونوریپو ستارے `undefined-parent-repository` کے ساتھ `null` ہیں۔
5. **دستاویزات اور فارمز:** عوامی دستاویزات، Markdown fences اور منظم فارمز درست رہتے ہیں۔
6. **تصادم اور تکرار کا خاتمہ:** کوئی ضم شدہ اندراج یا کھلی pull request ایک ہی معیاری پلگ ان کی نمائندگی نہیں کرتی۔

مختلف نام یا IDs نقل پلگ انز کو الگ نہیں بناتے۔ ایک ہی repository node ID اور subpath، ایک ہی معیاری پیکج، یا کسی دوسرے ثابت شدہ طور پر یکساں انسٹال ٹارگٹ کو تصادم سمجھیں۔ ضم کرنے سے پہلے aliases اور مسابقتی pull requests حل کریں۔ ایک براہِ راست تخلیق کار pull request کیوریشن یا آٹومیشن کے ساتھ تصادم جیتتی ہے؛ ورنہ مینٹینرز ایک جائزہ کی گاڑی منتخب کرتے ہیں اور دونوں کو ضم کرنے کے بجائے نقل کو بند یا ری ڈائریکٹ کرتے ہیں۔

تمام گیٹس پاس ہونے کے بعد صرف ایک مینٹینر پلگ ان ضم کرتا ہے۔ ہر قبول شدہ پلگ ان انفرادی طور پر ضم کیا جاتا ہے؛ توثیق، کیوریشن یا آٹومیشن خودکار یا بیچ ضم کرنے کا مطلب نہیں رکھتی۔

## Pull request چیک لسٹ

- [ ] میں نے ایک مخصوص برانچ استعمال کی اور یہ PR بالکل ایک پلگ ان اندراج تبدیل کرتی ہے۔
- [ ] ماخذ اصل تخلیق کار کی ریپوزٹری ہے، کوئی umbrella یا اگریگیٹر نہیں۔
- [ ] تخلیق کار کا ہینڈل/پروفائل، ریپوزٹری، node ID، subpath اور مکمل کمٹ ثبوت شدہ ہیں۔
- [ ] kind، زمرہ اور ٹیگز `docs/CATEGORIES.md` کی پیروی کرتے ہیں۔
- [ ] SPDX لائسنس اور پن شدہ انسٹال ڈسکرپٹر ثبوت شدہ ہیں۔
- [ ] نیٹو DSH انٹیگریشن اور smoke نتیجہ یا `not run` حیثیت ثبوت شدہ ہیں۔
- [ ] میں نے یہ شراکت تیار کرنے کے لیے پلگ ان یا پیکج lifecycle کوڈ ایگزیکیوٹ نہیں کیا۔
- [ ] مخصوص ستارے قابلِ تصدیق ہیں، یا مونوریپو ستارے درکار null پالیسی استعمال کرتے ہیں۔
- [ ] میں نے ایک ہی معیاری پلگ ان کے لیے موجودہ اندراج اور کھلی pull request چیک کی۔
- [ ] یہ اندراج واضح طور پر غیر سرکاری ہے اور اس میں کوئی خفیہ معلومات یا نجی ذاتی ڈیٹا شامل نہیں ہے۔

## زبان کی پالیسی

لانچ دستاویزات اور کیٹلاگ کی تفصیلات صرف انگریزی میں ہیں۔ 43-لوکیل رول آؤٹ ایک پوسٹ-MVP بیک لاگ آئٹم ہے؛ خالی لوکیل دستاویزات یا خودکار بلک ترجمے شامل نہ کریں۔
