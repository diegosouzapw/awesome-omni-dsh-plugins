# کیٹلاگ گورننس

> 🌐 [English](../../GOVERNANCE.md) · [Português (Brasil)](../pt-BR/GOVERNANCE.md) · [中文（简体）](../zh-CN/GOVERNANCE.md) · **اردو**

> **غیر سرکاری کمیونٹی پروجیکٹ۔ DeepSeek سے وابستہ، اس کی توثیق یافتہ یا اس کے زیرِ سرپرستی نہیں ہے۔**
> DeepSeek کے نام اور نشانات ان کے متعلقہ مالک کی ملکیت ہیں۔

عوامی کیٹلاگ کیسے چلایا جاتا ہے: کون فیصلہ کرتا ہے کہ کیا شامل ہو، مسابقتی شراکتوں کی عزت کس ترتیب میں کی جاتی ہے، کون سے چیکس خودکار طور پر چلتے ہیں، اور کون سے فیصلے انسانی رہتے ہیں۔ یہاں حوالہ دی گئی پالیسیاں [CONTRIBUTING.md](../../CONTRIBUTING.md)، [docs/CREDIT.md](../../docs/CREDIT.md) اور [docs/RANKING.md](../../docs/RANKING.md) میں موجود ہیں؛ یہ صفحہ بیان کرتا ہے کہ وہ کیسے ایک ساتھ فٹ ہوتی ہیں۔

## اصول

1. **تخلیق کار کو ترجیح۔** کیٹلاگ اس لیے موجود ہے کہ تخلیق کاروں کے کام کو قابلِ دریافت بنایا جائے، کبھی اس کی ملکیت لینے کے لیے نہیں۔ ایک ہی معیاری پلگ ان کے لیے، ایک براہِ راست تخلیق کار pull request کسی بھی کھلی کمیونٹی کیوریشن یا آٹومیشن pull request پر فوقیت رکھتی ہے — مکمل فوقیت کی ترتیب اور Git شناخت کے قواعد [docs/CREDIT.md](../../docs/CREDIT.md) میں ہیں۔
2. **ایک پلگ ان، ایک جائزہ شدہ pull request۔** کوئی بیچ ضم نہیں، عوامی کیٹلاگ میں کوئی تیار کردہ بلک امپورٹ نہیں۔ ہر اندراج اپنا الگ جائزہ حاصل کرتا ہے۔
3. **اعتماد پر ثبوت کی فوقیت۔** ہر عوامی فیلڈ کا اصل تخلیق کار کی ریپوزٹری تک، ایک پن شدہ کمٹ پر، سراغ ہوتا ہے۔ ایک سبز خودکار چیک کو کبھی origin کا ثبوت تسلیم نہیں کیا جاتا۔
4. **ہمیشہ غیر سرکاری۔** کوئی بھی کیٹلاگ حالت DeepSeek کے جائزے، سرٹیفیکیشن یا توثیق کے طور پر پیش نہیں کی جاتی۔

## `main` پر تبدیلیاں کیسے پہنچتی ہیں

تمام تبدیلیاں جائزہ شدہ pull requests کے ذریعے `main` تک پہنچتی ہیں — کوئی براہِ راست pushes نہیں ہیں۔ ڈیفالٹ برانچ کے لیے کام کرنے والی پالیسی:

- **صرف Pull requests۔** کیٹلاگ اندراجات، دستاویزات اور اسکیما کی تبدیلیاں سب PR کے ذریعے داخل ہوتی ہیں؛ کیٹلاگ PRs کو [CONTRIBUTING.md](../../CONTRIBUTING.md) میں دیے گئے ایک-پلگ ان-فی-برانچ قاعدے کی پیروی کرنی چاہیے۔
- **لکیری تاریخ۔** PRs کو اس طرح ضم کیا جاتا ہے کہ `main` ایک لکیری، قابلِ آڈٹ تاریخ برقرار رکھے؛ ضم شدہ عوامی تاریخ دوبارہ نہیں لکھی جاتی۔ اگر ایک کیوریٹ شدہ اندراج تخلیق کار کے سامنے آنے سے پہلے ضم ہو گئی، تو تخلیق کار تاریخ کو دوبارہ لکھنے کے بجائے فالو اَپ شراکت میں اس کا دعویٰ یا اصلاح کرتا ہے۔
- **جائزہ thread کا حل۔** ضم کرنے سے پہلے جائزہ گفتگو حل کی جاتی ہے؛ غیر حل شدہ feedback انضمام کو روکتا ہے۔
- **مینٹینر ضم کرنا۔** صرف ایک مینٹینر پلگ ان اندراج ضم کرتا ہے، اور صرف اس وقت جب [CONTRIBUTING.md](../../CONTRIBUTING.md) → "جائزہ گیٹس، تصادم اور ضم کرنا" میں موجود ہر گیٹ موجودہ PR commit پر پاس ہو جائے۔

## `catalog-validation` چیک

`catalog/plugins/`، `schemas/` یا خود workflow کو چھونے والی ہر pull request `catalog-validation` job (`.github/workflows/validate-catalog.yml`) چلاتی ہے، جو شائع شدہ CLI پر pin کی گئی ہے:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**یہ کیا توثیق کرتا ہے** — صرف مقامی ساخت اور سیمینٹکس:

- `catalog/plugins/` کے تحت ہر اندراج کی محفوظ YAML پارسنگ۔
- عوامی اسکیما کے ساتھ مطابقت (دیکھیں [docs/SCHEMA.md](../../docs/SCHEMA.md))۔
- SPDX اظہار پارسنگ، exact SemVer ورژنز، درست SHA-512 SRI integrity قدریں۔
- نقل مسترد کرنا: کوئی دہرائی گئی اندراج ID نہیں اور کوئی دہرائی گئی معیاری repository-node-plus-subpath keys نہیں۔
- جان بوجھ کر خالی کیٹلاگ پاس ہوتا ہے (`0 entries valid; catalog is empty`)۔

**یہ کیا توثیق نہیں کرتا** — اور اس لیے ایک سبز چیک کبھی کیا ثابت نہیں کرتا:

- ریموٹ ریپوزٹری کی شناخت: یہ GitHub سے رابطہ نہیں کرتا یا URL کے خلاف repository node ID حل نہیں کرتا۔
- پن شدہ کمٹ پر ثبوت: تفصیلات، لائسنسز، DSH انٹیگریشن اور smoke ثبوت حاصل یا معائنہ نہیں کیے جاتے۔
- تخلیق کار کی ملکیت، ستاروں کی تعداد، یا کھلی pull requests کے ساتھ تصادم۔

وہ فیصلے مینٹینرز کے علیحدہ provenance گیٹس سے تعلق رکھتے ہیں، جو ضم کرنے سے پہلے لاگو ہوتے ہیں اور [CONTRIBUTING.md](../../CONTRIBUTING.md) میں بیان کیے گئے ہیں۔ مقامی چیک فرش ہے، معیار نہیں۔

## توثیق کی حالتیں

توثیق ہر اندراج کے لیے اس کے عین پن شدہ کمٹ کے خلاف ریکارڈ کی جاتی ہے، عوامی اسکیما میں بیان کردہ حالتیں استعمال کرتے ہوئے (`eligible`، `verified`، `stale`، `unavailable`، `archived`، `quarantined`)۔ دو مثبت حالتیں جان بوجھ کر تنگ ہیں:

- `eligible` — عوامی ساخت اور نیٹو DSH انٹیگریشن کی توثیق کی گئی۔
- `verified` — اضافی طور پر، پن شدہ سورس یا پیکج کے لیے ایک انسٹالیشن smoke test پاس ہوا؛ اسکیما کو smoke-test ریکارڈ کی موجودگی درکار ہے۔

کوئی بھی حالت — یا کوئی اور — توثیق، ضمانت یا سیکیورٹی سرٹیفیکیشن نہیں ہے۔ مکمل معنی، بشمول یہ حالتیں درجہ بندی کے ساتھ کیسے تعامل کرتی ہیں، [docs/RANKING.md](../../docs/RANKING.md) میں ہیں؛ ریکارڈ کی شکل [docs/SCHEMA.md](../../docs/SCHEMA.md) میں ہے۔

## دعوے، اصلاحات اور ہٹانا

منظم GitHub issue فارمز (`.github/ISSUE_TEMPLATE/`) کسی ایسے اندراج کو تبدیل کرنے کا زیرِ نگرانی راستہ ہیں جو آپ نے جمع نہیں کروایا:

| فارم           | کون استعمال کرتا ہے                              | نتیجہ                                             |
| -------------- | ---------------------------------------- | --------------------------------------------------- |
| **دعویٰ**      | ایک تخلیق کار جس کا پلگ ان کسی اور نے کیوریٹ کیا | ملکیت اصل ماخذ سے منسلک کی جاتی ہے؛ تخلیق کار پھر براہِ راست حصہ ڈال سکتا ہے |
| **اصلاح** | کوئی بھی جسے غلط عوامی میٹا ڈیٹا نظر آئے | متاثرہ اندراج کی جائزہ شدہ اصلاح             |
| **ہٹانا**    | ایک تخلیق کار جو اپنی فہرست ہٹانا چاہتا ہے، یا پالیسی خلاف ورزی کا رپورٹر | اندراج کا جائزہ شدہ ہٹانا یا قرنطینہ |

تمام تینوں flows پر لاگو ہونے والے قواعد:

- ملکیت کے دعووں کو قابلِ تصدیق عوامی ثبوت (ریپوزٹری کی ملکیت، پیکج کی تصنیف، مینی فیسٹ میٹا ڈیٹا یا پن شدہ سورس تاریخ) کی حمایت حاصل ہونی چاہیے — کسی Discussion پر comment کرنا تخلیق کار ہونا ثابت نہیں کرتا ([docs/CREDIT.md](../../docs/CREDIT.md))۔
- فہرست شدہ پلگ ان میں سیکیورٹی مسائل پہلے اس پلگ ان کے اپنے مینٹینر کو جاتے ہیں؛ کیٹلاگ کا پہلو پھر exploit تفصیل شائع کیے بغیر اصلاح یا قرنطینہ سنبھالتا ہے ([SECURITY.md](../../SECURITY.md))۔
- کسی فارم میں کبھی بھی اسناد، نجی رابطے کی تفصیلات یا دیگر خفیہ معلومات شامل نہ کریں۔

## کردار

- **تخلیق کار** اپنے پلگ انز اور ان کی فہرستوں کی فوقیت کے مالک ہیں۔ وہ براہِ راست حصہ ڈال سکتے ہیں، کمیونٹی کیوریشن کی منظوری دے سکتے ہیں، یا کسی موجودہ اندراج کا دعویٰ/اصلاح/ہٹانا کر سکتے ہیں۔
- **کمیونٹی حصہ ڈالنے والے** ایسے تخلیق کاروں کے لیے اندراجات کیوریٹ کر سکتے ہیں جنہوں نے ابھی تک حصہ نہیں ڈالا، [docs/CREDIT.md](../../docs/CREDIT.md) میں دیے گئے باعزت رابطے اور کریڈٹ قواعد کے تحت۔ کیوریشن کبھی بعد کی براہِ راست تخلیق کار شراکت پر فوقیت نہیں رکھتی۔
- **مینٹینرز** جائزہ لیتے ہیں، provenance گیٹس لاگو کرتے ہیں، تصادم حل کرتے ہیں اور ضم کرتے ہیں۔ وہ ویب سائٹ ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online)) اور شائع شدہ CLI کو بھی نجی ماخذ سے برقرار رکھتے ہیں؛ اس ریپوزٹری کا عوامی ڈیٹا، اسکیما اور پالیسیاں وہی ہیں جو یہ surfaces استعمال کرتے ہیں۔
