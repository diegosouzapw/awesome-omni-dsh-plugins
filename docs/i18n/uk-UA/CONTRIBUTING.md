# Як зробити внесок

> 🌐 [English](../../CONTRIBUTING.md) · **Українська**

> **Неофіційний проєкт спільноти. Не пов'язаний із DeepSeek, не схвалений і не спонсорований компанією DeepSeek.**
> Назви та товарні знаки DeepSeek належать їхньому власнику.

Дякуємо, що покращуєте каталог. Внески мають пріоритет автора: використовуйте докази з
оригінального репозиторію, зберігайте вказівку авторства та робіть кожен плагін незалежно
перевірюваним. Каталог задумано порожнім на старті; жоден запис не приймається без власного
перевіреного pull request.

## Почніть з автора

Pull request, відкритий безпосередньо автором плагіна або організацією-власником, завжди
переважний. Якщо автор готовий зробити внесок, використовуйте його гілку та його pull request
замість того, щоб відтворювати його роботу в гілці куратора чи автоматизації.

Кураторство спільноти вітається, коли воно допомагає авторові, який ще не відкривав pull request.
Воно не встановлює власності чи пріоритету над пізнішим прямим внеском автора.

## Один плагін на гілку і на pull request

Створіть окрему гілку для одного плагіна і відкрийте один pull request із цієї гілки. Гілка та
pull request мають створювати або змінювати рівно один YAML-файл у `catalog/plugins/`. Не
змішуйте в цій гілці чи в цьому pull request кілька плагінів, упорядкування документації,
згенеровані індекси чи стороннє обслуговування.

ID запису та ім'я файлу мають бути одним і тим самим значенням у kebab-case малими літерами.
Мейнтейнери розглядають і зливають кожен pull request плагіна окремо; пакет із кількома
плагінами не розбивається і не зливається частково.

## Визначте оригінальне джерело

Кожне публічне поле має бути відтворено з оригінального репозиторію автора, пакета, маніфесту,
README, ліцензії чи релізу на закріпленому коміті. Не копіюйте прозу, призначення категорій,
скриншоти, рейтинги, бейджі чи згенеровані метадані іншого каталогу або агрегатора. Посилання,
знайдене в парасольковому проєкті, маркетплейсі, списку чи агрегаторі, — це лише наводка, а не
доказ і не джерело плагіна.

Ніколи не подавайте парасольковий проєкт, агрегатор, маркетплейс, каталог-інсталятор або список як
запис каталогу, навіть якщо він сам встановлюється незалежно. Використовуйте його лише як наводку
і визначте для кожного незалежно встановлюваного дочірнього плагіна його справжнього автора та
оригінальний репозиторій. Плагін у справжньому монорепозиторії автора можна подати з його точного
субшляху, але він має дотримуватися наведеної нижче політики зірок для монорепозиторіїв.

## Необхідні докази

Надайте у pull request усе перелічене:

- Канонічну публічну URL оригінального репозиторію та його незмінний вузловий ID репозиторію.
  Мейнтейнери розв'язують вузловий ID і відхиляють невідповідності URL в окремій перевірці
  походження.
- Публічний GitHub-хендл автора та відповідну публічну URL профілю. YAML зберігає хендл один раз;
  URL профілю виводиться як `https://github.com/<handle>`.
- Повний 40-символьний OID коміта джерела та точний субшлях плагіна, або `null` для плагіна в
  корені репозиторію.
- Обмежений опис англійською та шлях до його доказу на тому закріпленому коміті.
- `kind` артефакту, основну категорію та теги, вибрані з
  [docs/CATEGORIES.md](../../docs/CATEGORIES.md).
- Повний вираз ліцензії SPDX з висхідного джерела, підтверджений на закріпленому коміті.
- Канонічний інсталяційний дескриптор, закріплений на точній версії npm, або на репозиторії
  джерела, повному коміті та субшляху. Дескриптор — це дані, а не команда shell.
- Доказ нативної інтеграції з DSH та його шлях на закріпленому коміті.
- Наявний, нечутливий доказ smoke-тесту для саме того закріплення артефакту, або явне значення
  `not run`. Не встановлюйте плагін і не виконуйте код `preinstall`, `install`, `postinstall`,
  `prepare` чи інший код життєвого циклу пакета/плагіна лише для підготовки внеску до каталогу.
- Для виділеного репозиторію — перевірювану кількість зірок саме цього репозиторію разом із
  публічним джерелом і часом перевірки. Для плагіна з монорепозиторію використовуйте обов'язкову
  нульову політику нижче.
- Походження з публічного Discussion або коментаря, якщо воно існує; інакше використовуйте `null`.
- Машиночитне значення `unofficial: true`.

Якщо відповідного smoke-тесту ще не існує, використовуйте `verification.status: eligible` і
`verification.smokeTest: null`. Використовуйте `verified` лише тоді, коли існує перевірюваний
доказ smoke-тесту для точного закріплення. Жоден зі статусів не є схваленням або сертифікацією
безпеки.

Ніколи не надсилайте облікові дані, куки, приватні адреси електронної пошти, неопубліковані
вихідні коди чи інші секрети.

## Правила YAML і схеми

Створіть `catalog/plugins/<plugin-id>.yaml` і перевірте його за
[`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml). `id` має дорівнювати базовій
назві файлу й починатися з вашого простору імен: ваш хендл `creator.github` малими літерами
(будь-яка послідовність символів поза `[a-z0-9]` стає одним `-`) із наступним `-`, наприклад
`some-creator-my-plugin` для хендла `Some-Creator`. Валідація каталогу забезпечує обидві вимоги.
Схема є джерелом істини для назв полів і допустимих значень;
[docs/CATEGORIES.md](../../docs/CATEGORIES.md) визначає, як вибрати єдиний `kind` артефакту,
основну категорію, теги та область репозиторію.

npm-дескриптор має містити коректну назву пакета та точну версію. Публічна схема відхиляє
опцієподібні та необмежені значення, але не реалізує повторно SemVer чи SRI: валідація каталогу
має розпарсити версію, вимагати точний SemVer і розпарсити будь-яке значення цілісності як
коректний SHA-512 SRI. Дескриптор джерела прив'язаний до `source.repository`, `source.commit` і
`source.subpath` без дублювання змінних значень джерела.

Інсталятори мають використовувати масиви аргументів, вимикати виконання в shell і ставити
термінатор опцій перед наданими каталогом позиційними значеннями там, де викликана команда це
підтримує. Перевірка подання не повинна викликати інсталятор чи життєвий цикл плагіна.

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` — це локальна, призначена лише для читання структурна та семантична перевірка.
Вона парсить безпечний YAML, перевіряє публічну схему, парсить вирази SPDX, вимагає точний SemVer
і коректний SHA-512 SRI та відхиляє дублікати ID і канонічних ключів
«вузол репозиторію + субшлях». Вона не звертається до GitHub, не розв'язує ідентичність
репозиторію та не інспектує шляхи доказів на закріпленому коміті.

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

Перш ніж запис досягне `eligible`, мейнтейнери окремо розв'язують канонічний репозиторій і вузловий
ID, прив'язують автора до оригінального джерела та інспектують заявлений опис, ліцензію,
інтеграцію з DSH і доказ smoke-тесту на `source.commit`. Зелений результат локальної перевірки не
є доказом походження чи джерела.

## Зірки репозиторію

Записувати можна лише зірки, які перевірено належать саме виділеному репозиторію плагіна. Зірки
батьківського проєкту ніколи не можна приписувати плагіну, що зберігається в ширшому
монорепозиторії. Запис із монорепозиторію залишається прийнятним для функціональних розділів
каталогу, але має декларувати:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

Виділений запис використовує `repositoryScope: dedicated`, `starsPolicy: exact-repository` і
невід'ємну кількість зірок, спостережену на тому самому репозиторії. Прочитайте
[docs/RANKING.md](../../docs/RANKING.md), перш ніж подавати дані про популярність.

## Пріоритет автора і поважний контакт

Для того самого канонічного плагіна пріоритет такий:

1. Pull request, відкритий автором або організацією-власником.
2. Громадський pull request, явно схвалений автором.
3. Наявний чинний громадський кураторський pull request.
4. Pull request автоматизації каталогу.

Прямий pull request автора має пріоритет над будь-яким відкритим кураторським чи автоматизованим
pull request, незалежно від того, який відкрито раніше або який просунувся далі. Pull request
автора стає засобом рев'ю; мейнтейнери не роблять force-push у гілку автора і не переносять його
роботу в кураторський pull request. Якщо кураторський запис уже злито, публічну історію не
переписують. Автор може скористатися запитом на заявлення прав чи виправлення, а потім зробити
внесок безпосередньо наступним pull request.

Кураторський pull request має використовувати одну поважну публічну згадку `@автора` в описі,
поруч із посиланням на оригінальний репозиторій, запрошуючи автора переглянути його або замінити
прямим pull request. Не повторюйте згадку, не відкривайте промоційні issue, не робіть кроспостів,
не надсилайте небажаних прямих повідомлень і не спамте автора в будь-який інший спосіб.

<!-- creator-first:source-bound-git-identity -->

Pull request і коміти, створені автором, природно зберігають авторську вказівку. Кураторські
коміти можуть використовувати авторство автора в Git або трейлер `Co-authored-by` лише з
прив'язаною до джерела, публічно перевірюваною ідентичністю. Ніколи не вигадуйте і не вгадуйте
адресу електронної пошти. Якщо перевіреної ідентичності в Git немає, куратор є автором коміта і
надає явну вказівку `Created by @handle` із посиланням на оригінальний репозиторій у YAML та в
pull request. Обліковий запис мейнтейнера чи автоматизації може бути комітером або перевіреним
співавтором, але не повинен замінювати авторство автора. Повна політика — у
[docs/CREDIT.md](../../docs/CREDIT.md).

## Команди валідації та доступність

npm CLI опубліковано як `omni-dsh-plugins@1.0.1`, тож наведені нижче команди сьогодні доступні
через `npx`. Використовуйте їх саме так, як написано; учасникам не слід вигадувати команди-замінники.

Виконайте ці команди з кореня репозиторію:

```bash
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

`catalog validate` виконує лише описані вище локальні перевірки YAML, схеми, SPDX, точного SemVer,
SHA-512 SRI і дублікатів та приймає навмисно порожній каталог. Вона не доводить віддалену
ідентичність репозиторію чи докази закріпленого джерела. Інші команди перевіряють обов'язкову
публічну документацію та структуровані форми issue на GitHub. Локальне проходження цих команд не
послаблює вимог до доказів; мейнтейнери й надалі застосовують усі відповідні перевіркові шлюзи
перед злиттям.

## Перевіркові шлюзи, колізії та злиття

Перед злиттям мейнтейнери застосовують до поточного коміта pull request усі шлюзи:

1. **Обсяг:** одна окрема гілка, один YAML-файл плагіна і жодних сторонніх змін.
2. **Оригінальна ідентичність:** автор, канонічний репозиторій, вузловий ID, повний коміт і
   субшлях збігаються.
3. **Схема та докази:** YAML, категорії, SPDX, закріплення встановлення, докази DSH і статус
   smoke внутрішньо узгоджені без виконання коду життєвого циклу плагіна.
4. **Популярність:** виділені зірки перевірювані на точному репозиторії, або зірки
   монорепозиторію дорівнюють `null` з `undefined-parent-repository`.
5. **Документація та форми:** публічна документація, Markdown-огорожі та структуровані форми
   залишаються чинними.
6. **Колізії та дедуплікація:** жоден злитий запис чи відкритий pull request не представляє той
   самий канонічний плагін.

Різні назви чи ID не роблять дублікати плагінів різними. Трактуйте той самий вузловий ID
репозиторію і субшлях, той самий канонічний пакет або інший доведено ідентичний цільовий об'єкт
встановлення як колізію. Розв'яжіть альтернативні назви та конкурентні pull request перед
злиттям. Прямий pull request автора виграє колізію з кураторством чи автоматизацією; інакше
мейнтейнери обирають один засіб рев'ю та закривають чи переспрямовують дублікати, а не зливають
обидва.

Лише мейнтейнер зливає плагін після проходження всіх шлюзів. Кожен прийнятий плагін зливається
окремо; валідація, кураторство чи автоматизація не означають автоматичного чи пакетного злиття.

## Чекліст pull request

- [ ] Я використав одну окрему гілку, і цей PR змінює рівно один запис плагіна.
- [ ] Джерело — оригінальний репозиторій автора, а не парасольковий проєкт чи агрегатор.
- [ ] Хендл/профіль автора, репозиторій, вузловий ID, субшлях і повний коміт підтверджені.
- [ ] `kind`, категорія та теги відповідають `docs/CATEGORIES.md`.
- [ ] Ліцензію SPDX і закріплений інсталяційний дескриптор підтверджено.
- [ ] Нативну інтеграцію з DSH і результат smoke або статус `not run` підтверджено.
- [ ] Я не виконував код життєвого циклу плагіна чи пакета для підготовки цього внеску.
- [ ] Виділені зірки перевірювані, або зірки монорепозиторію використовують обов'язкову нульову
      політику.
- [ ] Я перевірив наявність чинного запису та відкритого pull request для того самого канонічного
      плагіна.
- [ ] Запис явно позначено як неофіційний, і він не містить секретів чи приватних особистих даних.
