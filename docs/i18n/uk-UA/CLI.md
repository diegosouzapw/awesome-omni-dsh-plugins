# Довідник CLI — `omni-dsh-plugins@1.0.1`

> 🌐 [English](../../docs/CLI.md) · **Українська**

> **Неофіційний проєкт спільноти. Не пов'язаний із DeepSeek, не схвалений і не спонсорований компанією DeepSeek.**
> Назви та товарні знаки DeepSeek належать їхньому власнику.

Ця сторінка документує опублікований CLI саме так, як він поводиться у версії `1.0.1`. Кожен
синопсис і прапорець нижче взято з власного виводу `--help` опублікованої команди; ніщо тут не
описує неопубліковану поведінку. CLI розробляється в цьому репозиторії, у [`cli/`](../../cli), і
випускається на npm як [`omni-dsh-plugins`](https://www.npmjs.com/package/omni-dsh-plugins), із
посвідченням походження, що прив'язує кожну збірку до коміта та запуску workflow, які її створили.

```bash
npx omni-dsh-plugins --help
```

## Принципи дизайну у v1.0.1

- **Типово лише для читання.** `catalog`, `search`, `info`, `list` і `doctor` ніколи не змінюють
  профілі, не записують файли та не запускають код плагінів.
- **Шлюз згоди на виконання коду.** `add`, `update` і `remove` відмовляються виконувати код
  життєвого циклу DSH/pnpm, якщо не передано `--allow-code-execution`. Без нього скористайтеся
  `--dry-run`, щоб побачити перевірений план.
- **Політика нативного Windows.** Змінювальні `add`/`update`/`remove` з виконанням коду на
  нативному Windows вимкнено у v1.0.1; використовуйте WSL. Тестовий прогін і команди лише для
  читання залишаються доступними, а маркери відновлення на нативному Windows потребують
  документованого відновлення вручну.
- **Закріплені вхідні дані.** Вхідний каталог може бути локальним каталогом, файлом знімка або
  закріпленою публічною URL знімка, за потреби замкненою на точну 40-символьну ревізію.

## Спільні опції

Ці опції присутні в командах, що споживають каталог (`catalog validate`, `search`, `info`,
`add`, `update`, `remove`, `doctor`):

| Опція                     | Значення                                                            |
| ------------------------- | ------------------------------------------------------------------ |
| `--catalog <path-or-url>` | Локальний каталог, файл знімка або закріплена публічна URL знімка |
| `--revision <sha>`        | Точна 40-символьна ревізія знімка                               |
| `--json`                  | Видає стабільний вивід у JSON                                            |

Глобальні опції: `-V, --version` виводить версію CLI; `-h, --help` виводить довідку для будь-якої
команди (`dsh-plugins help [command]` теж працює).

## Коди завершення

CLI використовує звичайні коди завершення процесу:

| Код завершення | Значення                                                                    |
| --------: | -------------------------------------------------------------------------- |
| `0`       | Успіх (включно з «порожніми, але коректними» результатами, як-от порожній каталог)     |
| `1`       | Помилка: помилка валідації, запис не знайдено, відсутня обов'язкова опція, або діагностична перевірка повідомляє про помилку |

Приклади, спостережувані у v1.0.1: `catalog validate` на коректному порожньому каталозі
завершується з `0` і `0 entries valid; catalog is empty`; `info <невідомий-id>` завершується з
`1` і `Plugin not found`; `doctor` завершується з `1`, коли будь-яка перевірка (наприклад,
відсутній виконуваний файл `dsh`) повідомляє про помилку.

## Команди

### `catalog` — перевірка публічних поверхонь каталогу

```text
dsh-plugins catalog validate [--catalog <path-or-url>] [--revision <sha>] [--json]
dsh-plugins catalog docs-check [root]
dsh-plugins catalog github-forms-check [root]
```

- **`catalog validate`** — перевіряє YAML і семантику каталогу: безпечний парсинг YAML, публічна
  схема, парсинг виразів SPDX, точний SemVer, SHA-512 SRI та відхилення дублікатів ID /
  ключів «вузол репозиторію + субшлях». Вона локальна і лише для читання: не звертається до
  GitHub, не розв'язує ідентичність репозиторію та не інспектує докази на закріпленому коміті.
  Це саме та команда, яку запускає завдання CI `catalog-validation` для кожного pull request
  каталогу.
- **`catalog docs-check [root]`** — перевіряє, що обов'язкова публічна документація каталогу
  існує і що Markdown-огорожі збалансовані.
- **`catalog github-forms-check [root]`** — перевіряє структуровані публічні форми issue на
  GitHub (заявлення прав, виправлення, видалення).

```bash
# З кореня репозиторію:
npx omni-dsh-plugins catalog validate --catalog .
npx omni-dsh-plugins catalog docs-check .
npx omni-dsh-plugins catalog github-forms-check .
```

### `search` — локальний пошук за публічними полями каталогу

```text
dsh-plugins search [options] <query...>
```

Локально шукає за публічними полями каталогу відносно вибраного вхідного каталогу. Виводить
знайдені записи або `No plugins found.` (завершення `0`), якщо нічого не знайдено.

```bash
npx omni-dsh-plugins search memory --catalog .
npx omni-dsh-plugins search notes markdown --catalog . --json
```

### `discover` — пошук плагінів за межами каталогу

```text
dsh-plugins discover [options] <query...>
```

> `discover` постачається в `1.0.0` — першому випуску під цією назвою пакета.

Спершу шукає в кураторському каталозі, потім — якщо не вказано `--offline` — у живій темі
GitHub `dsh-plugin`, тож плагін, який ще не подано, все одно можна знайти. Результати з каталогу
несуть докази, які має каталог (закріплений коміт, автор, ліцензія); результати спільноти не
несуть жодних і позначені відповідно, бо ніщо з них не перевірялося.

`--limit <n>` обмежує кількість результатів на рівень (типово `8`). `--json` видає стабільну
машиночитну форму, яка ніколи не локалізується.

```bash
npx omni-dsh-plugins discover memory --catalog .
npx omni-dsh-plugins discover vision --offline --catalog . --json
```

### `info` — показ одного публічного запису каталогу

```text
dsh-plugins info [options] <id>
```

Показує один публічний запис каталогу за канонічним ID плагіна. Завершується з `1` і
`Plugin not found: <id>`, якщо ID відсутній у каталозі.

```bash
npx omni-dsh-plugins info example-notes-search --catalog .
```

### `add` — додавання одного плагіна каталогу через офіційне делегування DSH

```text
dsh-plugins add [options] <id>
```

| Опція                    | Значення                                                            |
| ------------------------ | ------------------------------------------------------------------ |
| `--profile <name>`       | Профіль DSH для зміни (на практиці обов'язковий; команда помиляється без нього) |
| `--dry-run`              | Показує перевірений план без файлів і підпроцесів               |
| `--allow-code-execution` | Згода на код життєвого циклу DSH/pnpm (на нативному Windows вимкнено; використовуйте WSL) |
| `--catalog` / `--revision` / `--json` | Спільні опції вище                                  |

Семантика тестового прогону в цій версії: команда розв'язує та перевіряє план для закріпленого
запису і виводить його, не створюючи файлів і не запускаючи підпроцесів. Фактичне встановлення
делегується офіційним інструментам DSH і відбувається лише з `--allow-code-execution`.

```bash
# Лише перегляд — нічого не записується, нічого не виконується:
npx omni-dsh-plugins add example-notes-search --profile default --dry-run

# Справжнє встановлення — явна згода на код життєвого циклу:
npx omni-dsh-plugins add example-notes-search --profile default --allow-code-execution
```

### `update` — оновлення одного плагіна каталогу через офіційне делегування DSH

```text
dsh-plugins update [options] <id>
```

Ті самі опції та семантика згоди, що й у `add`: `--profile <name>`, `--dry-run`,
`--allow-code-execution`, плюс спільні опції каталогу.

### `remove` — видалення одного плагіна, керованого каталогом, через офіційне делегування DSH

```text
dsh-plugins remove [options] <id>
```

Ті самі опції та семантика згоди, що й у `add`. Видаляються лише встановлення, керовані
каталогом.

### `recover` — відновлення збереженої POSIX-мутації

```text
dsh-plugins recover
```

Відновлює збережену POSIX-мутацію після перерваного `add`/`update`/`remove`. Якщо нічого не
очікує на відновлення, виводить `No mutation recovery is pending.` і завершується з `0`.
Відновлення на нативному Windows залишається ручним, відповідно до документованої політики.

### `list` — перелік встановлень, керованих каталогом

```text
dsh-plugins list [--profile <name>] [--json]
```

Показує встановлення, керовані каталогом, не змінюючи профілів. `--profile <name>` фільтрує за
профілем DSH. Якщо встановлень немає, виводить `No catalog-managed plugins installed.` і
завершується з `0`.

### `doctor` — діагностика лише для читання

```text
dsh-plugins doctor [--catalog <path-or-url>] [--revision <sha>] [--json]
```

Виконує діагностику лише для читання щодо Node, DSH, політики нативного Windows і каталогу.
Кожна перевірка повідомляє `ok` або `error`; будь-який `error` робить загальний код завершення
`1`. Приклад виводу на машині без виконуваного файла `dsh`:

```text
node [ok]: Node 24.16.0 is supported
dsh [error]: dsh executable was not found
catalog [ok]: catalog is valid and empty
```

## Чого не доводить локальна перевірка

Зелений запуск `catalog validate` підтверджує лише структуру та локальну семантику. Він не
доводить віддалену ідентичність репозиторію, власність автора чи докази на закріпленому коміті —
мейнтейнери застосовують ці окремі перевірки походження перед будь-яким злиттям, як описано в
[CONTRIBUTING.md](../../CONTRIBUTING.md) і [docs/GOVERNANCE.md](../../docs/GOVERNANCE.md).
