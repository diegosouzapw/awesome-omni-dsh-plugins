# Категорії каталогу

> 🌐 [English](../../docs/CATEGORIES.md) · **Українська**

Кожен запис каталогу має один `kind` артефакту, одну основну категорію можливостей і нуль або
більше тегів. Основна категорія визначає, де з'являється запис; теги забезпечують пошук між
категоріями без дублювання запису.

## Види артефактів

<!-- catalog-policy:aggregators-never-entries -->

| Значення | Зміст | Ранжується за зірками як плагін |
|---|---|---:|
| `plugin` | Встановлюваний нативний пакет DSH | Лише коли виконано всі умови ранжування |
| `plugin-family` | Репозиторій, що містить кілька плагінів DSH | Ні; окремий розділ |
| `skin-theme` | Скін інтерфейсу DSH або візуальна тема | Ні; окремий розділ |
| `skill` | Навичка агента з підтримкою DSH | Ні |
| `preset-profile` | Профіль або пресет DSH | Ні |
| `client-interface` | Десктопний, TUI-, редакторський або віддалений клієнт | Ні |
| `bridge-adapter` | Інтеграція іншого продукту в DSH | Ні |
| `ecosystem-project` | Ширший проєкт, що містить інтеграцію з DSH | Ні |

Парасольковий репозиторій, агрегатор, маркетплейс, каталог-інсталятор або список ніколи не є
записом каталогу, навіть коли сам агрегатор встановлюваний. Його можна використовувати лише як
наводку. Пройдіть за кожною наводкою до незалежно встановлюваного дочірнього артефакту та
визначте справжнього автора, оригінальний репозиторій, пакет і субшлях джерела цього артефакту,
перш ніж подавати його. Справжній монорепозиторій автора може бути оригінальним репозиторієм для
дочірнього плагіна, але дочірній плагін має використовувати саме цей субшлях і політику зірок для
монорепозиторіїв.

Поле `kind` — канонічний розрізнювач артефактів DSH. Окремого виду інтеграції не існує: `plugin`
уже означає нативний пакет DSH, тоді як `ecosystem-project` уже означає ширший проєкт з
інтеграцією DSH. Це запобігає суперечливим парам класифікації.

## Основні категорії можливостей

| Значення | Мітка для відображення |
|---|---|
| `user-interface-dashboards` | Інтерфейс користувача та дашборди |
| `memory-rag` | Пам'ять і RAG |
| `search-research` | Пошук і дослідження |
| `coding-developer-tools` | Програмування та інструменти розробника |
| `browser-automation` | Браузер і автоматизація |
| `vision-audio-multimodal` | Зір, звук і мультимодальність |
| `sessions-productivity` | Сесії та продуктивність |
| `security-permissions-approvals` | Безпека, дозволи та погодження |
| `diagnostics-observability` | Діагностика та спостережуваність |
| `models-providers-routing` | Моделі, провайдери та маршрутизація |
| `messaging-notifications` | Обмін повідомленнями та сповіщення |
| `data-external-services` | Дані та зовнішні сервіси |
| `entertainment-customization` | Розваги та персоналізація |

Обирайте категорію, яка найкраще відображає основне призначення плагіна, а не категорію, яка з
найбільшою ймовірністю підвищить помітність.

## Теги інтерфейсу

Стандартні теги інтерфейсу включають `web-ui`, `sidebar`, `settings`, `tui`, `cli`, `desktop`,
`mobile`, `remote`, `editor`, `headless` і `theme`. Додаткові теги можливостей у kebab-case
малими літерами дозволені, якщо вони описують доказ, видимий у закріпленому оригінальному джерелі.

## Область репозиторію

Використовуйте `dedicated` лише тоді, коли зірки репозиторію належать саме каталогізованому
плагіну. Використовуйте `monorepo`, коли плагін є субшляхом або пакетом у ширшому проєкті. Запис
із монорепозиторію має використовувати `popularity.starsPolicy: undefined-parent-repository` і
`popularity.stars: null`.
