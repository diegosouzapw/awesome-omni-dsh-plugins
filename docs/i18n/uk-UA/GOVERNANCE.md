# Управління каталогом

> 🌐 [English](../../docs/GOVERNANCE.md) · **Українська**

> **Неофіційний проєкт спільноти. Не пов'язаний із DeepSeek, не схвалений і не спонсорований компанією DeepSeek.**
> Назви та товарні знаки DeepSeek належать їхньому власнику.

Як управляється публічний каталог: хто вирішує, що потрапляє всередину, у якому порядку
враховуються конкурентні внески, які перевірки виконуються автоматично, а які рішення залишаються
за людьми. Політики, на які тут посилаються, містяться в [CONTRIBUTING.md](../../CONTRIBUTING.md),
[docs/CREDIT.md](../../docs/CREDIT.md) і [docs/RANKING.md](../../docs/RANKING.md); ця сторінка
описує, як вони поєднуються.

## Принципи

1. **Пріоритет автора.** Каталог існує, щоб робити роботу авторів помітною, а не щоб привласнювати
   її. Для того самого канонічного плагіна прямий pull request автора має пріоритет над будь-яким
   відкритим громадським кураторським або автоматизованим pull request — повний порядок
   пріоритетів і правила ідентичності в Git у [docs/CREDIT.md](../../docs/CREDIT.md).
2. **Один плагін — один перевірений pull request.** Без пакетних злиттів, без згенерованих масових
   імпортів у публічний каталог. Кожен запис заслуговує на власне рев'ю.
3. **Докази понад довіру.** Кожне публічне поле простежується до оригінального репозиторію автора
   на закріпленому коміті. Зелена автоматична перевірка ніколи не приймається як доказ походження.
4. **Завжди неофіційно.** Жоден стан каталогу не подається як рев'ю, сертифікація чи схвалення
   DeepSeek.

## Як зміни потрапляють у `main`

Усі зміни потрапляють у `main` через перевірені pull request — прямих пушів немає. Робоча
політика для гілки за замовчуванням:

- **Лише pull request.** Записи каталогу, документація та зміни схеми потрапляють через PR; PR
  каталогу мають дотримуватися правила «один плагін на гілку» з
  [CONTRIBUTING.md](../../CONTRIBUTING.md).
- **Лінійна історія.** PR інтегруються так, щоб `main` зберігав лінійну, аудитовану історію;
  злита публічна історія не переписується. Якщо кураторський запис злито до того, як автор
  зголосився, автор заявляє права на нього або виправляє його наступним внеском замість
  переписування історії.
- **Розв'язання гілок рев'ю.** Розмови рев'ю розв'язуються перед злиттям; нерозв'язаний зворотний
  зв'язок блокує інтеграцію.
- **Злиття мейнтейнером.** Лише мейнтейнер зливає запис плагіна, і лише після того, як усі шлюзи з
  [CONTRIBUTING.md](../../CONTRIBUTING.md) → «Перевіркові шлюзи, колізії та злиття» пройдено на
  поточному коміті PR.

## Перевірка `catalog-validation`

Кожен pull request, що зачіпає `catalog/plugins/`, `schemas/` або сам workflow, запускає завдання
`catalog-validation` (`.github/workflows/validate-catalog.yml`), закріплене на опублікованому CLI:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**Що вона перевіряє** — лише локальну структуру та семантику:

- Безпечний парсинг YAML кожного запису в `catalog/plugins/`.
- Відповідність публічній схемі (див. [docs/SCHEMA.md](../../docs/SCHEMA.md)).
- Парсинг виразів SPDX, точні версії SemVer, коректні значення цілісності SHA-512 SRI.
- Відхилення дублікатів: без повторюваних ID записів і без повторюваних канонічних ключів
  «вузол репозиторію + субшлях».
- Навмисно порожній каталог проходить (`0 entries valid; catalog is empty`).

**Чого вона НЕ перевіряє** — а отже, чого зелена перевірка ніколи не доводить:

- Віддалену ідентичність репозиторію: вона не звертається до GitHub і не розв'язує вузловий ID
  репозиторію відносно URL.
- Докази на закріпленому коміті: описи, ліцензії, інтеграція з DSH і докази smoke не завантажуються
  та не інспектуються.
- Власність автора, кількість зірок чи колізії з відкритими pull request.

Ці рішення належать до окремих шлюзів походження мейнтейнерів, що застосовуються перед злиттям і
описані в [CONTRIBUTING.md](../../CONTRIBUTING.md). Локальна перевірка — це нижня межа, а не
планка.

## Статуси верифікації

Верифікація записується для кожного запису відносно його точного закріпленого коміта з
використанням статусів, визначених у публічній схемі (`eligible`, `verified`, `stale`,
`unavailable`, `archived`, `quarantined`). Два позитивні статуси навмисно вузькі:

- `eligible` — публічну структуру та нативну інтеграцію з DSH перевірено.
- `verified` — додатково, установчий smoke-тест пройшов для закріпленого джерела чи пакета; схема
  вимагає наявності запису smoke-тесту.

Жоден статус — і жоден інший — не є схваленням, гарантією чи сертифікацією безпеки. Повна
семантика, включно з тим, як статуси взаємодіють із ранжуванням, — у
[docs/RANKING.md](../../docs/RANKING.md); форма запису — у [docs/SCHEMA.md](../../docs/SCHEMA.md).

## Заявлення прав, виправлення та видалення

Структуровані форми issue на GitHub (`.github/ISSUE_TEMPLATE/`) — це врегульований шлях зміни
запису, який подавали не ви:

| Форма           | Хто використовує                              | Результат                                             |
| -------------- | ---------------------------------------- | --------------------------------------------------- |
| **Claim**      | Автор, чий плагін каталогізував хтось інший | Власність прив'язується до оригінального джерела; далі автор може робити внески безпосередньо |
| **Correction** | Будь-хто, хто помітив неточні публічні метадані | Перевірене виправлення відповідного запису             |
| **Removal**    | Автор, який хоче видалити свій запис, або заявник про порушення політики | Перевірене видалення або карантин запису |

Правила, що стосуються всіх трьох процесів:

- Заявлення власності мають підтверджуватися перевірюваними публічними доказами (власність
  репозиторію, авторство пакета, метадані маніфесту або історія закріпленого джерела) — коментар у
  Discussion не встановлює авторства ([docs/CREDIT.md](../../docs/CREDIT.md)).
- Проблеми безпеки плагіна, внесеного до каталогу, спершу адресуються власному супровіднику цього
  плагіна; потім бік каталогу обробляє виправлення або карантин без публікації деталей експлойта
  ([SECURITY.md](../../SECURITY.md)).
- Ніколи не включайте у форму облікові дані, приватні контактні дані чи інші секрети.

## Ролі

- **Автори** володіють своїми плагінами та пріоритетом своїх записів. Вони можуть робити внески
  безпосередньо, схвалювати кураторство спільноти або заявляти права/виправляти/видаляти наявний
  запис.
- **Учасники спільноти** можуть кураторувати записами для авторів, які ще не зробили внеску, за
  правилами поважного контакту та вказівки авторства з [docs/CREDIT.md](../../docs/CREDIT.md).
  Кураторство ніколи не має пріоритету над пізнішим прямим внеском автора.
- **Мейнтейнери** проводять рев'ю, застосовують шлюзи походження, розв'язують колізії та
  зливають. Вони також підтримують сайт
  ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online)) і опублікований CLI із
  закритого джерела; публічні дані, схема та політики цього репозиторію — саме те, що споживають
  ці поверхні.
