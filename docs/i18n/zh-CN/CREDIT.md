# 创作者署名与拉取请求优先级

> 🌐 [English](../../CREDIT.md) · [Português (Brasil)](../pt-BR/CREDIT.md) · **中文（简体）**

本目录的存在是为了让独立开发的 DSH 相关作品被人发现,而不会剥夺其创作者的所有权。公开条目会引用
原始仓库和一个不可变的源代码提交。

## 同一插件的优先级

<!-- creator-first:direct-pr-supersedes-curation-and-automation -->

1. 由插件创作者或所属组织开启的拉取请求。
2. 经创作者明确批准或共同撰写的社区拉取请求。
3. 已存在的有效社区拉取请求。
4. 目录自动化拉取请求。
5. 没有公开拉取请求的私有候选项。

创作者直接提交的拉取请求始终优先,并会取代针对同一规范插件的任何未合并社区策展或自动化拉取请
求,无论哪个先开启或进度更靠前。创作者的拉取请求将成为审查载体;他们的分支绝不会被覆盖、强制推送
或移植进策展拉取请求中。如果策展条目已经合并,历史记录会保持完整,创作者可以通过新的贡献进行认领
或更正。

## 公开署名

每个目录条目都携带创作者的公开 GitHub 用户名、原始仓库、仓库节点 ID、插件子路径和完整的固定提
交。公开的创作者主页是从这一个用户名派生得出的,而不是作为第二个身份单独存储。单独的维护者溯源门
禁负责解析节点 ID,并拒绝仓库 URL 不一致的情况。拉取请求描述中应写明 `Created by @handle`,并包含
源仓库和源提交的元数据。

在 Discussion 中发帖或评论的人不会被自动视为创作者。所有权必须由仓库所有者或所属组织、软件包作者
身份、清单元数据或确切的固定源代码历史来支持。

## Git 身份

<!-- creator-first:source-bound-git-identity -->

提交作者身份和拉取请求作者身份是两回事。创作者本人发起的拉取请求会将创作者列为拉取请求作者,其提
交也会自然保留作者身份。维护者或自动化账号可以作为提交者或经验证的共同作者出现,但绝不能取代创作
者的作者身份。

对于策展提交,只有当确切的身份与来源绑定且可公开验证时——例如已经附加在创作者原始仓库提交上的身
份——才可以将创作者列为 Git 作者,或添加 `Co-authored-by` 尾注。绝不能猜测电子邮件地址、编造 noreply
地址,或使用在授权公开来源之外找到的私人地址。

当没有可验证的 Git 身份时,由策展人或自动化账号担任提交作者,并给出明确的可见署名作为替代:在条
目和拉取请求中写明 `Created by @handle`、与之匹配的公开主页,以及指向原始仓库的链接。无论 Git 身份
映射如何,始终都需要在 YAML 中提供可见的署名。后续创作者直接提交的拉取请求会替代未合并的策展拉取
请求,而不是继承其人为构造的历史。

## 礼貌的创作者提及

策展拉取请求会在其描述中使用一次礼貌的公开 `@creator` 提及,并紧邻原始仓库链接。这可以邀请创作者
进行审查,或用直接拉取请求替换它。不要重复提及、开启推广性 issue、跨平台转发,或发送未经请求的私
信。

## 目录许可证与上游许可证的区别

目录的事实性内容和编辑性 YAML 元数据依据 CC0-1.0 公开贡献至公共领域。这一贡献不会改变上游插件自身
的许可证。上游代码、文档、截图、徽标及其他创意素材仍然受其原始许可证约束,并归其原始所有者所有。
