# 贡献指南

> 🌐 [English](../../CONTRIBUTING.md) · [Português (Brasil)](../pt-BR/CONTRIBUTING.md) · **中文（简体）**

> **非官方社区项目,与 DeepSeek 无关联、未经其认可,也未获其赞助。**
> DeepSeek 的名称与标识归其各自所有者所有。

感谢你为改进本目录所做的贡献。贡献遵循以创作者为先的原则:使用原始仓库证据、保留署名,并保证每个插件都可独立评审。目录在设计上从空目录开始;任何条目都必须经过独立评审的拉取请求(PR)才能被接受。

## 从创作者开始

始终优先接受由插件创作者本人或所属组织直接开启的拉取请求。如果创作者已准备好贡献代码,应使用他们自己的分支和拉取请求,而不是在策展人或自动化分支中重新创建他们的工作。

当社区策展有助于尚未开启拉取请求的创作者时,欢迎这样的贡献。但这并不会为后续创作者直接提交的贡献建立所有权或优先权。

## 每个分支和拉取请求对应一个插件

为单个插件创建一个专用分支,并从该分支开启一个拉取请求。该分支和拉取请求必须只创建或修改 `catalog/plugins/` 下的一个 YAML 文件。不要在该分支或拉取请求中混入其他插件、文档清理、生成的索引或无关的维护工作。

条目 ID 和文件名必须是同一个小写短横线命名(kebab-case)值。维护者会逐个审查并合并每个插件的拉取请求;包含多个插件的批量提交不会被拆分或部分合并。

## 溯源到原始来源

每一个公开字段都必须依据固定提交(pinned commit)处的原始创作者仓库、软件包、清单文件、README、许可证或发行版重新构建。不要照抄其他目录或聚合网站的文字描述、分类归属、截图、排名、徽章或生成的元数据。在综合项目、市场、列表或聚合网站中找到的链接只是一条线索,不是证据,也不是插件的来源。

切勿将综合项目、聚合网站、市场、安装器目录或列表本身作为目录条目提交,即使它可以被独立安装。应仅将其作为线索,并将每个可独立安装的子插件溯源到其真实的创作者和原始仓库。位于创作者真实单体仓库(monorepo)中的插件,可以从其确切子路径提交,但必须遵循下文的单体仓库星标政策。

## 必需的证据

请在拉取请求中提供以下全部内容:

- 原始仓库的规范公开 URL 及其不可变的仓库节点 ID(node ID)。维护者会在单独的溯源审查环节解析该节点 ID,并拒绝 URL 不一致的情况。
- 创作者的公开 GitHub 用户名及与之匹配的公开主页 URL。YAML 只存储一次用户名;主页 URL 通过 `https://github.com/<handle>` 推导得出。
- 完整的 40 个字符的源提交 OID,以及确切的插件子路径;若插件位于仓库根目录,则为 `null`。
- 一段长度受限的英文描述,以及该固定提交处对应的证据路径。
- 从 [docs/CATEGORIES.md](../../docs/CATEGORIES.md) 中选取的制品 `kind`(种类)、主分类和标签。
- 在固定提交处有证据支持的完整上游 SPDX 许可证表达式。
- 一个规范的安装描述符,固定到确切的 npm 版本,或固定到源仓库、完整提交和子路径。该描述符是数据,绝不是 shell 命令。
- 原生 DSH 集成证据及其在固定提交处的路径。
- 针对该确切制品固定版本的、已有的非敏感冒烟测试(smoke test)证据,或明确填写 `not run`。不要仅仅为了准备目录贡献,就安装该插件或执行 `preinstall`、`install`、`postinstall`、`prepare` 等软件包/插件生命周期代码。
- 对于专用仓库,提供该确切仓库的可验证星标数,以及对应的公开来源和核查时间。对于单体仓库中的插件,使用下文要求的空值(null)政策。
- 若存在公开的 Discussion 或评论溯源信息,请一并提供;否则使用 `null`。
- 机器可读的 `unofficial: true` 值。

如果尚不存在符合条件的冒烟测试,请使用 `verification.status: eligible` 和 `verification.smokeTest: null`。只有当该确切固定版本存在可供审查的冒烟测试证据时,才使用 `verified`。这两种状态都不代表官方背书或安全认证。

切勿提交凭据、Cookie、私人电子邮件地址、未公开的源代码或其他敏感信息。

## YAML 与模式(schema)规则

创建 `catalog/plugins/<plugin-id>.yaml` 文件,并对照 [`schemas/plugin.schema.yaml`](../../schemas/plugin.schema.yaml) 进行校验。该模式文件是字段名称和允许取值的唯一真实来源;[docs/CATEGORIES.md](../../docs/CATEGORIES.md) 定义了如何选择唯一的制品种类、主分类、标签和仓库范围。

npm 描述符必须包含有效的软件包名称和确切版本号。公开模式会拒绝形如选项参数的值和无边界的值,但不会重新实现 SemVer 或 SRI 的校验逻辑:目录校验必须解析版本号、要求确切的 SemVer,并将任何完整性(integrity)值解析为有效的 SHA-512 SRI。源描述符绑定到 `source.repository`、`source.commit` 和 `source.subpath`,不会重复存储可变的源信息。

安装器必须使用参数数组、禁用 shell 执行,并在被调用命令支持的情况下,在目录提供的位置参数前放置选项终止符。提交校验绝不能调用安装器或插件生命周期。

<!-- catalog-validation:local-structure-and-semantics-only -->

`catalog validate` 是一项本地的、只读的结构与语义检查。它会解析安全 YAML、校验公开模式、解析 SPDX 表达式、要求确切的 SemVer 和有效的 SHA-512 SRI,并拒绝重复的 ID 以及重复的“仓库节点 ID + 子路径”规范键。它不会联系 GitHub、解析仓库身份,也不会检查固定提交处的证据路径。

<!-- maintainer-gate:repository-origin-and-pinned-evidence -->

在条目达到 `eligible` 状态之前,维护者会单独解析规范仓库和节点 ID,将创作者与原始来源绑定,并检查在 `source.commit` 处声明的描述、许可证、DSH 集成和冒烟测试证据。本地校验通过并不能证明溯源或来源的真实性。

## 仓库星标

只能记录经过验证、确切属于该专用插件仓库的星标数。绝不能将父项目的星标归属给存放在更大单体仓库(monorepo)中的插件。单体仓库中的条目仍然可以进入目录的功能性板块,但必须声明:

```yaml
repositoryScope: monorepo
popularity:
  starsPolicy: undefined-parent-repository
  stars: null
```

专用条目使用 `repositoryScope: dedicated`、`starsPolicy: exact-repository`,以及在同一仓库上观察到的非负星标数。在提交热度数据前,请阅读 [docs/RANKING.md](../../docs/RANKING.md)。

## 创作者优先与礼貌联系

对于同一个规范插件,优先级如下:

1. 由创作者或所属组织开启的拉取请求。
2. 经创作者明确批准的社区拉取请求。
3. 已存在的有效社区策展拉取请求。
4. 目录自动化拉取请求。

创作者直接提交的拉取请求会取代任何未合并的策展或自动化拉取请求,无论哪个先开启或进度更靠前。创作者的拉取请求将成为审查载体;维护者不会强制推送创作者的分支,也不会将其工作移植到策展拉取请求中。如果策展条目已经合并,公开历史记录不会被改写。创作者可以先使用认领(claim)或更正请求,然后再直接贡献一个后续的拉取请求。

策展拉取请求应在其描述中使用一次礼貌的公开 `@creator` 提及,并附上原始仓库的链接,邀请创作者审查或用直接拉取请求替换它。不要重复提及、开启推广性 issue、跨平台转发、发送未经请求的私信,或以其他方式打扰创作者。

<!-- creator-first:source-bound-git-identity -->

由创作者撰写的拉取请求和提交会自然保留创作者的署名。策展提交只有在存在与来源绑定、可公开验证的身份时,才能使用创作者的 Git 作者身份或 `Co-authored-by` 尾注。绝不能编造或猜测电子邮件地址。当没有可验证的 Git 身份时,由策展人担任提交作者,并在 YAML 和拉取请求中明确给出 `Created by @handle` 的署名以及原始仓库链接。维护者或自动化账号可以担任提交者或经验证的共同作者,但绝不能取代创作者的作者身份。完整政策请参见 [docs/CREDIT.md](../../docs/CREDIT.md)。

## 校验命令与可用性

该 npm CLI 以 `@diegosouza.pw/dsh-plugins@0.1.0` 发布,因此下面的命令目前可以通过 `npx` 使用。请按原样使用这些命令;贡献者不应自行编造替代命令。

请在仓库根目录运行以下命令:

```bash
npx @diegosouza.pw/dsh-plugins catalog validate --catalog .
npx @diegosouza.pw/dsh-plugins catalog docs-check .
npx @diegosouza.pw/dsh-plugins catalog github-forms-check .
```

`catalog validate` 只执行上文所述的本地 YAML、模式、SPDX、确切 SemVer、SHA-512 SRI 和重复项检查,并接受有意为之的零条目目录。它不能证明远程仓库身份或固定来源证据。其他命令会检查所需的公开文档和结构化的 GitHub issue 表单。这些命令在本地通过并不会放宽证据要求;维护者在合并前仍会应用每一项对应的发布门禁。

## 审查门禁、冲突与合并

维护者在合并前会对当前拉取请求的提交应用每一项门禁:

1. **范围:** 一个专用分支、一个插件 YAML 文件,且没有无关的改动。
2. **原始身份:** 创作者、规范仓库、节点 ID、完整提交和子路径彼此一致。
3. **模式与证据:** YAML、分类、SPDX、安装固定版本、DSH 证据和冒烟测试状态在不执行插件生命周期代码的情况下保持内部一致。
4. **热度:** 专用仓库的星标可在该确切仓库上验证,或者单体仓库的星标为 `null` 并附带 `undefined-parent-repository`。
5. **文档与表单:** 公开文档、Markdown 代码围栏和结构化表单保持有效。
6. **冲突与去重:** 没有任何已合并条目或未关闭拉取请求代表同一个规范插件。

不同的名称或 ID 并不能使重复的插件变得不同。相同的仓库节点 ID 和子路径、相同的规范软件包,或其他可证明相同的安装目标,都应被视为冲突。在合并前必须解决别名和相互竞争的拉取请求。当创作者直接提交的拉取请求与策展或自动化拉取请求发生冲突时,创作者的拉取请求获胜;否则维护者会选定一个作为审查载体,并关闭或重定向其余重复项,而不是将两者都合并。

只有在所有门禁都通过后,才会由维护者合并插件。每个被接受的插件都是单独合并的;通过校验、策展或自动化并不意味着会自动合并或批量合并。

## 拉取请求检查清单

- [ ] 我使用了一个专用分支,并且该 PR 只改动了一个插件条目。
- [ ] 来源是原始创作者仓库,而不是综合项目或聚合网站。
- [ ] 创作者用户名/主页、仓库、节点 ID、子路径和完整提交都已提供证据。
- [ ] 种类(kind)、分类和标签遵循 `docs/CATEGORIES.md`。
- [ ] SPDX 许可证和固定的安装描述符都已提供证据。
- [ ] 原生 DSH 集成,以及冒烟测试结果或 `not run` 状态,都已提供证据。
- [ ] 我没有为准备此贡献而执行插件或软件包生命周期代码。
- [ ] 专用仓库的星标可验证,或单体仓库的星标使用了所要求的空值政策。
- [ ] 我已检查是否存在针对同一规范插件的现有条目或未关闭的拉取请求。
- [ ] 该条目已明确标注为非官方,且不包含任何敏感信息或私人个人数据。

## 语言政策

发布文档和目录描述仅提供英文版本。覆盖 43 种语言的推广计划仍是 MVP 之后的待办事项;请勿添加空的语言文档或自动批量翻译。
