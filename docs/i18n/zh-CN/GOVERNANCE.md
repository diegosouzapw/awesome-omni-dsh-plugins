# 目录治理

> 🌐 [English](../../GOVERNANCE.md) · [Português (Brasil)](../pt-BR/GOVERNANCE.md) · **中文（简体）**

> **非官方社区项目,与 DeepSeek 无关联、未经其认可,也未获其赞助。**
> DeepSeek 的名称与标识归其各自所有者所有。

本页说明公开目录如何被治理:由谁决定哪些内容可以收录、相互竞争的贡献按何种顺序被采纳、哪些检查是
自动运行的,以及哪些判断仍然由人来做。本页引用的政策位于 [CONTRIBUTING.md](../../CONTRIBUTING.md)、
[docs/CREDIT.md](../../docs/CREDIT.md) 和 [docs/RANKING.md](../../docs/RANKING.md) 中;本页描述的是这些政策
如何相互配合。

## 原则

1. **创作者优先。** 本目录的存在是为了让创作者的作品被人发现,绝不是为了从他们手中夺走所有权。对
   于同一个规范插件,创作者直接提交的拉取请求会取代任何未合并的社区策展或自动化拉取请求——完整的
   优先级顺序和 Git 身份规则见 [docs/CREDIT.md](../../docs/CREDIT.md)。
2. **一个插件,一个经过评审的拉取请求。** 不进行批量合并,也不向公开目录进行生成式的批量导入。每个
   条目都要经过独立的评审。
3. **证据优先于信任。** 每个公开字段都可以追溯到固定提交处的原始创作者仓库。自动化检查通过绝不能
   被视为来源真实性的证明。
4. **始终非官方。** 任何目录状态都不会被呈现为 DeepSeek 的审查、认证或背书。

## 变更如何进入 `main`

所有变更都通过经过评审的拉取请求进入 `main`——没有直接推送。针对默认分支的工作政策:

- **仅接受拉取请求。** 目录条目、文档和模式(schema)的变更都通过 PR 进入;目录相关的 PR 必须遵循
  [CONTRIBUTING.md](../../CONTRIBUTING.md) 中每个分支对应一个插件的规则。
- **线性历史。** PR 会以保持 `main` 线性、可审计历史的方式进行整合;已合并的公开历史不会被改写。如
  果某个策展条目在创作者出现之前就已合并,创作者应通过后续贡献进行认领或更正,而不是改写历史。
- **评审线程需已解决。** 评审对话必须在合并前解决;未解决的反馈会阻止合并。
- **由维护者合并。** 只有维护者才能合并插件条目,并且只有在当前 PR 提交通过
  [CONTRIBUTING.md](../../CONTRIBUTING.md) → “审查门禁、冲突与合并”中的每一项门禁之后才能合并。

## `catalog-validation` 检查

任何触及 `catalog/plugins/`、`schemas/` 或工作流本身的拉取请求,都会运行 `catalog-validation` 任
务(`.github/workflows/validate-catalog.yml`),该任务固定使用已发布的 CLI:

```bash
npx --yes omni-dsh-plugins catalog validate --catalog .
```

**它校验什么**——仅本地结构和语义:

- 对 `catalog/plugins/` 下每个条目进行安全 YAML 解析。
- 是否符合公开模式(见 [docs/SCHEMA.md](../../docs/SCHEMA.md))。
- SPDX 表达式解析、确切的 SemVer 版本号、有效的 SHA-512 SRI 完整性值。
- 拒绝重复项:没有重复的条目 ID,也没有重复的“仓库节点 ID + 子路径”规范键。
- 刻意为之的零条目目录能够通过(`0 entries valid; catalog is empty`)。

**它不校验什么**——因此绿色检查从来不能证明以下内容:

- 远程仓库身份:它不会联系 GitHub,也不会将仓库节点 ID 与 URL 进行核对。
- 固定提交处的证据:描述、许可证、DSH 集成和冒烟测试证据不会被抓取或检查。
- 创作者所有权、星标数,或是否与未关闭的拉取请求存在冲突。

这些判断属于维护者在合并前应用的单独溯源门禁,详见 [CONTRIBUTING.md](../../CONTRIBUTING.md)。本地
检查是最低门槛,而不是最终标准。

## 验证状态

验证是针对每个条目在其确切固定提交处进行记录的,使用公开模式中定义的状态(`eligible`、
`verified`、`stale`、`unavailable`、`archived`、`quarantined`)。这两个正向状态刻意保持狭窄:

- `eligible` —— 公开结构和原生 DSH 集成已通过校验。
- `verified` —— 在此基础上,针对固定源代码或软件包的安装冒烟测试也已通过;模式要求必须存在冒烟
  测试记录。

无论是这两个状态还是其他任何状态,都不代表官方背书、保证或安全认证。完整语义(包括这些状态如何
影响排名)见 [docs/RANKING.md](../../docs/RANKING.md);记录形状见 [docs/SCHEMA.md](../../docs/SCHEMA.md)。

## 认领、更正与移除

结构化的 GitHub issue 表单(`.github/ISSUE_TEMPLATE/`)是变更非你本人提交条目的规范途径:

| 表单           | 使用者                              | 结果                                             |
| -------------- | ---------------------------------------- | --------------------------------------------------- |
| **认领(Claim)**      | 插件被他人策展收录的创作者 | 所有权被绑定到原始来源;创作者随后可以直接贡献 |
| **更正(Correction)** | 发现公开元数据不准确的任何人 | 对受影响条目进行经过评审的修复             |
| **移除(Removal)**    | 希望移除自己插件收录的创作者,或政策违规行为的举报者 | 经过评审的移除或将条目标记为隔离 |

适用于以上三种流程的规则:

- 所有权认领必须有可验证的公开证据支持(仓库所有权、软件包作者身份、清单元数据或固定的源代码历
  史)——在 Discussion 中评论并不能确立创作者身份([docs/CREDIT.md](../../docs/CREDIT.md))。
- 已收录插件中的安全问题应首先提交给该插件自身的维护者;目录这一侧随后会在不公开利用细节的情况下
  处理更正或隔离([SECURITY.md](../../SECURITY.md))。
- 切勿在表单中包含凭据、私人联系方式或其他敏感信息。

## 角色

- **创作者** 拥有其插件及其收录条目的优先权。他们可以直接贡献、批准社区策展,或对现有条目进行
  认领/更正/移除。
- **社区贡献者** 可以为尚未贡献的创作者策展条目,须遵循 [docs/CREDIT.md](../../docs/CREDIT.md) 中的
  礼貌联系和署名规则。策展绝不会优先于后续创作者的直接贡献。
- **维护者** 负责评审、应用溯源门禁、解决冲突并进行合并。他们还从私有源代码维护网站
  ([dsh-plugins.omniroute.online](https://dsh-plugins.omniroute.online))和已发布的 CLI;本仓库的公开
  数据、模式定义和政策正是这些界面所消费的内容。
